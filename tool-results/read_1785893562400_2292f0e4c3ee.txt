    15→## TL;DR — The biggest discovery
    16→
    17→**`libkr64.so` is NOT a JNI library.** It is a standalone ELF executable disguised as a shared object, launched by the Android kernel via `fork`+`exec` (not by `System.loadLibrary`). Its `.interp` program-header entry points at `libkrloader64.so` — a custom dynamic linker that VM built from AOSP source. The kernel exec's `libkr64.so` → reads its `PT_INTERP` → exec's `libkrloader64.so` → `libkrloader64.so` loads `libkr64.so` and jumps to its `_start` (entry point `0x4e04`).
    18→
    19→So the previously-stated premise ("3 visible imports: mmap, socket, socketpair") was wrong. `libkr64.so` has **187 imported symbols** (full list below). It is the "kernel replacement" daemon — a real Linux process that creates the per-VM virtual device tree (`/dev/binder`, `/dev/event`, `/dev/qemu_pipe`, `/dev/gb`, `/dev/input/touch`, …) by `mknodat`-ing socket/char-device nodes and `bind`-ing AF_UNIX sockets to them.
    20→
    21→`libkrloader64.so` is itself a regular executable (its own `.interp = /system/bin/linker64`) that embeds a static copy of bionic libc. It exports only `_start` and imports only `calloc`/`free`/`malloc`/`realloc` from system libc. Built from AOSP source as `EXECUTABLES/krloader_intermediates` for product `marlin` (Pixel XL).

    52→### Entry point — `_start`
    53→
    54→`_start` is at file offset `0x4db0` (entry `0x4e04` just branches there). It is the standard bionic libc `_start` trampoline:
    55→
    56→```
    57→0x4db0: stp x29, x30, [sp, #-64]!
    58→0x4dc0: adrp x1, 0x16f000 ; ldr x1, [x1, #2480] ; structors.preinit_array = 0x16f410
    59→0x4dd0: adrp x1, 0x16f000 ; ldr x1, [x1, #2488] ; structors.fini_array  = 0x16f4e0
    60→0x4de0: adrp x1, 0x16f000 ; ldr x1, [x1, #2496] ; structors.fini        = 0x16f4f8
    61→0x4dec: adrp x0, 0x16f000 ; ldr x2, [x0, #2504] ; main = 0x7244
    62→0x4df8: ldr x0, [x29, #24] ; raw_args
    63→0x4dfc: mov x1, #0         ; onexit = NULL
    64→0x4e00: bl __libc_init
    65→```
    66→
    67→The `.got` relocation entries resolve the structors pointers and `main()`:
    68→
    69→| GOT slot   | Value     | Meaning |
    70→|------------|-----------|---------|
    71→| 0x16f9b0   | 0x16f410  | `.preinit_array` (empty) |
    72→| 0x16f9b8   | 0x16f4e0  | `.fini_array` (empty) |
    73→| 0x16f9c0   | 0x16f4f8  | (other) |
    74→| 0x16f9c8   | **0x7244** | **`main()` address** |
    75→
    76→### `main()` @ `0x7244`
    77→
    78→A 1.4 KB OLLVM-flattened function. Visible structure:
    79→1. Calls `0x13fd2c(arg)` — initial setup
    80→2. Iterates `argv[]` looking for an arg count of 7 (sets a flag `w10 = 1` if `argc == 7`)
    81→3. `memset(&config_struct, 0, 0x50)` — zeroes an 80-byte config struct at `.bss+0x1ee8`
    82→4. Calls `0x115a90()` — returns a handle (stored at `config_struct[0]`)
    83→5. If handle != -1, bulk-copies 64 bytes of rodata (`4× ldr qN, [rodata]`) into `config_struct[8..64]`, plus a 64-bit literal `0x78_2eee_c050` at offset 72
    84→
    85→This matches a configuration-loading pattern: parse argv, build a config struct (likely VM ID + paths + flags), then dispatch.

   542→## 5. The 3 unix-socket servers (bind clusters)
   543→
   544→There are **3 logical `bind()` call sites** (each appears twice in the disassembly due to OLLVM control-flow flattening):
   545→
   546→### 5.1 `bind @ 0x134328` — netlink_server
   547→
   548→Snprintf format string is at `.data+0x12d0` (vaddr `0x1712d0`), XOR key `0x2c`:
   549→```
   550→/data/data/com.clone.android.dual.space/vm/vm%d/dev/netlink_server
   551→```
   552→
   553→The function:
   554→1. `socket(AF_UNIX=1, SOCK_STREAM=2, 0)`
   555→2. `memset(&sockaddr_un, 0, 110)`
   556→3. `getpid()` and `gettid()` (for the snprintf args)
   557→4. `__snprintf_chk(buf, 106, 0, 108, fmt, vmid, getpid, gettid)` — formats the path
   558→5. `unlink(path)` — remove stale socket file
   559→6. `__strlen_chk(path, 108)` (UNIX_PATH_MAX)
   560→7. `bind(sockfd, &sockaddr_un, path_len + 3)`
   561→8. Then falls through to the `accept4` loop at `0x135f64`
   562→
   563→### 5.2 `bind @ 0x1381d0` — netlink_client/nl_dhcp_%d_%d
   564→
   565→Snprintf format at `.data+0x1370` (vaddr `0x171370`), XOR key `0x37`:
   566→```
   567→/data/data/com.clone.android.dual.space/vm/vm%d/dev/netlink_client/nl_dhcp_%d_%d
   568→```
   569→
   570→Args: `(vmid, getpid, gettid)`. This is the per-guest-thread DHCP netlink client socket (the guest's DHCP client connects here to receive virtual DHCP offers).
   571→
   572→### 5.3 `bind @ 0x1387f8` — netlink_client/netdevice_%d_%d
   573→
   574→Snprintf format at `.data+0x1400` (vaddr `0x171400`), XOR key `0x1e`:
   575→```
   576→/data/data/com.clone.android.dual.space/vm/vm%d/dev/netlink_client/netdevice_%d_%d
   577→```
   578→
   579→This is the per-guest-thread netlink client socket for virtual network-device events (link up/down, route changes, etc.).
   580→
   581→### 5.4 Where is `bind` for `/dev/binder`, `/dev/event`, `/dev/qemu_pipe`?
   582→
   583→**These are NOT in libkr64.so.** The 3 bind clusters above are all the bind calls in the entire binary — and they're all for netlink emulation. The other virtual device sockets (`/dev/binder`, `/dev/event`, `/dev/qemu_pipe`) are created by **`libvm.so`** (the JNI library loaded by the VM Java app), not by `libkr64.so`. This matches the `VM_JAVA_ANALYSIS.md` finding that `BinderService.setupBinder(vmId, ...)` is a JNI call into `libvm.so`.
   584→
   585→So the architecture is:
   586→- **`libkr64.so`** (separate process) creates: netlink sockets, `/dev/vmproc`, `/dev/__kmsg__`, `/dev/__krlog__`, `/dev/input/touch`, `/dev/gb`, `/dev/gb2` (Android 11), `/dev/qemu_pipe` (or `/dev/goldfish_pipe`), `/dev/socket/process_pid`, `/dev/.coldboot_done`, `/dev/.busybox`, `/dev/tmpfs`, `/dev/tmpfs/ns`, `/dev/__properties__`, `/dev/ashmem`, `/dev/ashmemsim`, `/dev/block/vdc`, `/dev/fuse`, `/dev/hal/power_supply%s`, `/dev/socket/logdw`, `/dev/socket/logdr`, `/dev/log`

   591→## 6. The `mknodat` call site — device file creation
   592→
   593→There is exactly **one** logical `mknodat()` call in libkr64.so, at `0x11d770`. The disassembly:
   594→
   595→```
   596→0x11d69c: and w8, w22, #0xf000       ; w8 = mode & S_IFMT
   597→0x11d6a0: orr w8, w8, #0x4000        ; w8 |= S_IFSOCK (partial)
   598→0x11d6a4: cmp w8, #0x6, lsl #12      ; compare with 0x6000 (S_IFBLK)
   599→0x11d6a8: b.ne 0x11d760              ; if NOT block device, jump to mknodat
   600→                                     ; (block devices fall through to openat+write)
   601→0x11d760: mov w0, w24                ; dirfd (likely AT_FDCWD = -100)
   602→0x11d764: mov x1, x20                ; path (stack buffer)
   603→0x11d768: mov w2, w22                ; mode (S_IFSOCK|0666 or S_IFIFO|0666 etc.)
   604→0x11d76c: mov x3, x21                ; dev (0 for sockets/fifos)
   605→0x11d770: bl mknodat@plt
   606→```
   607→
   608→The function is a **generic `mknod(path, mode, dev)` wrapper** — it dispatches between:
   609→- **mknodat** for sockets/fifos/char/block devices (mode & S_IFMT != S_IFBLK)
   610→- **openat + write + close** for regular files (mode & S_IFMT == S_IFBLK — wait, that's odd; let me re-check)
   611→
   612→Actually re-reading: the branch `b.ne 0x11d760` means "if NOT block device, go to mknodat". The fall-through path (block device) does `syscall(0x38, -100, path, 0x42, 0x1b6)` — `syscall 0x38 = 56 = openat(AT_FDCWD, path, O_CREAT|O_RDWR, 0666)`, then writes 8 bytes and closes. This is the "create regular file and write 8 bytes" path.
   613→
   614→So this is `__kr_mknod(path, mode, dev)`:
   615→```c
   616→int __kr_mknod(const char *path, mode_t mode, dev_t dev) {
   617→    if (S_ISBLK(mode)) {
   618→        // create a regular file with 8-byte content (probably a marker)
   619→        int fd = openat(AT_FDCWD, path, O_CREAT|O_RDWR, 0666);
   620→        write(fd, &dev_or_marker, 8);
   621→        close(fd);
   622→    } else {
   623→        // create actual device node
   624→        mknodat(AT_FDCWD, path, mode, dev);
   625→    }
   626→}
   627→```
   628→
   629→This is used to create:
   630→- `/dev/vmproc`, `/dev/__kmsg__`, `/dev/__kmsg2__`, `/dev/__krlog__`, `/dev/__properties__`, `/dev/socket/process_pid`, `/dev/socket/logdw`, `/dev/socket/logdr`, `/dev/ashmem`, `/dev/ashmemsim`, `/dev/tmpfs`, `/dev/.busybox`, `/dev/.coldboot_done` (all sockets/fifos via mknodat)
   631→- `/dev/gb`, `/dev/gb2` (char devices via mknodat — for graphics buffer)
   632→- `/dev/input/touch` (char device via mknodat — for touch input)
   633→- `/dev/qemu_pipe` / `/dev/goldfish_pipe` (socket via mknodat — for GL transport)
   634→
   635→The path argument is built by the callers via snprintf, using the format strings in `.data` (e.g., `.../vm/vm%d/dev/qemu_pipe`).

   641→### `fork @ 0x13dd14` / `0x13dd5c` (paired)
   642→
   643→Inside a function starting around `0x13dc80`. The prologue saves `x28..x30`, sets up `x29`, then calls `fork()`. The PID is stored in `w24`.

It might be `ptrace` (which is 26) — let me recheck. The aarch64 syscall numbers are different from x86_64. Anyway, this is some kind of pre-fork setup.

   689→## 10. The `syscall()` calls (100 sites)
   690→
   691→Many of the 100 `syscall()` calls bypass PLT and go directly to the kernel. This is intentional — libkr64.so wants to call syscalls that:
   692→1. Don't have a libc wrapper (e.g., `seccomp(SECCOMP_SET_MODE_FILTER, ...)` syscall 277 on aarch64)
   693→2. Are hooked by shadowhook and would be intercepted if called via libc (e.g., `mprotect`, `prctl`)
   694→3. Take a variable number of args (e.g., `fcntl`)
   695→
   696→Sample syscall numbers found by scanning immediate values loaded into `w0` before `bl syscall@plt`:
   697→
   698→| Syscall # | Name (aarch64) | Use |
   699→|-----------|----------------|-----|
   700→| 0x38 (56) | `openat` | create regular files |
   701→| 0x75 (117) | (unknown — possibly `getresuid` or a custom VM syscall?) | pre-fork setup |
   702→| 0x4e (78) | `setpgid` | process group management |
   703→| 0xa1 (161) | `sethostname` | set virtual hostname |
   704→| 0xa7 (167) | `setsid` | create new session |
   705→| 0xb5 (181) | `pivot_root` | change root filesystem |
   706→| 0xc8 (200) | `bind` (syscall form) | socket bind (bypassing libc) |
   707→| 0xca (202) | `listen` (syscall form) | socket listen (since no listen@plt!) |
   708→| 0xd3 (211) | `shutdown` | socket shutdown |
   709→| 0xdc (220) | `clone` (deep flags) | process creation |
   710→
   711→The use of direct syscalls for `bind`/`listen`/`shutdown` confirms that libkr64.so bypasses its OWN shadowhook hooks (which intercept `bind`, `connect`, etc.) when it needs to call the real syscalls. This is the classic shadowhook pattern: hook the libc wrapper, but use direct syscalls internally.

   728→## 12. Seccomp — the "kernel replacement" enforces syscall filters
   729→
   730→Strings decoded from `.data`:
   731→- `INIT.SECCOMP` (key 0xb4)
   732→- `init_seccomp` (key 0x67, only in libkr64.11.so)
   733→- `__NR_rt_sigaction SIGSYS` (key 0x1a, only in libkr64.11.so)
   734→- `BLOCKED.SYSCALL.FAILED` (key 0xc9)
   735→- `blocked syscall failed %d` (key 0xc2 / 0xe2)
   736→
   737→`libkr64.so` installs a **seccomp filter** on the guest process that traps forbidden syscalls, sends SIGSYS, and is caught by a custom SIGSYS handler (installed via `sigaction(SIGSYS, ...)`). The handler logs `BLOCKED.SYSCALL.FAILED` and either emulates the syscall or kills the guest.
   738→
   739→This is how VM "kernel replacement" enforces process isolation — the guest runs in a seccomp sandbox where the only "syscalls" that succeed are the ones libkr64.so chooses to emulate (via the SIGSYS handler).

   743→## 13. `libkrloader64.so` — the custom ELF interpreter
   744→
   745→### Structure
   746→
   747→```
   748→ELF64, AArch64, DYN
   749→Entry point: 0x2cd0
   750→.interp = /system/bin/linker64   ← standard Android linker (the loader is itself loaded by the system linker)
   751→DT_NEEDED: libc++.so, libdl.so, libc.so, libm.so
   752→DT_FLAGS: SYMBOLIC BIND_NOW
   753→Exports: _start (12 bytes), x.0..x.36 (OBJECT, 4 bytes each), y.0..y.37 (OBJECT, 4 bytes each)
   754→Imports: calloc, free, malloc, realloc (only 4 functions from system libc)
   755→Build path (from .dynstr): out_gp/target/product/marlin/obj/EXECUTABLES/krloader_intermediates/LINKED/libkrloader64.so
   756→```
   757→
   758→### `_start` @ `0x2cd0`
   759→
   760→```
   761→0x2cd0: mov x0, sp             ; pass stack pointer
   762→0x2cd4: bl 0x40b0              ; call __libc_init-like function
   763→0x2cd8: br x0                  ; jump to main()
   764→```
   765→
   766→Standard bionic `_start` trampoline. Calls into `0x40b0` (probably `__libc_init`-equivalent) which then calls `main()`.
   767→
   768→### Embedded bionic libc
   769→
   770→`.rodata` (12 KB) contains all of bionic libc's internal strings:
   771→```
   772→bionic/libc/bionic/libc_logging.cpp
   773→legacy_system_prop_area
   774→/dev/socket/logdw
   775→/dev/stderr
   776→ro.logd.timestamp
   777→persist.logd.timestamp
   778→ANDROID_PROPERTY_WORKSPACE
   779→/property_contexts
   780→%s/properties_serial
   781→u:object_r:properties_serial:s0
   782→security.selinux
   783→fsetxattr failed to set context (%s) for "%s"
   784→Access denied finding property "%s"
   785→Access denied adding property "%s"
   786→/sys/kernel/debug/tracing/trace_marker
   787→/proc/self/fd/%d
   788→%s:%d: assertion "%s" failed
   789→%s:%d: %s: assertion "%s" failed
   790→```
   791→
   792→Plus all of `strerror`'s error-message table (`Operation not permitted`, `No such file or directory`, ..., `Exec format error`, `Cannot exec a shared library directly`).
   793→
   794→### What it does
   795→
   796→When the Android kernel `execve`s `libkr64.so`:
   797→1. Kernel reads `libkr64.so`'s `PT_INTERP` = `libkrloader64.so`
   798→2. Kernel actually `execve`s `libkrloader64.so`, passing `libkr64.so` as the "binary to interpret" (via `execve`'s `AT_EXECFN` and the kernel's `binfmt_script` mechanism)
   799→3. `libkrloader64.so` runs `_start`, which calls `__libc_init` (embedded bionic)
   800→4. The embedded bionic linker code loads `libkr64.so` as an ELF binary — parses its program headers, mmap's PT_LOAD segments, applies relocations, resolves DT_NEEDED dependencies (libdl, liblog, libc, libc++, libm — the system libs), calls `.preinit_array` → `.init_array` → `main`
   801→5. `libkr64.so`'s `main()` then runs the VM daemon
   802→
   803→**Why use a custom interpreter instead of just running libkr64.so directly?** Because:
   804→1. **Android restricts exec'ing files from `/data/data/...`** — only files in `/system/bin` can be exec'd directly. By using a custom interpreter, libkrloader64.so (which IS in `/system/bin`? no, it's in `/data/user/0/.../lib64/`) can load libkr64.so from any path.
   805→2. Actually `libkrloader64.so` is also in `/data/user/0/...` — so the question is how it gets exec'd. **Hypothesis:** the VM Java app calls `Runtime.exec("libkrloader64.so libkr64.so")` or `Process.exec()` with these as args.    952→### Why twoyi doesn't need a "kernel replacement"
   953→
   954→twoyi runs the guest in the **same process** as the host (via `libloader.so` which patches the dynamic linker to allow cross-process symbol resolution). The guest shares the host's:
   955→- `/dev/binder` (uses host binder directly)
   956→- `/dev/qemu_pipe` (created by `libOpenglRender.so` for GL transport)
   957→- `/proc`, `/dev`, `/sys` (uses host's directly)
   958→- Network stack (uses host's netlink directly)
   959→
   960→This is simpler but means:
   961→1. No isolation between guest and host (a malicious guest can read host files)
   962→2. No multi-VM support
   963→3. No ability to "fake" a different Android version (the guest sees the host's `/proc/version`, `/system/build.prop`, etc.)
   964→4. No per-VM `/dev/binder` — the guest's `servicemanager` is the host's `servicemanager`
   965→
   966→### What twoyi would need to add to match Virtual Master
   967→
   968→1. **A "kernel replacement" daemon** (like `libkr64.so`) that:
   969→   - Creates per-VM virtual device files via `mknodat`
   970→   - Listens on `/vm%d/dev/event`, `/vm%d/dev/binder`, `/vm%d/dev/netlink_server` unix sockets
   971→   - Installs a seccomp filter on the guest with a SIGSYS handler
   972→   - Manages a per-VM mount namespace
   973→
   974→2. **shadowhook integration** (or equivalent) to hook the guest's `dlopen`/`dlsym` so it loads guest-specific libraries from the VM's data directory.
   975→
   976→3. **A custom ELF interpreter** (or simpler: a `ptrace`-based loader) that can exec the guest from `/data/data/.../lib64/`.
   977→
   978→4. **Binder virtualization** — this is the hardest piece. Either:
   979→   - Implement a binder driver emulation layer (translate `BINDER_WRITE_READ` ioctls on `/vm%d/dev/binder` to host binder calls), OR
   980→   - Use a Java `Proxy` (as VM does) to intercept binder calls at the Java level.
   981→
   982→5. **Netlink emulation** — at minimum, fake `RTM_GETLINK`/`RTM_NEWLINK` so the guest thinks it has network interfaces.

   986→## 16. The binder virtualization mystery — resolved
   987→
   988→The previous analysis (`VM_JAVA_ANALYSIS.md` worklog) showed these XOR-decoded strings in **libvm.so** (NOT libkr64.so):
   989→- `/dev/binder`
   990→- `/vm%d/dev/binder` (per-VM virtual binder)
   991→- `setup_binder: mmap binder file failed`
   992→- `get_binder_version: open /dev/binder failed`
   993→
   994→We now know **binder virtualization is in libvm.so**, not libkr64.so. `libkr64.so` handles everything ELSE:
   995→- /dev/vmproc (proc emulation)
   996→- /dev/__kmsg__ / /dev/__kmsg2__ / /dev/__krlog__ (kernel log)
   997→- /dev/__properties__ (property area)
   998→- /dev/ashmem / /dev/ashmemsim (shared memory)
   999→- /dev/tmpfs / /dev/tmpfs/ns (mount namespace)
  1000→- /dev/socket/process_pid, /dev/socket/logdw, /dev/socket/logdr (Android sockets)
  1001→- /dev/input/touch (touch input)
  1002→- /dev/gb, /dev/gb2 (graphics buffers — Android 11 only)
  1003→- /dev/qemu_pipe / /dev/goldfish_pipe (GL transport)
  1004→- /dev/block/vdc (block device — Android 11)
  1005→- /dev/fuse (FUSE — Android 11)
  1006→- /dev/hal/power_supply%s (HAL proxy — Android 11)
  1007→- /dev/.busybox, /dev/.coldboot_done (init markers)
  1008→- 3× netlink unix-socket servers
  1009→
  1010→The split is:
  1011→- **`libvm.so`** (loaded into VM Java app process): binder virtualization (via Java Proxy of `IActivityManager`), OpenGL render server, JNI bindings
  1012→- **`libkr64.so`** (separate daemon process via `libkrloader64.so`): everything else (proc, dev, mounts, netlink, seccomp, shadowhook)
  1013→
  1014→The Java app launches `libkr64.so` as a separate process (probably via `Runtime.exec()` or `Process.start()` with `libkrloader64.so` as the interpreter), and `libkr64.so` runs in the background creating the virtual device tree. The Java app's `libvm.so` then connects to these devices.

  1018→## 17. Conclusion
  1019→
  1020→`libkr64.so` is **not a JNI library** — it is a standalone ELF executable disguised as a shared object, launched by the Android kernel via the custom `libkrloader64.so` interpreter. It runs as a separate process and acts as the "kernel replacement" for the guest Android VM:
  1021→
  1022→1. It creates the virtual device tree under `/data/data/com.clone.android.dual.space/vm/vm%d/dev/` via `mknodat` (for char/block devices like `/dev/gb`, `/dev/input/touch`, `/dev/qemu_pipe`) and via `bind` (for unix-socket servers like `netlink_server`, `netlink_client/nl_dhcp_*`, `netlink_client/netdevice_*`).
  1023→
  1024→2. It embeds **shadowhook v1.0.8** to inline-hook the dynamic linker's `do_dlopen` function, redirecting guest `dlopen` calls to its own loader.
  1025→
  1026→3. It embeds **LZMA/XZ + zlib** decompressors (to decompress embedded configuration data at runtime).
  1027→
  1028→4. It installs a **seccomp filter** on the guest with a SIGSYS handler that emulates "blocked" syscalls.
  1029→
  1030→5. It manages a per-VM **mount namespace** (`vm.mount.ns`) with bind mounts, tmpfs, and propagation control.
  1031→
  1032→6. It emulates **`/proc`** by intercepting `open("/proc/...")` and synthesizing per-VM content (`/proc/maps_%d_%d`, `/proc/exe_%d`, `/proc/status_%d_%d`, `/proc/mounts_%d_%d`, etc.).
  1033→
  1034→7. It calls `fork` once (to spawn the guest `app_process64`) and uses `socketpair` for parent↔child IPC.
  1035→
  1036→8. The Android 11 variant (`libkr64.11.so`) is 35% larger and adds `/dev/gb`, `/dev/gb2` (graphics buffer devices), SOCKS5 proxy support, APEX support, modern mount paths, kernel-hardening sysctls, and Samsung GameSDK hooks (`libGamesAware.so`, `libVSR.so`, `libGLESv2_samsung.so`).
  1037→
  1038→9. `libkrloader64.so` is the custom ELF interpreter built from AOSP source (product `marlin` / Pixel XL), embedding a static bionic libc. It only exports `_start` and imports 4 libc functions.
  1039→
  1040→10. **Binder virtualization is NOT in libkr64.so** — it's in `libvm.so` (the JNI library), which creates `/vm%d/dev/binder` and proxies binder calls via a Java `Proxy`.
  1041→
  1042→twoyi does not have any of this infrastructure. To match Virtual Master's level of isolation and multi-VM support, twoyi would need to implement a similar "kernel replacement" daemon — a significant native-side engineering effort.
  1043→
