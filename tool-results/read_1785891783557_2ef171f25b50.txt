    11→    11→## 0. Executive summary (read this first)
    12→    12→
    13→    13→Virtual Master proves that **a Treble GSI can be booted in an unprivileged Android app process**, without KVM and without root, by replacing the kernel's role with a userspace daemon (`libkr64.so`) plus an in-process binder proxy (`libvm.so` + `BinderService.java`). Twoyi already does about 30 % of this work — it has the in-process loader, the open-source `libOpenglRender.so`, an input subsystem, and a socket IPC. What it is missing is:
    14→    14→
    15→    15→1. A **kernel-replacement daemon** that materialises a virtual `/dev` tree (binder, qemu_pipe, gb, gb2, vmproc, ashmem, __properties__, etc.).
    16→    16→2. **Binder virtualisation** — a per-VM `/vm%d/dev/binder` plus a Java-side `IActivityManager` proxy that re-routes the guest's `servicemanager` lookups back into the host app.
    17→    17→3. A **seccomp filter with a SIGSYS emulation handler** (this is what makes "blocked" syscalls become no-ops or fake-success instead of killing the guest).
    18→    18→4. A **`/proc` emulator** that synthesises `/proc/self/maps`, `/proc/self/status`, `/proc/cmdline`, `/proc/version`, `/proc/mounts`, … per VM.
    19→    19→5. A **GSI ROM extractor** that knows how to unpack `system.img`, `vendor.img`, `product.img`, `system_ext.img`, `boot.img`-derived ramdisk into the `<vmDataDir>/fs/` tree (not just unzip a flat folder like today).
    20→    20→6. **Init configuration** — patch the guest's `init.rc` / `init.{vendor,product}.rc` so it talks to the virtual devices instead of real hardware HALs.
    21→    21→
    22→    22→For **x86_64**, all of the above still applies, but additionally:
    23→    23→- The guest GSI must be an **x86_64** GSI (`system-x86_64.img`, `product-x86_64.img`, …) — an ARM GSI will not run natively on x86_64 (and twoyi's container model is *not* an emulator — it shares the host kernel).
    24→    24→- `libOpenglRender_aosp_x86_64.so` is already built and present at `/home/z/my-project/app/src/main/jniLibs/x86_64/libOpenglRender_aosp.so` (597 KB, all 6 twoyi ABI symbols exported, see `AOSP_BUILD_RESULTS.md`).
    25→    25→- If KVM is available (codespace `twoyi-dev-3-jr47xg6xvx7ghq6p` has working KVM per `TWOYI_HONEST_STATUS.md`), we *could* alternatively boot the GSI in a true VM via crosvm/QEMU. That is **out of scope** for the container path; it is listed in §6 as a future option.
    26→    26→
    27→    27→The plan below targets the **container path** (no KVM, shares the host kernel) because that is the architectural direction twoyi is already on and is what `libkr64.so` does. The KVM path is a separate project.

    31→    31→## 1. What is a GSI?
    32→    32→
    33→    33→### 1.1 Definition
    34→    34→
    35→    35→A **GSI (Generic System Image)** is an Android `system.img` that conforms to the Treble HAL interface contract. It was introduced in Android 8.0 (Project Treble) so that the **system** partition can be updated independently of the **vendor** partition. The same GSI boots on any device whose `vendor` partition implements the matching VINTF manifest.
    36→    36→
    37→    37→* Source: https://source.android.com/docs/core/architecture/halse
    38→    38→* Source: https://source.android.com/docs/core/ota/gsi
    39→    39→
    40→    40→### 1.2 Differences from a pre-Treble `system.img`
    41→    41→
    42→    42→| Aspect | Pre-Treble (≤ Android 7.1) | Treble GSI (≥ Android 8.0) |
    43→    43→|---|---|---|
    44→    44→| `system.img` contents | All framework + most HALs jammed together | Framework + generic HALs only; vendor-specific HALs live in `vendor.img` |
    45→    45→| `vendor.img` | Optional, often empty | Required, contains all SoC-specific HALs |
    46→    46→| HAL interface discovery | Hard-coded class lookups | **VINTF manifest** at `/vendor/etc/vintf/manifest/*.xml` (XML manifest of HALs and versions) |
    47→    47→| `product.img` | Did not exist | Optional (Treble) / required (Android 10+) — contains product-specific apps/overlays |
    48→    48→| `system_ext.img` | Did not exist | Required (Android 10+) — system extensions that are product-agnostic but vendor-specific |
    49→    49→| `odm.img` | Did not exist | Optional — original-design-manufacturer partition |
    50→    50→| Boot flow | `boot` → mount `system` → `init` reads `/system/**/init.rc` | `boot` → mount `system` + `vendor` + `product` + `system_ext` → `init` reads `/system/etc/init/hw/init.rc` AND `/vendor/etc/init/*.rc` |
    51→    51→| Binder namespace | Single binder driver `/dev/binder` | Three binder contexts: `/dev/binder` (framework), `/dev/hwbinder` (hwbinder HALs), `/dev/vndbinder` (vendor binder) |
    52→    52→| APEX | Did not exist | Required (Android 10+) — `/system/apex/com.android.*` are mountable mini-images |
    53→    53→| Properties | `/system/build.prop` + `/vendor/build.prop` | Adds `/system/product/build.prop`, `/system/system_ext/build.prop`, `/vendor/etc/prop/default.prop` |
    54→    54→
    55→    55→### 1.3 Minimum requirements to boot one
    56→    56→
    57→    57→To boot a Treble GSI (in any environment — bare metal, VM, or container) you must provide:
    58→    58→
    59→    59→1. **Kernel** — must match the GSI's kernel ABI. For Android 11 GSIs that is typically Linux 4.14+ with selinux, binder, ashmem, and the Android-specific ioctl extensions enabled. In a container, you reuse the host kernel.
    60→    60→2. **`/dev/binder`** — the binder driver. Treble additionally requires `/dev/hwbinder` and `/dev/vndbinder`. In a container you must either proxy these (VM's approach: per-VM `/vm%d/dev/binder`) or share the host's.
    61→    61→3. **`/dev/ashmem`** (Android ≤ 10) or **`/dev/dm-user`** + memfd (Android 11+) — shared memory for SurfaceFlinger and binder transactions.
    62→    62→4. **`/dev/__properties__`** — the property area file (mmap'd read-only by every process). The `init` process writes here; everyone else reads.
    63→    63→5. **`init`** binary at `/system/bin/init` — parses `/system/etc/init/hw/init.rc` and starts `servicemanager`, `surfaceflinger`, `zygote`, etc.
    64→    64→6. **`servicemanager`** at `/system/bin/servicemanager` — registers framework services in the binder namespace.
    65→    65→7. **`surfaceflinger`** + a gralloc HAL — without a gralloc that produces buffers SurfaceFlinger can publish, you get no display.
    66→    66→8. **HALs declared in `/vendor/etc/vintf/manifest/*.xml`** — every HAL listed must be either implemented or stubbed. A missing HAL causes `init` to fail to start its dependent services.
    67→    67→9. **Mount points** — `/system`, `/vendor`, `/product`, `/system_ext`, `/apex/*`, `/data`, `/cache`, `/dev`, `/proc`, `/sys`.
    68→    68→10. **`/proc` and `/sys`** — Android expects these to look like real Linux procfs/sysfs (e.g. `/proc/cmdline`, `/proc/mounts`, `/proc/self/maps`, `/sys/class/net/*`).
    69→    69→
    70→    70→### 1.4 What the GSI doesn't include (and you must supply)
    71→    71→
    72→    72→A GSI ships **only** `system.img`, `product.img`, `system_ext.img` (and sometimes a `boot.img` containing the kernel + ramdisk). It does **not** ship:
    73→    73→
    74→    74→- `vendor.img` — must come from the device (or in our case, be a synthetic stub)
    75→    75→- `boot.img` kernel — must be the host kernel
    76→    76→- `/data` partition — must be created empty by the boot environment
    77→    77→- `/cache` — same
    78→    78→
    79→    79→For twoyi's container path, we will:
    80→    80→- Use the host kernel.
    81→    81→- Use a synthetic `vendor.img` with stub HALs (a pre-built one is fine — see §5.7).
    82→    82→- Use the host's `/dev/binder` for *some* services and per-VM proxy binder for *others* (see §3.2 for the split).

    86→    86→## 2. How Virtual Master boots GSIs (from our analysis)
    87→    87→
    88→    88→This section summarises what the three prior analysis reports (`VM_JAVA_ANALYSIS.md`, `VM_KR64_ANALYSIS.md`, `VM_ROM_ANALYSIS.md`) established about VM's GSI boot. Every fact below is traceable to one of those reports.
    89→    89→
    90→    90→### 2.1 The startup pipeline (Java side)
    91→    91→
    92→    92→From `VM_JAVA_ANALYSIS.md` §2.3 and §6, the boot sequence is driven by an explicit state machine in `com.android.vmcore.VMInstance.f8940WWoWWo` with 11 states (`-5..7`):
    93→    93→
    94→    94→```
    95→    95→state 0 (STOPPED) → 1 (CHECKING_ENV)
    96→    96→  ├─ CPU/SDK/data-dir checks
    97→    97→  └─ clearZombieProcess loop
    98→    98→state 1 → 2 (INSTALLING)  [only if ROM changed or first boot]
    99→    99→  Setup pipeline (sequential, each task returns bool):
   100→   100→    PrepareFsTask  → chmod the fs dir
   101→   101→    InstallFsTask  → download + decrypt + extract rom.zip (see §2.2)
   102→   102→    FixFsTask      → fix fs paths/symlinks (ROM-version specific)
   103→   103→    CleanFsTask    → remove stale cache
   104→   104→    ChmodFsTask    → NativeHelper.chmodRecursively(fsDir, 0xA1FF)
   105→   105→    CleanCacheTask → clear caches
   106→   106→    FixCPUArchTask → rewrite /system/bin/app_process{32,64}_xposed shims
   107→   107→    LoadVMPropTask → parse /system/build.prop into VMConfig.f8870 HashMap
   108→   108→state 2 → 3 (STARTING_SVC)
   109→   109→  Start HAL services:
   110→   110→    BinderService  → reflect IActivityManager, install Java Proxy, call
   111→   111→                     native setupBinder(vmId, binderVer, 1, 2,
   112→   112→                       "com.android.vmcore.service.IBinderService",
   113→   113→                       parcelledIntent)
   114→   114→                     → creates /vm%d/dev/binder in libvm.so
   115→   115→                     → bindService(BinderService.class) — wait up to 5 s
   116→   116→    InputService   → nativeStartService   (creates /dev/input/touch)
   117→   117→    AudioService   → start                 (creates /dev/audio)
   118→   118→    HALManager     → nativeStartHALMgr     (creates camera/sensor/etc. dev nodes)
   119→   119→    DisplayService → nativeStartService    (opens /dev/qemu_pipe)
   120→   120→    NetlinkManager → start                 (creates /dev/netlink_client/*)
   121→   121→    VMEventManager → new Thread() { LocalServerSocket("<vmDataDir>/dev/event"); accept loop }
   122→   122→state 3 → 4 (BOOTING)
   123→   123→  Startup pipeline (sequential):
   124→   124→    ApplyOverlaysTask  → copy /system/product overlay files
   125→   125→    Bug1..Bug8FixTask  → ROM-version-specific patches
   126→   126→    CleanLogTask       → clear logs
   127→   127→    SuperuserTask      → extract superuser.zip
   128→   128→    XposedTask         → extract xposed.zip
   129→   129→    GooglePlayTask     → extract play.zip (GApps)
   130→   130→    MagiskTask         → extract magisk.zip, patch init.rc
   131→   131→    BuildTmpfsTask     → mount tmpfs on /tmp, /dev, etc. (via native)
   132→   132→    BuildVMPropTask    → write /system/build.prop (PIE/build fingerprint/Build.ID)
   133→   133→    BuildExecPathTask  → set PATH and exec dirs
   134→   134→state 4 → 5 (OS_BOOTING)
   135→   135→  int pid = startOS(vmId, dpi, kernelPath);   // JNI → libvm.so
   136→   136→    kernelPath = dataDir + "/lib64"
   137→   137→    libvm.so forks a child process, chroots into <vmDataDir>/fs,
   138→   138→    LD_PRELOADs libkr64.so as a "kernel replacement", and exec's
   139→   139→    /system/bin/init from the guest ROM.
   140→   140→state 5 → 6 (OS_READY_1)
   141→   141→  Guest eventually calls back through the /dev/event socket with:
   142→   142→    "com.android.vmcore.action.BOOT_COMPLETED`<payload>"
   143→   143→  → VMInstance.mo5013WWWWWWWW(...) sets state = 6.
   144→   144→state 6 → 7 (OS_READY_2)
   145→   145→  Guest signals SHUTDOWN on /dev/event → state = 7.
   146→   146→```
   147→   147→
   148→   148→### 2.2 ROM extraction
   149→   149→
   150→   150→From `VM_ROM_ANALYSIS.md` §4 and `VM_JAVA_ANALYSIS.md` §4.3, the ROM is downloaded as `rom.zip` (one file per `rom_uri` mirror, parallel download, on-the-fly AES-128-ECB decryption with key `%z89aviCM0KkbEs9`, then extracted via ZIP or 7-Zip into `<vmDataDir>/fs/`). After extraction, the dex code references these specific Treble paths that we now know exist inside `rom.zip`:
   151→   151→
   152→   152→```
   153→   153→/system/build.prop
   154→   154→/system/etc/prop.default
   155→   155→/system/etc/init/hw/init.rc
   156→   156→/system/product/build.prop           ← Treble product partition
   157→   157→/system/system_ext/build.prop        ← Android 10+ system_ext partition
   158→   158→/vendor/build.prop
   159→   159→/vendor/etc/vintf/manifest/vibrator-default.xml      ← VINTF HAL manifest
   160→   160→/vendor/etc/init/vibrator-default.rc                  ← vendor init .rc
   161→   161→/vendor/bin/hw/android.hardware.vibrator-service.example   ← vendor HAL binary
   162→   162→```
   163→   163→
   164→   164→The presence of these paths in the *runtime* dex confirms the newer ROMs (9.0, 11.0) are real Treble GSIs (with the partitions flattened into the extracted directory tree — i.e. `/system/product/...` rather than a separate `product.img` mount).
   165→   165→
   166→   166→### 2.3 How `libkr64.11.so` sets up the environment
   167→   167→
   168→   168→From `VM_KR64_ANALYSIS.md`:
   169→   169→
   170→   170→- `libkr64.11.so` is **not a JNI library**. It is a standalone ELF executable disguised as a `.so`, with `.interp = libkrloader64.so` (a custom dynamic linker built from AOSP source for product `marlin`/Pixel XL, embedding a static bionic libc).
   171→   171→- Launched by the kernel via `fork`+`exec`. Entry point `0x4e04` (A 7) / `0x5594` (A 11) → `_start` → `__libc_init` → 24 `.init_array` constructors → `main()` at `0x7244` (A 7).
   172→   172→- `main()` parses `argv` (expects 7 args: `vmid`, `data_dir`, `rom_dir`, `kernel_path`, `config_path`, `log_level`, `socket_fd` — best inference from `VM_KR64_ANALYSIS.md` §2 and Action 2).
   173→   173→- Builds a config struct (80 bytes), calls `0x115a90()` to get a handle, then dispatches.
   174→   174→- `libkr64.11.so` is 2.03 MB (35 % larger than A 7's 1.50 MB) and links against **`libbinder.so` + `libutils.so`** (but doesn't actually use any binder symbols — the deps are loaded only so libkr64.11.so can hook or dlsym them).
   175→   175→- Has 213 undefined symbols (vs. 187 in A 7) and uses 100 direct `syscall()` calls to bypass its own shadowhook hooks.
   176→   176→

   214→   214→
   215→   215→### 2.5 Binder virtualisation
   216→   216→
   217→   217→From `VM_JAVA_ANALYSIS.md` §5.2 and `VM_KR64_ANALYSIS.md` §16:
   218→   218→
   219→   219→The split is:
   220→   220→- **`libvm.so`** (loaded into VM Java app process): binder virtualisation via a Java `Proxy` of `android.app.IActivityManager`, OpenGL render server, JNI bindings.
   221→   221→- **`libkr64.so`** (separate daemon process via `libkrloader64.so`): everything else (proc, dev, mounts, netlink, seccomp, shadowhook).
   222→   222→
   223→   223→The Java-side setup (`com.android.vmcore.service.BinderService.m5206WWWWoWWWWo`) does:
   224→   224→
   225→   225→1. **Reflect into `ActivityManager`** to obtain the system `IBinder` for `android.app.IActivityManager` (hidden-API access enabled by FreeReflection's `exemptAll()` in `VMApp.attachBaseContext`).
   226→   226→2. **Wrap that IBinder with a `java.lang.reflect.Proxy`** whose `transact()` invocation captures the calling thread ID and the return code into `iArr[0]`.
   227→   227→3. **Reinstall the proxy** via reflection on `ActivityManager.IActivityTaskManager` (replacing the system's `IActivityTaskManager` field with the proxied one).
   228→   228→4. **Trigger the proxy** by calling `peekService(vMApp, new Intent())`. The captured integer is the system's binder version.
   229→   229→5. **Call native `setupBinder(vmId, binderVersion, 1, 2, "com.android.vmcore.service.IBinderService", parcelledIntent)`**. This is the JNI into `libvm.so` that:
   230→   230→   - Creates the per-VM `/vm%d/dev/binder` device.
   231→   231→   - Sets up a binder-redirect mapping so the guest's `servicemanager` calls for `activity`/`package`/`window`/etc. are proxied back to the host's `BinderService.f9244WWWWoWWWWo` (the `IBinderService.Stub` instance).
   232→   232→   - The host then fulfills those calls (or passes them through to the real system service with the host's identity).
   233→   233→6. **`bindService(Intent(BinderService.class), …, BIND_AUTO_CREATE)`** — wait up to 5 s for `onServiceConnected`.
   234→   234→
   235→   235→So the guest's `Context.startActivity()` ends up calling host `VMDisplayActivity.onDialNumberEvent()`, etc. The guest's `PackageManager` queries are routed to a per-VM package list maintained by the host.
   236→   236→
   237→   237→### 2.6 APEX support
   238→   238→
   239→   239→From `VM_KR64_ANALYSIS.md` §14:
   240→   240→
   241→   241→`libkr64.11.so` references these APEX paths (decoded from XOR-obfuscated `.data`):
   242→   242→- `/system/apex/com.android.vndk.current` — VNDK APEX (Android 10+)
   243→   243→- `/system/apex/com.android.art.release` — ART runtime APEX
   244→   244→
   245→   245→An APEX file is a ZIP with an `apex_payload.img` (ext4 or sparse-ext4) inside. The guest's `init` mounts each APEX via the `apexd` daemon, which loops-mounts `apex_payload.img` onto `/apex/com.android.<name>/`. The libkr64 daemon supports this because:
   246→   246→1. It runs as a separate process with `loop` mount permissions (or it emulates loop mounts via bind mounts).
   247→   247→2. It can hook `mount()` (via shadowhook) so when `apexd` calls `mount("/dev/block/loopN", "/apex/…", "ext4", …)`, libkr64 redirects it to a bind mount of the pre-extracted APEX directory.
   248→   248→
   249→   249→For a minimal viable GSI boot we can **skip APEX** by pre-extracting all APEXes into the `fs/system/apex/<name>/` directory and patching `apexd`'s init.rc to be a no-op. This is what `Bug8FixTask` (in `com.android.vmcore.startup.Bug8FixTask`) likely does — see §2.7 below.
   250→   250→
   251→   251→### 2.7 Seccomp filter
   252→   252→
   253→   253→From `VM_KR64_ANALYSIS.md` §12 and §11:
   254→   254→
   255→   255→`libkr64.so` installs a **seccomp filter** on the guest process. Strings decoded from `.data`:
   256→   256→- `INIT.SECCOMP` (key 0xb4)
   257→   257→- `init_seccomp` (key 0x67, A 11 only)
   258→   258→- `__NR_rt_sigaction SIGSYS` (key 0x1a, A 11 only)
   259→   259→- `BLOCKED.SYSCALL.FAILED` (key 0xc9)
   260→   260→- `blocked syscall failed %d` (key 0xc2 / 0xe2)
   261→   261→
   262→   262→Mechanism:
   263→   263→1. `libkr64.so` calls `prctl(PR_SET_NO_NEW_PRIVS, 1)` (4 paired `prctl` calls at `0x111e28`/`0x112694`/`0x11270c`/`0x112f78`).
   264→   264→2. `libkr64.so` installs a SIGSYS handler via `sigaction(SIGSYS, …)` (the `__NR_rt_sigaction SIGSYS` string is the giveaway).
   265→   265→3. `libkr64.so` installs a `SECCOMP_SET_MODE_FILTER` (syscall 277 on aarch64) BPF program via the `syscall()` wrapper.
   266→   266→4. The BPF program traps forbidden syscalls (the ones that would let the guest escape its sandbox — e.g. `mount` without our hook, `chroot`, `pivot_root`, `reboot`, raw `swapon`/`swapoff`, `acct`, etc.).
   267→   267→5. When a forbidden syscall is hit, the kernel delivers SIGSYS to the guest.
   268→   268→6. The SIGSYS handler logs `BLOCKED.SYSCALL.FAILED: <syscall_nr>` and either:
   269→   269→   - **Emulates** the syscall (returns 0 or a fake-success value), OR
   270→   270→   - **Kills** the guest (via `_exit`).
   271→   271→
   272→   272→This is the core of VM's "kernel replacement" pattern: the seccomp filter turns syscalls into traps that the userspace daemon can intercept and synthesise, mimicking the kernel's behaviour for a controlled subset of syscalls.
   273→   273→
   274→   274→### 2.8 `/proc` emulation
   275→   275→
   276→   276→From `VM_KR64_ANALYSIS.md` §4.2 and §16:
   277→   277→
   278→   278→`libkr64.so` emulates `/proc` by intercepting `open("/proc/…")` calls (via shadowhook on `open`/`openat`). When the path matches one of these patterns, libkr64 synthesises the content:
   279→   279→
   280→   280→| Decoded path | Synthesised content |
   281→   281→|---|---|
   282→   282→| `/proc/self/exe` | Resolves to the guest's `/system/bin/init` (not the host's `app_process64`) |
   283→   283→| `/proc/self/maps` | Per-VM map (filtered to show only guest mappings, not host's) — uses `/proc/maps_%d_%d` template (vmid, pid) |
   284→   284→| `/proc/self/status` | Per-VM status — template `/proc/status_%d_%d` |
   285→   285→| `/proc/self/mounts` | Per-VM mounts (only guest mounts, not host's) — template `/proc/mounts_%d_%d` |
   286→   286→| `/proc/self/fd/%d` | Resolves to the per-VM view of FDs |
   287→   287→| `/proc/cmdline` | Synthesised as `androidboot.hardware=… androidboot.bootdevice=…` (matches the GSI's expected cmdline) |
   288→   288→| `/proc/version` | Synthesised as `Linux version 4.14.x …` (matches the GSI's expected kernel version) |
   289→   289→| `/proc/mounts` | Alias for `/proc/self/mounts` |
   290→   290→| `/proc/net/if_inet6/` | Synthesised based on `NetlinkManager`'s virtual interfaces |
   291→   291→| `/proc/sys/kernel/kptr_restrict` | Returns `1` (A 11 hardening) |
   292→   292→| `/proc/sys/vm/mmap_rnd_bits` | Returns `16` (A 11 hardening) |
   293→   293→| `/proc/%d/%s` | Per-VM view of any process's `/proc/<pid>/<file>` |
   294→   294→| `/proc/exe_%d` | Per-VM `exe` symlink for PID `<d>` |
   295→   295→| `/proc/mnt_points` | Per-VM mount point list |
   296→   296→
   297→   297→The `/dev/vmproc` device (created via `mknodat` at `0x11d770`, decoded with keys 0x47/0x64/0x07) is the entry point — `open("/proc/…")` is redirected to `open("/dev/vmproc")` + an ioctl that selects which virtual file to read.
   298→   298→
   299→   299→### 2.9 Init configuration patches
   300→   300→
   301→   301→From `VM_JAVA_ANALYSIS.md` §2.3 (startup pipeline) and `VM_ROM_ANALYSIS.md` §4.3:
   302→   302→
   303→   303→Eight `BugNFixTask` classes (`com.android.vmcore.startup.Bug1FixTask` … `Bug8FixTask`) apply ROM-version-specific patches to the extracted filesystem before boot. The pipeline (state 4) is:
   304→   304→
   305→   305→```
   306→   306→ApplyOverlaysTask → Bug1FixTask → … → Bug8FixTask → CleanLogTask →
   307→   307→SuperuserTask → XposedTask → GooglePlayTask → MagiskTask →
   308→   308→BuildTmpfsTask → BuildVMPropTask → BuildExecPathTask
   309→   309→```
   310→   310→
   311→   311→Notable patches inferred from path constants decoded in `VM_ROM_ANALYSIS.md` §4:
   312→   312→- **`app_process32`/`app_process64` shims** — rewrite the symlinks at `/system/bin/app_process32`, `/system/bin/app_process32_xposed`, `/system/bin/app_process64`, `/system/bin/app_process64_xposed` so they point at the host's `app_process` binary (avoiding the need to ship a full ART runtime).
   313→   313→- **`libui.so` ABI selection** — replace `/system/lib/libui.so` with `libui10.so` (Android 10 variant), `libui51.so` (Android 5.1), or `libhostlibui.so`/`libhostlibui_10.so` (the host-aware shim) depending on ROM version.
   314→   314→- **`build.prop` patching** — `BuildVMPropTask` writes `/system/build.prop` with the host's actual build fingerprint, `Build.ID`, and a synthetic kernel version. This makes `Build.FINGERPRINT` inside the guest match the host (required by SafetyNet / Play Integrity basic attestation).
   315→   315→- **`init.rc` patching** — `MagiskTask` injects magisk service entries into `/system/etc/init/hw/init.rc`. The same mechanism is presumably used to inject the `libkr64.so` LD_PRELOAD.
   316→   316→- **`PATH` and exec dirs** — `BuildExecPathTask` sets the guest's `PATH` to include `/system/bin:/system/xbin:/system/sbin:/vendor/bin:/system/apex/com.android.runtime/bin`.

   361→   361→### 3.2 Binder virtualisation (the hard one)
   362→   362→
   363→   363→**What VM does.** `libvm.so` (in the Java app process) creates `/vm%d/dev/binder` via the `setupBinder()` JNI, and the Java `BinderService` wraps the host's `IActivityManager` with a `java.lang.reflect.Proxy` so the guest's `servicemanager` lookups are proxied back into the host app (see §2.5).
   364→   364→
   365→   365→**What twoyi currently does.** Uses the host's `/dev/binder` directly. The guest's `servicemanager` registers with the host's `servicemanager`. This means the guest's `getSystemService(ACTIVITY_SERVICE)` returns the *host's* ActivityManager — the guest can launch host apps but not its own. This is why twoyi can't have its own package manager.
   366→   366→
   367→   367→**What to build.** Two pieces:
   368→   368→
   369→   369→**(a) Native binder proxy in Rust** — `app/rs/kr64/src/binder_proxy.rs`:
   370→   370→- Open `/dev/binder` on the host side.
   371→   371→- Create `/vm%d/dev/binder` as a char device via `mknodat(S_IFCHR, …)`.
   372→   372→- Accept `BINDER_WRITE_READ` / `BINDER_VERSION` / `BINDER_SET_MAX_THREADS` ioctls from the guest.
   373→   373→- Parse the binder transaction header.
   374→   374→- For transactions targeting `android.app.IActivityManager` / `android.app.IActivityTaskManager` / `android.content.pm.IPackageManager` / `android.view.IWindowManager` — route them to the Java side via the event socket.
   375→   375→- For transactions targeting `android.os.IServiceManager` — synthesise responses (return a fake service handle for each well-known service name).
   376→   376→- For all other transactions — proxy directly to the host binder.
   377→   377→
   378→   378→**(b) Java-side binder service** — `app/src/main/java/io/twoyi/service/BinderService.java`:
   379→   379→- Copy VM's `BinderService.m5206WWWWoWWWWo` structure (see §2.5).
   380→   380→- Reflect into `ActivityManager` to get the system `IActivityManager` IBinder.
   381→   381→- Wrap with a `Proxy`.
   382→   382→- Add a `setupBinder()` JNI that calls into `libkr64.so`.
   383→   383→- Implement `IBinderService.Stub` with the AIDL interface `io.twoyi.service.IBinderService`.
   384→   384→
   385→   385→**Files to create.**
   386→   386→- `app/src/main/java/io/twoyi/service/BinderService.java`
   387→   387→- `app/src/main/java/io/twoyi/service/IBinderService.aidl` — AIDL stub (interface descriptor `"io.twoyi.service.IBinderService"`).
   388→   388→- `app/src/main/java/io/twoyi/FreeReflection.java` — copy the FreeReflection trick (or use ` Reflection_exemptAll` from `me.weishu.reflection.BootstrapClass` — bundle the dex).

   402→   402→### 3.3 Graphics buffer management (`/dev/gb` and `/dev/gb2`)
   403→   403→
   404→   404→**What VM does.** `libkr64.11.so` (A 11 only) creates `/dev/gb` and `/dev/gb2` as char devices (via `mknodat S_IFCHR` at `0x11d770`, decoded with keys 0xe0 and 0x0c). These expose a `gralloc`-like ioctl interface for allocating graphics buffers. The guest's `surfaceflinger` calls these ioctls to allocate buffers for compositing; the host returns a buffer handle that maps to either an ashmem region or a host `AHardwareBuffer`.
   405→   405→
   406→   406→The presence of two devices (`gb` + `gb2`) suggests:
   407→   407→- `/dev/gb` is the **framework gralloc** (used by surfaceflinger, accessed via `/dev/binder`).
   408→   408→- `/dev/gb2` is the **vendor gralloc** (used by HALs, accessed via `/dev/vndbinder`).
   409→   409→
   410→   410→This split matches Android 11's gralloc HAL layout where `android.hardware.graphics.allocator@4.0` (framework) and `android.hardware.graphics.allocator-V1-ndk` (vendor) are separate services.
   411→   411→
   412→   412→**What twoyi currently does.** No gralloc emulation. The `libOpenglRender_aosp.so` (the rebuilt AOSP emugl renderer at `/home/z/my-project/app/src/main/jniLibs/x86_64/libOpenglRender_aosp.so`) implements its own buffer management via the `ColorBuffer` class in `app/rs/openglrenderer/src/gralloc.rs`. The guest's SurfaceFlinger has no gralloc HAL, so it crashes on the first composite.
   413→   413→
   414→   414→**What to build.** `app/rs/kr64/src/gb.rs`:
   415→   415→- Create `/dev/gb` and `/dev/gb2` as char devices.
   416→   416→- Implement these ioctls (the exact numbers can be inferred from `android.hardware.graphics.allocator@4.0` HAL header in AOSP `hardware/interfaces/graphics/allocator/4.0/IAllocator.hal`):
   417→   417→  - `ALLOCATE` — allocate a buffer of given width/height/format/usage. Return a buffer handle that's a host `AHardwareBuffer` (we already have these via `libEGL.so`).
   418→   418→  - `DUMP_DEBUG_INFO` — return a fake debug string.
   419→   419→  - `GET_ALL_ALLOCATOR_FUNCTIONS` — return function pointers for the gralloc module.
   420→   420→
   421→   421→For the MVP, we can route gralloc allocation through the existing `libOpenglRender_aosp.so` ColorBuffer infrastructure — each guest gralloc allocation creates a host-side `ColorBuffer` and returns its ID as the buffer handle.
   422→   422→
   423→   423→**Files to create.**
   424→   424→- `app/rs/kr64/src/gb.rs` — char device + ioctls.
   425→   425→- `app/rs/openglrenderer/src/gralloc.rs` — already has `ColorBuffer`; add a `from_guest_handle(u64) -> ColorBuffer` lookup.
   426→   426→
   427→   427→**Files to modify.**
   428→   428→- `app/rs/kr64/src/devices.rs` — register `/dev/gb` and `/dev/gb2`.
   429→   429→
   430→   430→**Acceptance criteria.**

   434→   434→### 3.4 Seccomp filter
   435→   435→
   436→   436→**What VM does.** Installs a `SECCOMP_SET_MODE_FILTER` BPF program with a SIGSYS handler that emulates blocked syscalls (see §2.7).
   437→   437→
   438→   438→**What twoyi currently does.** No seccomp. The guest can call any syscall the host kernel allows. This is unsafe and also means the guest sees the host's `/proc`, `/sys`, etc. (no isolation).
   439→   439→
   440→   440→**What to build.** `app/rs/kr64/src/seccomp.rs`:
   441→   441→
   442→   442→1. **Allowlist of syscalls** — start from Android's own seccomp policy (in AOSP at `system/seccomp/policy.txt`). For twoyi we need to also allow the syscalls that `libkr64.so` intercepts (so they trap to our SIGSYS handler).
   443→   443→
   444→   444→2. **Blocklist (trap-to-SIGSYS)** — these syscalls are blocked and emulated:
   445→   445→   - `open`/`openat` for `/proc/…`, `/sys/…`, `/dev/…` paths (intercepted by the proc emulator)
   446→   446→   - `mount`/`umount`/`umount2` (intercepted by the mount_mgr)
   447→   447→   - `pivot_root`/`chroot` (intercepted to redirect to the per-VM rootfs)
   448→   448→   - `reboot` (intercepted to send a shutdown event)
   449→   449→   - `swapon`/`swapoff` (intercepted to be no-ops)
   450→   450→   - `acct` (intercepted to be a no-op)
   451→   451→   - `sethostname`/`setsid` (intercepted for the per-VM hostname)
   452→   452→
   453→   453→3. **SIGSYS handler** — `sigaction(SIGSYS, …)`:
   454→   454→   - Read the syscall number from `ucontext->uc_mcontext`.
   455→   455→   - Log `BLOCKED.SYSCALL.FAILED: <nr>`.
   456→   456→   - Dispatch to the appropriate emulator function.
   457→   457→   - Set the return value in `ucontext->uc_mcontext.regs[0]`.
   458→   458→   - Increment the instruction pointer past the syscall instruction.
   459→   459→   - Return.
   460→   460→
   461→   461→**Files to create.**
   462→   462→- `app/rs/kr64/src/seccomp.rs`
   463→   463→- `app/rs/kr64/src/bpf_filter.rs` — the compiled BPF program (generate with `libseccomp` or hand-write).
   464→   464→
   465→   465→**Files to modify.**
   466→   466→- `app/rs/kr64/src/main.rs` — call `seccomp::init()` after all devices are created and before `fork`+`exec` of the guest `init`.
   467→   467→
   468→   468→**Acceptance criteria.**
   469→   469→- After boot, `adb shell cat /proc/self/status` inside the guest returns a synthesised status (not the host's).
   470→   470→- After boot, `adb shell mount` inside the guest shows only guest mounts.
   471→   471→- After boot, `adb shell reboot` inside the guest sends a shutdown event (doesn't actually reboot the host).
   472→   472→
   473→   473→### 3.5 `/proc` emulator
   474→   474→
   475→   475→**What VM does.** Intercepts `open("/proc/…")` and synthesises content (see §2.8).
   476→   476→
   477→   477→**What twoyi currently does.** Uses the host's `/proc`. The guest sees the host's process list, mounts, cmdline, version — which breaks the guest's `init` (it expects `androidboot.hardware=…` on the cmdline) and leaks host info.
   478→   478→
   479→   479→**What to build.** `app/rs/kr64/src/proc_emu.rs`:
   480→   480→

   483→   483→- When the path matches `/proc/…`, redirect to `/dev/vmproc` + an ioctl that selects the virtual file.
   484→   484→- Implement these synthesised files (per §2.8 table):
   485→   485→  - `/proc/cmdline` — `androidboot.hardware=twoyi androidboot.bootdevice=/dev/block/vdc androidboot.serialno=…`
   486→   486→  - `/proc/version` — `Linux version 4.14.x-perf-g… (build@host) …` (match what the GSI expects)
   487→   487→  - `/proc/self/maps` — filtered host maps (only show guest-mapped regions)
   488→   488→  - `/proc/self/status` — synthesised with the guest's PID/UID/GID
   489→   489→  - `/proc/self/mounts` — only guest mounts
   490→   490→  - `/proc/self/exe` — symlink to `/system/bin/init` (the guest's init, not the host's)
   491→   491→  - `/proc/net/if_inet6/` — based on `NetlinkManager`'s virtual interfaces
   492→   492→  - `/proc/sys/kernel/kptr_restrict` — `1`
   493→   493→  - `/proc/sys/vm/mmap_rnd_bits` — `16`
   494→   494→
   495→   495→**Files to create.**
   496→   496→- `app/rs/kr64/src/proc_emu.rs`
   497→   497→
   498→   498→**Files to modify.**
   499→   499→- `app/rs/kr64/src/devices.rs` — register `/dev/vmproc`.
   500→   500→- `app/rs/kr64/src/seccomp.rs` — add `open`/`openat` to the trap list (or use shadowhook instead).
   501→   501→
   502→   502→**Acceptance criteria.**
   503→   503→- After boot, `adb shell cat /proc/cmdline` inside the guest returns the synthesised cmdline.
   504→   504→- After boot, `adb shell cat /proc/version` inside the guest returns a Linux version string matching the GSI's expected kernel.

   507→   507→### 3.6 Inline hooking (shadowhook equivalent)
   508→   508→
   509→   509→**What VM does.** Embeds `shadowhook v1.0.8` (ByteDance's inline hook library) — hooks the dynamic linker's `do_dlopen` so guest `dlopen` calls can be redirected (see `VM_KR64_ANALYSIS.md` §4.1).
   510→   510→
   511→   511→**What twoyi currently does.** No hooking. The guest's `dlopen` calls go to the system linker, which loads from `/system/lib64/` (the host's system).
   512→   512→
   513→   513→**What to build.** Two options:
   514→   514→
   515→   515→**(a) Use shadowhook directly** — there's a Rust binding `shadowhook-sys` (https://crates.io/crates/shadowhook-sys). Add it to `app/rs/kr64/Cargo.toml`. Hook:
   516→   516→- `do_dlopen` in the linker (so guest `dlopen` loads from the per-VM rootfs).
   517→   517→- `open`/`openat` in libc (for `/proc` emulation).
   518→   518→- `mount`/`umount` (for the mount_mgr).
   519→   519→- `__system_property_get` (for property emulation).
   520→   520→
   521→   521→**(b) Use LD_PRELOAD** — simpler, less invasive. Set `LD_PRELOAD=libkr64.so` when exec'ing the guest. Override the libc functions in `libkr64.so` itself. This is what VM probably does for some hooks (shadowhook is for hooks they can't override via LD_PRELOAD because the function is already loaded).
   522→   522→
   523→   523→Recommend (b) for the MVP — it's simpler and works for all the hooks we need.
   524→   524→
   525→   525→**Files to create.**
   526→   526→- `app/rs/kr64/src/hooks.rs` — LD_PRELOAD overrides for `open`, `openat`, `mount`, `umount`, `__system_property_get`, `dlopen`.
   527→   527→
   528→   528→**Files to modify.**
   529→   529→- `app/rs/kr64/src/main.rs` — set `LD_PRELOAD=libkr64.so` in the env before `execve("./init")`.
   530→   530→
   531→   531→**Acceptance criteria.**
   532→   532→- After boot, `adb shell ls /system/lib64/` inside the guest shows the guest's libraries (not the host's).
   533→   533→- After boot, `adb shell getprop ro.build.fingerprint` returns the guest's fingerprint.
   534→   534→
   535→   535→### 3.7 ROM extraction (GSI-aware)
   536→   536→
   537→   537→**What VM does.** Downloads `rom.zip` (a ZIP), decrypts with AES-128-ECB, extracts via ZIP or 7-Zip into `<vmDataDir>/fs/` (see §2.2). The extracted tree is already flattened (e.g. `/system/product/...` is a directory inside `/system/`, not a separate mount).
   538→   538→
   539→   539→**What twoyi currently does.** `RomManager.java` extracts a pre-built `rootfs.7z` (Android 8.1 only) into `/data/data/io.twoyi/rootfs/`. The format is a flat directory tree, not a multi-partition GSI.
   540→   540→
   541→   541→**What to build.** `app/src/main/java/io/twoyi/utils/GsiExtractor.java`:
   542→   542→
   543→   543→1. **Input**: a GSI `system.img` (ext4 or sparse-ext4) + optionally `product.img`, `system_ext.img`, `boot.img` (for the ramdisk).
   544→   544→2. **Extract `system.img`**:
   545→   545→   - If sparse: `simg2img system.img system.raw.img` (use the `libsparse` Rust crate or shell out to `simg2img`).
   546→   546→   - If ext4: mount via `fuse2fs` (no root needed) or extract via `rust-ext4` crate (https://crates.io/crates/ext4).
   547→   547→   - Walk the filesystem and copy files into `<vmDataDir>/fs/system/`.
   548→   548→3. **Extract `product.img`** (if present) → `<vmDataDir>/fs/system/product/` (note: Treble flattens product under system on the device).
   549→   549→4. **Extract `system_ext.img`** (if present) → `<vmDataDir>/fs/system/system_ext/`.
   550→   550→5. **Extract `boot.img`** ramdisk (if present):
   551→   551→   - `boot.img` = header + kernel + ramdisk (gzip/lz4) + second stage.
   552→   552→   - Use the `bootimage` Rust crate to parse.
   553→   553→   - Extract the ramdisk and unpack with `cpio -idmv` (shell out).
   554→   554→   - Place into `<vmDataDir>/fs/ramdisk/`.
   555→   555→6. **Synthesise a minimal `vendor.img`** if the user didn't supply one:
   556→   556→   - Pre-built at `app/src/main/assets/vendor.img` — contains stub HALs for `vibrator`, `graphics.allocator`, `graphics.mapper`, `graphics.composer`, `audio`, `camera`, `sensors`, `gatekeeper`, `keymaster`, `health`, `power`.
   557→   557→   - Each HAL is a tiny binary that returns success for all calls.
   558→   558→   - Extract into `<vmDataDir>/fs/vendor/`.
   559→   559→7. **Apply init patches**:
   560→   560→   - Patch `/system/etc/init/hw/init.rc` to remove `mount` directives that would fail (e.g. `mount tmpfs tmpfs /tmp` is fine, `mount ext4 /dev/block/by-name/system /system` is not — remove these).
   561→   561→   - Add `LD_PRELOAD=libkr64.so` to the zygote service.
   562→   562→   - Patch `/vendor/etc/init/*.rc` similarly.
   563→   563→
   564→   564→**Files to create.**
   565→   565→- `app/src/main/java/io/twoyi/utils/GsiExtractor.java`
   566→   566→- `app/rs/gsi_extractor/Cargo.toml` — Rust crate for sparse/ext4/cpio parsing (call from Java via JNI).
   567→   567→- `app/rs/gsi_extractor/src/lib.rs` — JNI entry points: `nativeExtractSystemImg(path, destDir)`, `nativeExtractProductImg`, `nativeExtractBootImg`.
   568→   568→- `app/src/main/assets/vendor.img` — pre-built minimal vendor image (or a script to generate one from AOSP — see §5.7).
   569→   569→
   570→   570→**Files to modify.**
   571→   571→- `app/src/main/java/io/twoyi/utils/RomManager.java` — replace `initRootfs()` with a call to `GsiExtractor.extract(context, gsiFile)`.
   572→   572→
   573→   573→**Acceptance criteria.**
   574→   574→- Given an Android 11 x86_64 GSI `system.img` (from https://ci.android.com/builds/branches/aosp-master/grid), `GsiExtractor.extract()` produces a directory tree at `<vmDataDir>/fs/` containing `/system/bin/init`, `/system/etc/init/hw/init.rc`, `/system/product/`, `/system/system_ext/`, `/vendor/etc/vintf/manifest/`, etc.
   575→   575→- `file <vmDataDir>/fs/system/bin/init` reports `ELF 64-bit LSB shared object, x86-64`.
   576→   576→- The total size of the extracted tree is within 2x of the input `system.img` size (some files compress better as ext4 than as plain files).
   577→   577→
   578→   578→### 3.8 Init configuration
   579→   579→
   580→   580→**What VM does.** Eight `BugNFixTask` classes patch the extracted filesystem (see §2.9). Notably:
   581→   581→- `BuildVMPropTask` rewrites `/system/build.prop` with the host's build fingerprint.
   582→   582→- `MagiskTask` patches `/system/etc/init/hw/init.rc` to inject magisk service entries.
   583→   583→- `FixCPUArchTask` rewrites `app_process32`/`app_process64` symlinks.
   584→   584→- `BuildTmpfsTask` mounts tmpfs on `/tmp`, `/dev`, etc.
   585→   585→
   586→   586→**What twoyi currently does.** Patches `services.jar` for the `PackageInstallerSession` bug (`patchServicesJarForPackageInstaller`). No other init patches.
   587→   587→
   588→   588→**What to build.** A `GsiInitPatcher` Java class that applies these patches to the extracted GSI:
   589→   589→
   590→   590→1. **`/system/build.prop`** — overwrite these properties:
   591→   591→   - `ro.build.fingerprint` — set to the host's `Build.FINGERPRINT` (so Play Integrity basic attestation passes).
   592→   592→   - `ro.build.id` — set to the host's `Build.ID`.
   593→   593→   - `ro.build.version.incremental` — set to the host's `Build.VERSION.INCREMENTAL`.
   594→   594→   - `ro.product.cpu.abi` — set to the host's primary ABI (`x86_64` or `arm64-v8a`).
   595→   595→   - `ro.hardware` — set to `twoyi` (matches what `/proc/cmdline` returns).
   596→   596→2. **`/system/etc/init/hw/init.rc`** — apply these patches:
   597→   597→   - Remove all `mount ext4 …` and `mount f2fs …` lines (the filesystems are already mounted by libkr64).
   598→   598→   - Remove the `service flash_recovery` block (no recovery partition).
   599→   599→   - Add `setenv LD_PRELOAD /system/lib64/libkr64.so` to the `service zygote` block.
   600→   600→   - Add a new `service twoyi_event /system/bin/twoyi_event` that connects to the host's event socket and signals `BOOT_COMPLETED`.
   601→   601→3. **`/vendor/etc/init/*.rc`** — remove all `service` blocks that start HALs we don't implement (camera HAL, sensors HAL if not proxying). Replace with stub services that exit 0 immediately.
   602→   602→4. **`/system/bin/app_process64`** — replace with a wrapper script that execs the host's `app_process64` with `LD_PRELOAD` set:
   603→   603→   ```sh
   604→   604→   #!/system/bin/sh
   605→   605→   exec /system/bin/linker64 /system/lib64/libkr64.so --preload /system/bin/app_process64_real "$@"
   606→   606→   ```
   607→   607→   (Or better — keep the original `app_process64` binary from the GSI, but preload `libkr64.so` via `LD_PRELOAD` in the zygote service in init.rc.)
   608→   608→5. **`/system/etc/prop.default`** — apply the same patches as `/system/build.prop`.
   609→   609→6. **`/vendor/build.prop`** — set `ro.vendor.build.fingerprint` to match.
   610→   610→
   611→   611→**Files to create.**
   612→   612→- `app/src/main/java/io/twoyi/utils/GsiInitPatcher.java` — implements the above patches.
   613→   613→- `app/src/main/java/io/twoyi/utils/setup/` — port VM's `Bug1FixTask` … `Bug8FixTask` classes from `/home/z/my-project/vm-java-src/sources/com/android/vmcore/startup/`.
   614→   614→
   615→   615→**Files to modify.**
   616→   616→- `app/src/main/java/io/twoyi/utils/RomManager.java` — call `GsiInitPatcher.patch()` after `GsiExtractor.extract()`.
   617→   617→
   618→   618→**Acceptance criteria.**
   619→   619→- After patching, `grep "mount ext4" <vmDataDir>/fs/system/etc/init/hw/init.rc` returns no matches.
   620→   620→- After patching, `cat <vmDataDir>/fs/system/build.prop | grep ro.build.fingerprint` returns the host's fingerprint.
   621→   621→- After patching, `cat <vmDataDir>/fs/system/etc/init/hw/init.rc | grep LD_PRELOAD` shows the libkr64 preload.

   623→   623→### 3.9 HAL virtualisation
   624→   624→
   625→   625→**What VM does.** Full HAL proxy via `HALManager` (display, input, audio, camera, sensor, location, wifi, phone, battery, network) — see `VM_JAVA_ANALYSIS.md` §5.4 table.
   626→   626→
   627→   627→**What twoyi currently does.** Display (via `libOpenglRender`), input (touch + key), and that's it. No audio, camera, sensor, location, wifi, phone, battery, or network HALs.
   628→   628→
   629→   629→**What to build.** The minimum viable HAL set for a GSI to boot:
   630→   630→

   698→   698→## 4. Implementation priority (MVP → full)
   699→   699→
   700→   700→### 4.1 Minimum Viable Boot (MVP) — get a GSI to show its first frame
   701→   701→
   702→   702→To boot an Android 11 x86_64 GSI to the launcher (no apps installed, no audio, no camera), the minimum set is:
   703→   703→
   704→   704→1. **`app/rs/kr64/`** with:
   705→   705→   - Device tree creation (all 20+ devices from §2.4 table) — `devices.rs`.
   706→   706→   - `/dev/qemu_pipe` server (port from `app/rs/openglrenderer/src/pipe.rs`).
   707→   707→   - `/dev/__properties__` writer (init writes here, everyone reads).
   708→   708→   - `/dev/ashmem` proxy (use host's ashmem — Android 11 still supports it via the host kernel if the host is Android 10 or earlier; for Android 11+ hosts, use memfd).
   709→   709→   - `/dev/input/touch` (port from `app/rs/src/input.rs`).
   710→   710→   - `/dev/event` socket server (port from `app/src/main/java/io/twoyi/TwoyiSocketServer.java` — but make it a unix socket at `<vmDataDir>/dev/event`, not an abstract socket).
   711→   711→2. **`app/rs/kr64/src/proc_emu.rs`** — `/proc/cmdline` and `/proc/version` only (the rest can wait).
   712→   712→3. **`app/rs/kr64/src/gb.rs`** — `/dev/gb` with `ALLOCATE` ioctl routing to `libOpenglRender_aosp.so` ColorBuffer.
   713→   713→4. **`app/src/main/java/io/twoyi/utils/GsiExtractor.java`** — extract `system.img` + `product.img` + `system_ext.img` from a GSI.
   714→   714→5. **`app/src/main/java/io/twoyi/utils/GsiInitPatcher.java`** — apply the init.rc + build.prop patches.
   715→   715→6. **`app/rs/hals/graphics/`** — graphics allocator/mapper/composer HALs (critical).
   716→   716→7. **`app/rs/hals/keymaster/`** + **`app/rs/hals/gatekeeper/`** — stubs (return fixed keys).
   717→   717→8. **`app/rs/hals/health/`** + **`app/rs/hals/power/`** + **`app/rs/hals/vibrator/`** — stubs.
   718→   718→9. **`app/src/main/assets/vendor.img`** — pre-built minimal vendor image with the stub HALs.
   719→   719→
   720→   720→**Estimated effort:** 4–6 weeks for one engineer.
   721→   721→
   722→   722→### 4.2 What can be skipped initially
   723→   723→
   724→   724→- **Binder virtualisation (§3.2)** — skip for MVP. Use host's binder. The guest will boot but every `getSystemService()` returns host services. The guest's `system_server` will fail to register itself — boot will hang at the Android boot animation. To work around this for the MVP, patch `system_server` to not register (remove the `publishService` calls). This is hacky but lets you verify the rest of the stack works.
   725→   725→- **Seccomp filter (§3.4)** — skip for MVP. Just don't install it. The guest will see the host's `/proc` etc., which is wrong but won't crash immediately.
   726→   726→- **Full `/proc` emulator (§3.5)** — implement only `/proc/cmdline` and `/proc/version`. The rest can be the host's (until we hit a boot failure caused by it).
   727→   727→- **Inline hooking (§3.6)** — skip for MVP. The guest's `dlopen` will load from the host's `/system/lib64/`. This may cause ABI mismatches (host is Android 11, guest GSI is Android 11 — should be OK if versions match).
   728→   728→- **Audio/camera/sensors/gps/wifi/telephony/bluetooth HALs (§3.9)** — all stubs for MVP.
   729→   729→- **APEX support (§2.6)** — pre-extract all APEXes into `fs/system/apex/<name>/` and patch `apexd` to be a no-op.
   730→   730→
   731→   731→### 4.3 What's the hardest part?
   732→   732→
   733→   733→**Binder virtualisation (§3.2)** is by far the hardest. Reasons:
   734→   734→1. The binder protocol is complex (transactions, async/sync, death notifications, file descriptor passing).
   735→   735→2. The guest's `servicemanager` must register with our virtual binder, but the host's `servicemanager` is still running on the host's `/dev/binder`. We need to either:
   736→   736→   - Run a second `servicemanager` instance on our virtual binder (this is what VM does), or
   737→   737→   - Proxy all binder transactions to the host's `servicemanager` and translate the responses.
   738→   738→3. The Java-side `Proxy` of `IActivityManager` requires hidden-API access (FreeReflection) and careful handling of `transact()` calls.
   739→   739→4. Each Android version changes the binder transaction codes — we need to support A 9, A 11, A 13+ if we want multi-version support.
   740→   740→
   741→   741→**Graphics buffer management (§3.3)** is the second hardest — getting gralloc right so that SurfaceFlinger can composite is fiddly.
   742→   742→
   743→   743→**Seccomp + SIGSYS handler (§3.4)** is the third hardest — getting the BPF filter right so we trap exactly the right syscalls without breaking the guest requires careful testing.
   744→   744→
   745→   745→### 4.4 Suggested milestone order
   746→   746→
   747→   747→1. **Week 1–2:** `app/rs/kr64/` skeleton with device tree creation + `/dev/qemu_pipe` + `/dev/input/touch` + `/dev/event`. Test: can spawn `libkr64.so` and see the device files appear.
   748→   748→2. **Week 2–3:** `GsiExtractor.java` + `GsiInitPatcher.java`. Test: can extract an Android 11 x86_64 GSI into `<vmDataDir>/fs/` and patch init.rc.
   749→   749→3. **Week 3–4:** `app/rs/hals/graphics/` (graphics allocator/mapper/composer). Test: can allocate a buffer via the HAL.
   750→   750→4. **Week 4–5:** `/dev/gb` + integration with `libOpenglRender_aosp.so` ColorBuffer. Test: SurfaceFlinger can composite a frame.
   751→   751→5. **Week 5–6:** `app/rs/hals/keymaster/` + `gatekeeper/` + `health/` + `power/` + `vibrator/` stubs. Test: GSI boots to launcher.

   758→   758→## 5. Architecture for x86_64
   759→   759→
   760→   760→### 5.1 Why x86_64 is different
   761→   761→
   762→   762→Twoyi was originally arm64-only. The codespace `twoyi-dev-3-jr47xg6xvx7ghq6p` is x86_64 with KVM. Per `TWOYI_HONEST_STATUS.md`, the codespace has working KVM (AMD EPYC 7763, EastUs region). The Android emulator (AVD) on the codespace runs an x86_64 Android 11 image.
   763→   763→
   764→   764→For the container path (no KVM), we need:
   765→   765→1. An **x86_64 GSI** — `system-x86_64.img`, `product-x86_64.img`, etc. (from https://ci.android.com/builds/branches/aosp-master/grid).
   766→   766→2. **x86_64 native libraries** — `libkr64.so` must be built for x86_64. The existing PIE pattern in `app/rs/src/interp.c` already supports x86_64 (per `PIE_IMPLEMENTATION.md` and `app/rs/.cargo/config.toml`).
   767→   767→3. **x86_64 `libOpenglRender.so`** — already built and present at `/home/z/my-project/app/src/main/jniLibs/x86_64/libOpenglRender_aosp.so` (597 KB, all 6 twoyi ABI symbols exported — see `AOSP_BUILD_RESULTS.md`).
   768→   768→4. **x86_64 host** — the codespace runs Android Studio's emulator (or redroid container — see `REDROID_TESTING.md`). The host kernel must be x86_64 Linux (it is).
   769→   769→
   770→   770→### 5.2 x86_64-specific concerns
   771→   771→
   772→   772→1. **CPU architecture detection** — `libkr64.so` must detect the host ABI at runtime (via `__system_property_get("ro.product.cpu.abi")` or `getauxval(AT_BASE_PLATFORM)`) and load the correct guest libraries.
   773→   773→2. **Host vs guest ABI mismatch** — if the host is x86_64 and the guest GSI is arm64, the guest binaries won't run (no binary translation in the container path). **Always use a GSI matching the host ABI.**
   774→   774→3. **Kernel modules** — x86_64 kernels may not have `binder` or `ashmem` modules loaded by default. The codespace has them (per `TWOYI_HONEST_STATUS.md` — KVM is working). For non-codespace x86_64 hosts (e.g. a Linux desktop), the user may need to `modprobe binder_linux ashmem_linux`.
   775→   775→4. **SELinux** — x86_64 Android hosts (emulator, redroid) typically run with SELinux permissive. This is good for debugging but means we don't need to worry about SELinux denials for the MVP.
   776→   776→5. **GL driver** — `libOpenglRender_aosp.so` loads `libEGL.so` / `libGLESv1_CM.so` / `libGLESv2.so` from the system. On the x86_64 emulator these are SwiftShader (software GL). On a real x86_64 device they'd be the vendor's GL driver. Both work for our purposes.

   793→   793→### 5.4 The x86_64 boot flow (target)
   794→   794→
   795→   795→```
   796→   796→TwoyiApplication.onCreate (Java, x86_64)
   797→   797→  ├─ FreeReflection.exemptAll()
   798→   798→  ├─ System.loadLibrary("twoyi")  → libtwoyi.so (x86_64)
   799→   799→  └─ RomManager.ensureBootFiles()
   800→   800→      ├─ GsiExtractor.extract(context, systemImg)  → <vmDataDir>/fs/
   801→   801→      ├─ GsiInitPatcher.patch(<vmDataDir>/fs/)
   802→   802→      └─ BinderService.setupBinder(vmId, …)  → creates /vm0/dev/binder
   803→   803→
   804→   804→Render2Activity.onCreate (Java)
   805→   805→  └─ surfaceCreated → Renderer.init(surface, loaderPath, w, h, dpi)
   806→   806→      → libtwoyi.so::core::init_renderer
   807→   807→         ├─ input::start_input_system  (creates /dev/input/touch, /dev/input/key0)
   808→   808→         ├─ thread::spawn (renderer thread — opens /dev/qemu_pipe server)
   809→   809→         └─ Command::new("./libkr64.so")
   810→   810→              .arg("0").arg(vmDataDir).arg(fsDir).arg(libDir).arg(configPath).arg("3").arg("0")
   811→   811→              .env("LD_PRELOAD", "")  ← not for libkr64 itself
   812→   812→              .spawn()
   813→   813→              │
   814→   814→              └─ libkr64.so (x86_64 process):
   815→   815→                  ├─ parse argv (7 args)
   816→   816→                  ├─ create /dev/qemu_pipe, /dev/gb, /dev/gb2, /dev/input/touch,
   817→   817→                  │   /dev/event, /dev/__properties__, /dev/ashmem, /dev/vmproc, …
   818→   818→                  ├─ install seccomp filter
   819→   819→                  ├─ install SIGSYS handler
   820→   820→                  ├─ fork() → child:
   821→   821→                  │   ├─ chroot(<vmDataDir>/fs)
   822→   822→                  │   ├─ setenv("LD_PRELOAD", "/system/lib64/libkr64.so")
   823→   823→                  │   ├─ setenv("TWOYI_VM_ID", "0")
   824→   824→                  │   └─ execve("/system/bin/init", argv, envp)
   825→   825→                  └─ parent: accept loop on /dev/event socket
   826→   826→
   827→   827→Guest init (x86_64, in chroot):
   828→   828→  ├─ reads /system/etc/init/hw/init.rc (patched)
   829→   829→  ├─ mounts tmpfs on /tmp, /dev (already done by libkr64)
   830→   830→  ├─ starts servicemanager → registers with /vm0/dev/binder
   831→   831→  ├─ starts surfaceflinger → opens /dev/qemu_pipe (GL), /dev/gb (gralloc)
   832→   832→  ├─ starts hwservicemanager → registers with /dev/hwbinder (proxy to /vm0/dev/binder)
   833→   833→  ├─ starts audioserver, cameraserver → stub HALs
   834→   834→  ├─ starts zygote (with LD_PRELOAD=libkr64.so) → fork system_server
   835→   835→  ├─ system_server boots PackageManagerService, ActivityManagerService, etc.
   836→   836→  │   (these register with /vm0/dev/binder and proxy to host BinderService)
   837→   837→  └─ sys.boot_completed=1 → guest sends event via /dev/event socket:
   838→   838→       "BOOT_COMPLETED`"
   839→   839→       → TwoyiStatusManager.markStarted() → boot latch released → first frame
   840→   840→```

   842→   842→### 5.5 KVM alternative (out of scope for this plan)
   843→   843→
   844→   844→If the container path proves too hard, the alternative is to use KVM to boot the GSI in a real VM. The codespace has KVM. The flow would be:
   845→   845→
   846→   846→1. Use `crosvm` (Rust, https://crosvm.dev/) or QEMU to boot a minimal Linux kernel + the GSI's ramdisk.
   847→   847→2. The GSI boots in the VM as if on real hardware.
   848→   848→3. Display: `crosvm`'s GPU passthrough or `virglrenderer` — render to a host surface.
   849→   849→4. Input: `crosvm`'s virtual input devices.
   850→   850→5. Network: `crosvm`'s virtual network.
   851→   851→6. Binder: native (the guest has its own kernel binder).
   852→   852→
   853→   853→This is much simpler conceptually (no binder virtualisation, no `/proc` emulator, no seccomp — the guest kernel does everything) but requires:
   854→   854→- A Linux kernel configured for Android (binder, ashmem, etc.) — `android-common kernel`.
   855→   855→- A `boot.img` with that kernel + the GSI's ramdisk.
   856→   856→- `crosvm` or QEMU built for x86_64 Android (or run on the codespace's Linux host).
   857→   857→
   858→   858→**This is a separate project.** It's mentioned here for completeness. The container path is the architectural direction twoyi is already on, and is what `libkr64.so` does.

   981→   981→## 8. Conclusion
   982→   982→
   983→   983→Booting a GSI inside twoyi is a substantial but achievable project. The minimum viable boot (GSI to launcher, no audio/camera/etc.) requires:
   984→   984→
   985→   985→1. A new `app/rs/kr64/` Rust crate that mirrors VM's `libkr64.so` — creates the virtual `/dev` tree, installs seccomp, emulates `/proc`.
   986→   986→2. A new `app/src/main/java/io/twoyi/utils/GsiExtractor.java` that can extract an Android 11 GSI's `system.img`/`product.img`/`system_ext.img` into the per-VM `fs/` directory.
   987→   987→3. A new `app/src/main/java/io/twoyi/utils/GsiInitPatcher.java` that patches the extracted init.rc/build.prop for the container environment.
   988→   988→4. Stub HALs for graphics (critical), keymaster, health, power, vibrator.
   989→   989→5. A pre-built minimal `vendor.img` with the stub HALs.
   990→   990→
   991→   991→The hardest piece — binder virtualisation (§3.2) — can be skipped for the MVP by patching `system_server` to not register its services. The guest will boot to the launcher but won't be able to start its own apps. Once the rest of the stack works, implementing binder virtualisation is the next priority.
   992→   992→
   993→   993→For x86_64, all the necessary infrastructure is already in place: the codespace has KVM (for the alternative KVM path), the AOSP-built `libOpenglRender_aosp_x86_64.so` is ready, the Rust crates already build for x86_64, and x86_64 GSIs are downloadable from `ci.android.com`.
   994→   994→
   995→   995→**Estimated total effort:** 8–12 weeks for one engineer to reach a MVP GSI boot on x86_64, 16–24 weeks for full feature parity with Virtual Master.
