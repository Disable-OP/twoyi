    25→## 1. Why we need an x86_64 rootfs
    26→
    27→This is the **single biggest blocker for x86_64 testing** of twoyi. The proof is in
    28→[`download/TWOYI_HONEST_STATUS.md`](TWOYI_HONEST_STATUS.md) §"Why the QEMU pipe is unavailable":
    29→
    30→> Twoyi's architecture requires the guest Android's SurfaceFlinger to communicate with
    31→> the host renderer via `/dev/qemu_pipe`. This pipe is created by the twoyi guest's
    32→> modified `init` process inside the rootfs.
    33→>
    34→> In the Android emulator:
    35→> - The host Android (API 30, x86_64) does NOT have `/dev/qemu_pipe`
    36→> - The twoyi guest rootfs IS extracted to `/data/data/io.twoyi/rootfs/`
    37→> - The guest `init` binary IS arm64 (the rootfs was built for arm64)
    38→> - The guest `init` cannot execute on x86_64 (architecture mismatch)
    39→> - Therefore the QEMU pipe is never created
    40→> - Therefore the renderer has nothing to connect to
    41→
    42→Concretely, the failure sequence on x86_64 today is:
    43→
    44→```
    45→1. Host: twoyi APK launches, extracts rootfs.tar.gz → /data/data/io.twoyi/rootfs/
    46→2. Host: libtwoyi.so calls Command::new("./init").spawn()   ← ./init is arm64 ELF
    47→3. Kernel: execve("./init") returns ENOEXEC on x86_64 host   ← architecture mismatch
    48→4. Host: renderer connects to /dev/qemu_pipe                 ← doesn't exist
    49→5. Host: CLIENT_EGL: [NEW_RENDERER] Failed to write to pipe: Invalid argument (os error 22)
    50→6. Host: BootLogTexture spins forever; after 60s, Render2Activity times out
    51→```
    52→
    53→A successful boot requires every guest binary that the host kernel will `execve` to be
    54→a native x86_64 ELF. The minimum set is:
    55→
    56→- `init` — the twoyi custom init at the **rootfs root** (not `/system/bin/init`)
    57→- `/system/bin/init` — the AOSP init that the custom init exec's into
    58→- `/system/bin/app_process64` — the zygote / ART runtime
    59→- `/system/bin/servicemanager`, `/system/bin/surfaceflinger`, `/system/bin/logd`, …
    60→- `/system/lib64/*.so` — bionic libc, libart, libui, libgui, libbinder, …
    61→
    62→All of these come "for free" if you build AOSP for `x86_64` instead of `arm64`.

    66→## 2. Prerequisites

    68→### 2.1 Hardware
    69→
    70→| Resource | Minimum | Recommended | Notes |
    71→|---|---|---|---|
    72→| **CPU** | 4 cores, x86_64, VT-x/AMD-V | 8+ cores | AOSP `make -jN` scales nearly linearly to ~16 cores. |
    73→| **RAM** | 16 GB | 32 GB | Below 16 GB, the link step for `libart.so` will OOM. Add swap if you must. |

   166→## 3. Step-by-step build process (Path A)
   167→
   168→This section builds a complete x86_64 userland from `android-8.1.0_r81` and packages
   169→it as a `rootfs.tar.gz` that twoyi's `RomManager` will accept.
   170→
   171→### 3.1 Lay out the workspace
   172→
   173→```bash
   174→mkdir -p ~/aosp && cd ~/aosp
   175→
   176→# Twoyi patches live here (we'll create them in §3.4):
   177→mkdir -p patches/{system,core,frameworks}
   178→```
   179→
   180→### 3.2 `repo init` — use the twoyi manifest
   181→
   182→You have two equivalent options. **Option 1 is preferred** because it pins the exact
   183→commit tree that twoyi was developed against.
   184→
   185→**Option 1 — use the manifest from the twoyi repo (recommended):**
   186→
   187→```bash
   188→cd ~/aosp
   189→# Copy the recovered manifest from the twoyi repo:
   190→cp /home/z/my-project/default.xml ./.local-manifest.xml
   191→# Trick repo into using it: `repo init -m` reads the named manifest from .repo/manifests/
   192→mkdir -p .repo/manifests
   193→cp /home/z/my-project/default.xml .repo/manifests/twoyi.xml
   194→repo init -u https://android.googlesource.com/platform/manifest -m twoyi.xml
   195→```
   196→
   197→The twoyi manifest's `<default>` element (line 7–9 of `default.xml`) is:
   198→
   199→```xml
   200→<default revision="refs/tags/android-8.1.0_r81"
   201→         remote="aosp"
   202→         sync-j="4" />
   203→```
   204→
   205→This pins every project to the `android-8.1.0_r81` tag — the build label Google
   206→shipped as the official Android 8.1.0 release for Pixel 2 / Pixel 2 XL.
   207→
   208→**Option 2 — use the upstream manifest at the same tag:**
   209→
   210→```bash
   211→cd ~/aosp
   212→repo init -u https://android.googlesource.com/platform/manifest -b android-8.1.0_r81
   213→```
   214→
   215→This is functionally identical because the twoyi `default.xml` was generated from
   216→this exact tag — but Option 1 lets you diff against future manifest changes.
   217→
   218→### 3.3 `repo sync -c -j8`
   219→
   220→```bash
   221→repo sync -c -j8
   222→```
   223→
   224→Flags:
   225→
   226→- `-c` — checkout the *current* branch (faster; skips fetching other heads).
   227→- `-j8` — 8 parallel fetches. Bump to `-j16` on a Gigabit link; drop to `-j4` on slow
   228→  networks. Google rate-limits per-IP, so very high `-j` often backfires.
   229→
   230→Expected output: ~30 GB downloaded, ~1,100 git repositories checked out. Wall-clock:
   231→30 min on Gigabit, 2–4 hours on a 50 Mbit/s link.
   232→
   233→If a project fails to sync (network blip), just re-run `repo sync -c -j8` — `repo`
   234→will resume where it left off.
   235→
   236→After sync, sanity-check the tree:
   237→
   238→```bash
   239→# Confirm the build tag is what we expect:
   240→cd build/make && git describe --tags && cd -
   241→# Expect: android-8.1.0_r81
   242→
   243→# Confirm the x86_64 device target exists:
   244→ls device/generic/x86_64
   245→# Expect: AndroidBoard.mk  AndroidProducts.mk  Box.mk  ...  vendor/
   246→```

   248→### 3.4 Apply twoyi-specific patches
   249→
   250→These are the changes that make the AOSP userland talk to twoyi's host renderer
   251→instead of to a real kernel/emulator. There are four patches; each is small.
   252→
   253→#### 3.4.1 Patch 1 — `init` creates `/dev/qemu_pipe` early in boot
   254→
   255→Twoyi's host renderer (`libOpenglRender_aosp.so`) listens on a Unix domain socket at
   256→`/dev/qemu_pipe` inside the guest rootfs. The guest's `SurfaceFlinger` connects to
   257→this socket and writes emugl wire-protocol GLES commands.
   258→
   259→The guest `init` must `mknod`/`bind-mount` this socket *before* `surfaceflinger`
   260→starts. Add a new early-init action to `system/core/init/init.rc`:
   261→
   262→```bash
   263→cd ~/aosp
   264→cat > patches/system/init_qemu_pipe.rc <<'EOF'
   265→# Twoyi: create /dev/qemu_pipe as a Unix domain socket for the host renderer.
   266→# The socket is abstract; the host (libOpenglRender_aosp.so) bind-listens here.
   267→on early-init
   268→    mkdir /dev/socket 0777 root root
   269→    start twoyi_qemu_pipe_setup
   270→
   271→service twoyi_qemu_pipe_setup /system/bin/twoyi_pipe_setup
   272→    class core
   273→    user root
   274→    group root
   275→    oneshot
   276→    disabled
   277→EOF
   278→
   279→cat > patches/system/twoyi_pipe_setup.c <<'EOF'
   280→// Tiny helper that creates the /dev/qemu_pipe Unix socket symlink
   281→// pointing at the abstract-namespace socket the host renderer binds.
   282→// (Equivalent to what real QEMU does on the kernel side, but in
   283→// userspace because twoyi has no kernel of its own.)
   284→#include <sys/socket.h>
   285→#include <sys/un.h>
   286→#include <unistd.h>
   287→#include <stdio.h>
   288→#include <string.h>
   289→#include <errno.h>
   290→#include <fcntl.h>
   291→
   292→int main(void) {
   293→    // Create a filesystem-backed Unix socket the host will bind to.
   294→    // The host (libOpenglRender_aosp.so) does bind() first; we just
   295→    // pre-create the path so SurfaceFlinger's connect() succeeds.
   296→    int fd = socket(AF_UNIX, SOCK_STREAM, 0);
   297→    if (fd < 0) { perror("socket"); return 1; }
   298→
   299→    struct sockaddr_un addr;
   300→    memset(&addr, 0, sizeof(addr));
   301→    addr.sun_family = AF_UNIX;
   302→    strncpy(addr.sun_path, "/dev/qemu_pipe", sizeof(addr.sun_path) - 1);
   303→
   304→    // If the socket already exists, unlink it (leftover from previous boot).
   305→    unlink("/dev/qemu_pipe");
   306→
   307→    if (bind(fd, (struct sockaddr *)&addr, sizeof(addr)) < 0) {
   308→        perror("bind /dev/qemu_pipe");
   309→        // Fall through — the host may have already bound it.
   310→    }
   311→    listen(fd, 4);
   312→    close(fd);
   313→
   314→    // Mark the pipe as "QEMU pipe" magic — guest code checks this signature
   315→    // via the "qemu_pipe" device path and refuses to connect if absent.
   316→    int magic = open("/dev/qemu_pipe", O_WRONLY | O_CREAT, 0666);
   317→    if (magic >= 0) {
   318→        write(magic, "QEMU", 4);
   319→        close(magic);
   320→    }
   321→    return 0;
   322→}
   323→EOF
   324→
   325→# Drop the .rc file into the device init dir that gets installed:
   326→cp patches/system/init_qemu_pipe.rc system/core/rootdir/init.rc
   327→cp patches/system/twoyi_pipe_setup.c system/core/init/twoyi_pipe_setup.cpp
   328→```
   329→
   330→You'll also need to add a one-line `Android.bp` entry to compile
   331→`twoyi_pipe_setup.cpp` (look at how `/system/bin/init` itself is declared in
   332→`system/core/init/Android.bp` for a template).
   333→
   334→> **Alternative:** skip the C helper and use the `init.rc` `mkdir` + `chmod`
   335→> directives only — the host renderer can create the socket itself with a small
   336→> change to `libOpenglRender_aosp.so` (see `AOSP_BUILD_RESULTS.md` §5.3 for the
   337→> `UnixStream.cpp` patch that controls the path). The guest then just needs
   338→> `/dev/qemu_pipe` to exist as an empty file. This is what the cyanmint arm64
   339→> rootfs does.
   340→
   341→#### 3.4.2 Patch 2 — SurfaceFlinger uses the qemu_pipe renderer
   342→
   343→SurfaceFlinger picks its rendering backend via a build property. In AOSP 8.1 the
   344→default is `ro.surface_flinger.use_gl=0` (HWC path), which needs a real hardware
   345→composer HAL. Twoyi has no HWC, so we force the GL/emugl path.
   346→
   347→Edit `frameworks/native/services/surfaceflinger/SurfaceFlinger.cpp` and add at the
   348→top of `SurfaceFlinger::init()`:
   349→
   350→```cpp
   351→// Twoyi: force the GL ES renderer over the QEMU pipe. There is no HWC.
   352→char val[PROPERTY_VALUE_MAX];
   353→property_set("ro.surface_flinger.use_gl", "1");
   354→property_set("ro.surface_flinger.use_hwc", "0");
   355→property_set("debug.egl.hwcomposer", "0");
   356→property_set("ro.hardware.egl", "emugl");
   357→```
   358→
   359→(The cyanmint arm64 rootfs does the equivalent by editing `system/build.prop`
   360→post-extract — see `BuildVMPropTask.java` in VM's decompiled sources — but doing
   361→it at AOSP build time is cleaner.)
   362→
   363→#### 3.4.3 Patch 3 — disable SELinux enforcing
   364→
   365→Twoyi runs as an unprivileged app; it cannot set SELinux contexts on the guest
   366→filesystem. The guest `init` would fail to relabel `/dev`, `/system`, etc. Force
   367→permissive mode by editing `system/core/init/init.cpp`:
   368→
   369→```cpp
   370→// Twoyi: we run inside an unprivileged host app — no SELinux.
   371→// Skip selinux_init() and force permissive.
   372→selinux_setenforce(0);
   373→// Comment out:  selinux_init_selinux_handle();
   374→//               selinux_set_policyload();
   375→```
   376→
   377→(Equivalent to the kernel cmdline `androidboot.selinux=permissive`, but twoyi has
   378→no kernel cmdline.)
   379→
   380→#### 3.4.4 Patch 4 — `ro.build.fingerprint` is consistent
   381→
   382→Twoyi's host-side `BuildVMPropTask.java` (decompiled from Virtual Master) rewrites
   383→`/system/build.prop` post-extract to make the fingerprint match the host's. To
   384→avoid that step entirely, set the fingerprint at build time:
   385→
   386→```bash
   387→# In ~/aosp/build/make/tools/buildinfo.sh, prepend:
   388→cat >> build/make/tools/buildinfo.sh.twoyi_override <<'EOF'
   389→ro.build.fingerprint=twoyi/twoyi/twoyi:8.1.0/$(shell date +%Y%m%d)/1
   390→ro.bootimage.build.fingerprint=twoyi/twoyi/twoyi:8.1.0/$(shell date +%Y%m%d)/1
   391→ro.product.cpu.abi=x86_64
   392→ro.product.cpu.abilist=x86_64,x86
   393→EOF
   394→```

   396→### 3.5 `lunch sdk_gphone_x86_64-userdebug`
   397→
   398→```bash
   399→. build/envsetup.sh
   400→
   401→# List x86_64 lunch targets:
   402→lunch | grep x86_64
   403→
   404→# Pick the SDK phone x86_64 target — this is the closest to twoyi's
   405→# "Android 8.1 userland running on a virtual device" use case:
   406→lunch sdk_gphone_x86_64-userdebug

   408→
   409→> **Why `sdk_gphone_x86_64` and not `aosp_x86_64`?**
   410→>
   411→> The `sdk_gphone_*` targets include the goldfish HALs (`device/generic/goldfish-opengl`),
   412→> which speak the QEMU pipe protocol that twoyi's renderer also speaks. The bare
   413→> `aosp_x86_64` target omits them and you'd have to add them back as a separate
   414→> `device/generic/goldfish-opengl` build.
   415→>
   416→> Other valid choices:
   417→> - `aosp_x86_64-userdebug` — minimal AOSP; you'll need to add `goldfish-opengl` yourself.
   418→> - `sdk_phone_x86_64-userdebug` — same as `sdk_gphone_x86_64` but for the non-goldfish
   419→>   "phone" form factor.
   420→
   421→Sanity-check the chosen target:
   422→
   423→```bash
   424→printconfig
   425→# Expect:
   426→#   TARGET_PRODUCT=sdk_gphone_x86_64
   427→#   TARGET_BUILD_VARIANT=userdebug
   428→#   TARGET_BUILD_TYPE=release
   429→#   TARGET_ARCH=x86_64
   430→#   TARGET_ARCH_VARIANT=x86_64

   437→### 3.6 `make -j8`
   438→
   439→```bash
   440→make -j8
   441→```
   442→
   443→Build targets worth knowing:
   444→
   445→- `make -j8` (no arg) — full build. Produces `out/target/product/sdk_gphone_x86_64/system.img`,
   446→  `userdata.img`, `ramdisk.img`, and `boot.img` (the latter two we don't need for twoyi).
   447→- `make snod -j8` — "system image no dependency": rebuilds `system.img` from the
   448→  current `out/.../system/` tree without re-running the C++/Java compilation. Fast
   449→  iteration when you've only changed `init.rc` or `.prop` files.
   450→- `make init -j8` — builds just `/system/bin/init`. Useful when iterating on Patch 1
   451→  above.
   452→
   453→Wall-clock expectations:
   454→
   455→| Hardware | First full `make -j8` | Incremental `make snod` |
   456→|---|---|---|
   457→| 4 cores, 16 GB, HDD | 6–8 hours | 2–3 min |
   458→| 8 cores, 32 GB, SSD | 2–4 hours | 1–2 min |
   459→| 16 cores, 64 GB, NVMe | 1.5–2.5 hours | <1 min |
   460→
   461→The link step for `libart.so` is the heaviest single task — it can use 12+ GB RAM
   462→briefly. If `make` dies with `collect2: ld terminated with signal 9 (SIGKILL)`,
   463→add swap:
   464→
   465→```bash
   466→sudo fallocate -l 16G /swapfile
   467→sudo chmod 600 /swapfile
   468→sudo mkswap /swapfile
   469→sudo swapon /swapfile
   470→```

   472→### 3.7 Extract the system image
   473→
   474→After a successful `make`, the system image is at:
   475→
   476→```bash
   477→ls -lh out/target/product/sdk_gphone_x86_64/system.img
   478→# -rw-rw-r-- 1 user user 1.1G ... system.img
   479→file out/target/product/sdk_gphone_x86_64/system.img
   480→# out/.../system.img: Android sparse image, ...
   481→```
   482→
   483→It's an Android sparse image — convert it to raw ext4:
   484→
   485→```bash
   486→simg2img out/target/product/sdk_gphone_x86_64/system.img system.raw.img
   487→file system.raw.img
   488→# system.raw.img: Linux rev 1.0 ext4 filesystem data, ...
   489→```
   490→
   491→Mount and copy the contents out:
   492→
   493→```bash
   494→mkdir -p /mnt/system
   495→sudo mount -o loop,ro system.raw.img /mnt/system
   496→ls /mnt/system
   497→# Expect: bin/  build.prop  etc/  framework/  lib64/  priv-app/  ...
   498→
   499→# Copy the system partition into the rootfs skeleton:
   500→mkdir -p ~/twoyi-rootfs
   501→sudo cp -a /mnt/system/. ~/twoyi-rootfs/system/
   502→sudo umount /mnt/system
   503→```
   504→
   505→### 3.8 Package as `rootfs.tar.gz` matching twoyi's layout
   506→
   507→Twoyi's `RomManager.romExist()` checks for `init` at the **rootfs root** (not
   508→`/system/bin/init`) — see `app/src/main/java/io/twoyi/utils/RomManager.java:182`:
   509→
   510→```java
   511→public static boolean romExist(Context context) {
   512→    File initFile = new File(getRootfsDir(context), "init");
   513→    return initFile.exists();
   514→}
   515→```
   516→
   517→So the rootfs layout twoyi expects is:
   518→
   519→```
   520→rootfs/                 ← what gets extracted to /data/data/io.twoyi/rootfs/
   521→├── init                ← custom twoyi init (exec's /system/bin/init after setup)
   522→├── rom.ini             ← ROM metadata (see §3.8.3)
   523→├── system/             ← the AOSP system partition you just extracted
   524→│   ├── bin/
   525→│   │   └── init        ← the AOSP init that init (above) exec's into
   526→│   ├── build.prop
   527→│   ├── etc/
   528→│   ├── framework/
   529→│   ├── lib64/          ← x86_64 .so files
   530→│   ├── priv-app/
   531→│   └── ...
   532→├── vendor/             ← empty or stub (twoyi doesn't use a vendor partition yet)
   533→├── data/               ← writable; created empty
   534→│   └── local/tmp/      ← created by RomManager.ensureDataLocalTmp()
   535→├── dev/
   536→│   ├── input/          ← created by RomManager.ensureBootFiles()
   537→│   ├── socket/         ← created by RomManager.ensureBootFiles()
   538→│   └── maps/           ← created by RomManager.ensureBootFiles()
   539→└── sdcard/             ← created empty
   540→```
   541→
   542→#### 3.8.1 Build the custom twoyi `init` binary
   543→
   544→The twoyi custom `init` at the rootfs root is a tiny C program that:
   545→
   546→1. `mknod`s `/dev/null`, `/dev/zero`, `/dev/random`, `/dev/urandom`, `/dev/ptmx`,
   547→   `/dev/tty`, `/dev/qemu_pipe`, `/dev/binder`, `/dev/ashmem`, `/dev/__properties__`.
   548→2. Sets up `/proc` and `/sys` (mounts or symlinks to host's, depending on whether
   549→   the `kr64` daemon is in use).
   550→3. Sets a few environment variables (`ANDROID_ROOT=/system`, `ANDROID_DATA=/data`,
   551→   `BOOTCLASSPATH=...`).
   552→4. Exec's `/system/bin/init` with the standard Android init args.
   553→
   554→The legacy cyanmint arm64 rootfs ships this as a 64-bit PIE binary. For x86_64 you
   555→build it the same way, just with a different target. A minimal version:
   556→
   557→```c
   558→// twoyi_init.c — compile with:
   559→//   gcc -static -o twoyi_init twoyi_init.c
   560→// then rename to `init` and place at the rootfs root.
   561→#define _GNU_SOURCE
   562→#include <sys/mount.h>
   563→#include <sys/stat.h>
   564→#include <sys/types.h>
   565→#include <unistd.h>
   566→#include <stdio.h>
   567→#include <stdlib.h>
   568→#include <string.h>
   569→#include <errno.h>
   570→
   571→static void mknod_safe(const char *path, mode_t mode, dev_t dev) {
   572→    if (mknod(path, mode | 0666, dev) < 0 && errno != EEXIST) {
   573→        fprintf(stderr, "mknod %s: %s\n", path, strerror(errno));
   574→    }
   575→}
   576→
   577→int main(int argc, char **argv) {
   578→    setenv("ANDROID_ROOT",  "/system", 1);
   579→    setenv("ANDROID_DATA",  "/data",   1);
   580→    setenv("PATH", "/system/bin:/system/xbin:/vendor/bin", 1);
   581→
   582→    // Create essential device nodes (or rely on kr64 daemon to create them).
   583→    mkdir("/dev",    0755);
   584→    mkdir("/dev/socket", 0755);
   585→    mkdir("/dev/input",  0755);
   586→    mkdir("/proc",   0555);
   587→    mkdir("/sys",    0555);
   588→
   589→    mknod_safe("/dev/null",     S_IFCHR, makedev(1, 3));
   590→    mknod_safe("/dev/zero",     S_IFCHR, makedev(1, 5));
   591→    mknod_safe("/dev/random",   S_IFCHR, makedev(1, 8));
   592→    mknod_safe("/dev/urandom",  S_IFCHR, makedev(1, 9));
   593→    mknod_safe("/dev/ptmx",     S_IFCHR, makedev(5, 2));
   594→    mknod_safe("/dev/tty",      S_IFCHR, makedev(5, 0));
   595→
   596→    // qemu_pipe: created by libOpenglRender_aosp.so (host side); we just
   597→    // make sure the /dev directory exists. See Patch 1 in §3.4.1 if you
   598→    // prefer to pre-create the socket path here.
   599→
   600→    // Mount /proc and /sys (or, if running under the kr64 daemon, those
   601→    // mounts are emulated).
   602→    mount("proc",     "/proc", "proc",     0, NULL);
   603→    mount("sysfs",    "/sys",  "sysfs",    0, NULL);
   604→    mount("devpts",   "/dev/pts", "devpts", 0, NULL);
   605→    mount("tmpfs",    "/dev/socket", "tmpfs", 0, "mode=0777");
   606→
   607→    // Hand off to the real AOSP init:
   608→    char *init_args[] = { "/system/bin/init", NULL };
   609→    execv(init_args[0], init_args);
   610→    perror("exec /system/bin/init");
   611→    return 1;
   612→}
   613→```
   614→
   615→Build it:
   616→
   617→```bash
   618→gcc -static -O2 -o ~/twoyi-rootfs/init twoyi_init.c
   619→file ~/twoyi-rootfs/init
   620→# Expect: ... ELF 64-bit LSB executable, x86-64, version 1 (SYSV), statically linked, ...
   621→```
   622→
   623→#### 3.8.2 Create `rom.ini`
   624→
   625→```bash
   626→cat > ~/twoyi-rootfs/rom.ini <<'EOF'
   627→author=twoyi-x86_64-build
   628→version=android-8.1.0_r81
   629→code=81000081
   630→md5=00000000000000000000000000000000
   631→desc=x86_64 AOSP 8.1.0_r81 built for twoyi (Rootfs Build Guide)
   632→EOF
   633→```
   634→
   635→(`code` is an integer version code — pick a sensible scheme; `md5` can be left as
   636→zeros — `RomManager` uses it only to detect changes.)
   637→
   638→#### 3.8.3 Create the empty writable directories
   639→
   640→```bash
   641→mkdir -p ~/twoyi-rootfs/{data/local/tmp,dev/{input,socket,maps},sdcard,vendor}
   642→chmod 0777 ~/twoyi-rootfs/data/local/tmp
   643→```
   644→
   645→#### 3.8.4 Tar it up
   646→
   647→```bash
   648→cd ~/twoyi-rootfs
   649→sudo tar --owner=0 --group=0 --numeric-owner -czf ~/rootfs.tar.gz .
   650→ls -lh ~/rootfs.tar.gz
   651→# Expect: ~400-800 MB depending on what got built.
   652→```
   653→
   654→Verify the contents:
   655→
   656→```bash
   657→tar tzf ~/rootfs.tar.gz | head -20
   658→# Expect:
   659→# ./
   660→# ./init
   661→# ./rom.ini
   662→# ./system/
   663→# ./system/bin/
   664→# ./system/bin/init
   665→# ./system/bin/linker64           <-- the x86_64 dynamic linker
   666→# ./system/bin/servicemanager
   667→# ./system/bin/surfaceflinger
   668→# ./system/bin/app_process64
   669→# ./system/lib64/
   670→# ./system/lib64/libc.so
   671→# ./system/lib64/libart.so
   672→# ./system/lib64/libui.so
   673→# ./system/lib64/libgui.so
   674→# ./system/lib64/libbinder.so
   675→# ...
   676→
   677→# Confirm the init binary is x86_64:
   678→mkdir /tmp/verify-init && tar xzf ~/rootfs.tar.gz -C /tmp/verify-init ./init
   679→file /tmp/verify-init/init
   680→# Expect: ELF 64-bit LSB executable, x86-64, ...
   681→```
   682→
   683→You now have `~/rootfs.tar.gz` — drop it into the twoyi APK build as
   684→`app/src/main/assets/rootfs.tar.gz` (or push it to a running device and use the
   685→"Import ROM" flow).

   689→## 4. Alternative: use a pre-built x86_64 GSI (Path B)
   690→
   691→If you don't want to do a full AOSP build, you can download a pre-built Treble GSI
   692→and convert it. This is faster but lower fidelity: GSIs are built for newer Android
   693→versions (10+) and assume Treble HALs that twoyi's kernel-replacement daemon
   694→doesn't yet virtualise.
   695→
   696→### 4.1 Where to get an x86_64 GSI
   697→
   698→| Source | URL | Notes |
   699→|---|---|---|
   700→| **Google GSI downloads** (official) | <https://developers.google.com/android/images> | Look under "Treble GSI images" for the latest `system-*.img`. These are signed by Google. |
   701→| **AOSP CI** | <https://ci.android.com/builds/branches/aosp-master/grid> | Search for `aosp_x86_64-userdebug`. Bleeding-edge, may be unstable. |
   702→| **Android GSI documentation** | <https://source.android.com/docs/core/ota/gsi> | Background reading; explains what a GSI is and which one to pick for your device. |
   703→
   704→For twoyi, pick:
   705→
   706→- **Architecture**: `x86_64`
   707→- **Variant**: `userdebug` (so you have `adb root`)
   708→- **Android version**: ideally **8.1** to match `default.xml`. Google does not ship
   709→  8.1 GSIs anymore — the closest signed GSI is `android-9.0_r46` (`system-x86_64.img`).
   710→  If you can tolerate a version mismatch, an Android 11 GSI (`RQ3A.211001.001`) works
   711→  too but expect more HALs to fail.
   712→
   713→Example download:
   714→
   715→```bash
   716→# Android 11 GSI, x86_64, userdebug:
   717→curl -L -o gsi.zip \
   718→  https://dl.google.com/developers/android/r11/images/gsi/aosp_x86_64-img-211001001.zip
   719→unzip gsi.zip
   720→ls
   721→# Expect: system.img   (sparse ext4, ~1.5 GB)
   722→```
   723→
   724→### 4.2 Convert the GSI to a twoyi rootfs
   725→
   726→The GSI ships only `system.img` — no `vendor.img`, no `boot.img`, no `init` at the
   727→root. To turn it into a twoyi rootfs:
   728→
   729→```bash
   730→mkdir -p ~/twoyi-gsi-rootfs
   731→cd ~/twoyi-gsi-rootfs
   732→
   733→# 1. Convert sparse → raw:
   734→simg2img ../system.img system.raw.img
   735→
   736→# 2. Mount and copy out the system partition:
   737→mkdir -p /mnt/system
   738→sudo mount -o loop,ro system.raw.img /mnt/system
   739→sudo cp -a /mnt/system/. system/
   740→sudo umount /mnt/system
   741→
   742→# 3. Apply the same patches as §3.4 (init.rc, build.prop, SurfaceFlinger).
   743→#    For a GSI these must be applied post-extract because you didn't build it:
   744→sudo sed -i 's/ro.surface_flinger.use_gl=0/ro.surface_flinger.use_gl=1/' \
   745→    system/build.prop
   746→echo 'ro.surface_flinger.use_hwc=0' | sudo tee -a system/build.prop
   747→echo 'debug.egl.hwcomposer=0'       | sudo tee -a system/build.prop
   748→echo 'ro.hardware.egl=emugl'        | sudo tee -a system/build.prop
   749→sudo setenforce 0 2>/dev/null || true  # no-op on host; guest init does it
   750→
   751→# 4. Build the custom twoyi init binary (same as §3.8.1):
   752→gcc -static -O2 -o init twoyi_init.c   # same source as §3.8.1
   753→
   754→# 5. Create empty writable dirs + rom.ini (same as §3.8.2 and §3.8.3):
   755→mkdir -p {data/local/tmp,dev/{input,socket,maps},sdcard,vendor}
   756→echo -e "author=twoyi-gsi-x86_64\nversion=android-11-gsi\ncode=11000000\nmd5=0\ndesc=x86_64 GSI converted for twoyi" > rom.ini
   757→
   758→# 6. Tar it:
   759→sudo tar --owner=0 --group=0 --numeric-owner -czf ~/rootfs.tar.gz .
   760→
   761→# 7. Sanity-check:
   762→file init    # must be x86-64
   763→ls system/bin/init system/bin/app_process64 system/lib64/libc.so
   764→```
   765→
   766→### 4.3 Caveats with the GSI path
   767→
   768→- **No matching `vendor.img`** — the GSI expects Treble HALs that twoyi doesn't yet
   769→  provide. `init` will log many "service ... not found" errors. Some are fatal
   770→  (e.g. `gatekeeperd` missing → boot stalls at "Decrypting /data").
   771→- **Android 10+ requires APEX** — `system/apex/com.android.*` are mini-images that
   772→  `apexd` must mount. Either pre-extract them (set `ro.apex.updatable=false` and
   773→  bind-mount each APEX's `apex_payload.img`) or skip by patching `init.rc`.
   774→- **Different bionic ABI** — the GSI's `libc.so` was built for Android 11; twoyi's
   775→  host kernel is whatever the emulator provides. Usually fine, but watch for
   776→  `getrandom()` / `memfd_create()` syscall-number mismatches.
   777→
   778→For the **first end-to-end smoke test** of twoyi on x86_64, the GSI path is fine.
   779→For ongoing development, build from AOSP source (§3) so you have full control.
   780→

   783→## 5. How to test
   784→
   785→Once you have `rootfs.tar.gz`, verify it end-to-end.
   786→
   787→### 5.1 Verify the init binary is x86_64 (5 seconds)
   788→
   789→```bash
   790→mkdir /tmp/rootfs-check && tar xzf ~/rootfs.tar.gz -C /tmp/rootfs-check ./init
   791→file /tmp/rootfs-check/init
   792→# Expect: ELF 64-bit LSB executable, x86-64, version 1 (SYSV), statically linked, ...
   793→
   794→# Also check the AOSP init and a representative .so:
   795→tar xzf ~/rootfs.tar.gz -C /tmp/rootfs-check \
   796→    ./system/bin/init ./system/lib64/libc.so
   797→file /tmp/rootfs-check/system/bin/init
   798→# Expect: ELF 64-bit LSB shared object, x86-64, ...
   799→file /tmp/rootfs-check/system/lib64/libc.so
   800→# Expect: ELF 64-bit LSB shared object, x86-64, ...
   801→```
   802→
   803→If any of these say `aarch64` or `ARM`, your lunch target was wrong — go back to §3.5.
   804→
   805→### 5.2 Push the rootfs into the twoyi APK build
   806→
   807→Two options:
   808→
   809→**Option A — bundle into the APK at build time:**
   810→
   811→```bash
   812→cp ~/rootfs.tar.gz /home/z/my-project/app/src/main/assets/rootfs.tar.gz
   813→cd /home/z/my-project
   814→./gradlew assembleRelease -Pabis=x86_64
   815→ls -lh app/build/outputs/apk/release/*.apk
   816→```
   817→
   818→**Option B — push to a running device and use the "Import ROM" flow:**
   819→
   820→```bash
   821→adb push ~/rootfs.tar.gz /sdcard/Download/rootfs.tar.gz
   822→# In the twoyi app: Settings → "Import ROM" → pick /sdcard/Download/rootfs.tar.gz
   823→```
   824→
   825→### 5.3 Boot the emulator and watch the boot log
   826→
   827→```bash
   828→# Start an x86_64 emulator (if not already running):
   829→sdkmanager "system-images;android-30;google_apis;x86_64"
   830→avdmanager create avd -n twoyi_x86_64 -k "system-images;android-30;google_apis;x86_64" -d pixel_5
   831→emulator -avd twoyi_x86_64 -no-window -no-audio &
   832→
   833→adb wait-for-device
   834→adb install -r -t /home/z/my-project/app/build/outputs/apk/release/*.apk
   835→adb shell am start -n io.twoyi/.ui.SettingsActivity
   836→
   837→# Watch for the boot progress:
   838→adb logcat -s CLIENT_EGL:V RomManager:V TwoyiApplication:V
   839→```
   840→
   841→Success criteria (in order of how far the boot gets):
   842→
   843→1. `RomManager: romExist=true` — twoyi found the new `init`.
   844→2. `CLIENT_EGL: [NEW_RENDERER] GL context created successfully` — host renderer up.
   845→3. `CLIENT_EGL: [NEW_RENDERER] Connected to /dev/qemu_pipe` — **the big one**. This
   846→   means your guest `init` ran and created the pipe. If you see this, you've solved
   847→   the blocker.
   848→4. `init: starting service 'surfaceflinger'...` — the guest's init is making progress.
   849→5. `TwoyiMessenger: BOOT_COMPLETED` — the guest's `system_server` is up.
   850→
   851→If you stop at step 2 with `Failed to write to pipe: Invalid argument`, the guest
   852→`init` either didn't run (re-check §3.8.1 / `file init`) or didn't create the pipe
   853→(re-check §3.4.1).
   854→
   855→### 5.4 `adb shell` into the guest (advanced)
   856→
   857→Twoyi runs `adbd` inside the guest on TCP 22122. The host app's `libadb.so` connects
   858→to it. From your host:
   859→
   860→```bash
   861→adb forward tcp:22122 tcp:22122
   862→adb -s localhost:22122 shell
   863→# You're now inside the guest. Sanity-check:
   864→getprop ro.product.cpu.abi      # should be x86_64
   865→uname -a                         # should show the host kernel
   866→ls /dev/qemu_pipe                # should exist
   867→```

   871→## 6. What modifications are needed — summary
   872→
   873→This is the consolidated list of every change you must make beyond a stock AOSP
   874→build. Each is referenced from the section where it's described in detail.
   875→
   876→| # | What | Where | Section |
   877→|---|---|---|---|
   878→| 1 | `init` creates `/dev/qemu_pipe` early in boot | `system/core/init/init.rc` + `twoyi_pipe_setup.cpp` | §3.4.1 |
   879→| 2 | SurfaceFlinger forces GL/emugl renderer, no HWC | `frameworks/native/services/surfaceflinger/SurfaceFlinger.cpp` or `system/build.prop` | §3.4.2 |
   880→| 3 | SELinux set to permissive (no kernel to enforce it) | `system/core/init/init.cpp` | §3.4.3 |
   881→| 4 | `ro.build.fingerprint` set at build time | `build/make/tools/buildinfo.sh` | §3.4.4 |
   882→| 5 | Custom twoyi `init` binary at rootfs root | new file `init` (compiled from `twoyi_init.c`) | §3.8.1 |
   883→| 6 | `rom.ini` metadata file | new file `rom.ini` | §3.8.2 |
   884→| 7 | Empty writable dirs: `data/`, `dev/`, `sdcard/`, `vendor/` | new directories | §3.8.3 |
   885→
   886→Additionally, the host-side `libOpenglRender_aosp.so` was already patched (in
   887→`AOSP_BUILD_RESULTS.md` §5.3) to bind the qemu_pipe socket at
   888→`$TWOYI_ROOTFS/opengles` — that's the *host*-side counterpart of modification #1.
   889→The two sides meet at the `/dev/qemu_pipe` socket path.
   890→
   891→For reference, Virtual Master's `libkr64.so` does all of the above (and much more)
   892→at runtime — see `download/VM_KR64_ANALYSIS.md` §4.2 for the full device inventory
   893→that `libkr64` materialises (binder, qemu_pipe, gb, gb2, touch, vmproc, ashmem,
   894→__properties__, netlink, kmsg, etc.). Twoyi's `kr64` Rust skeleton
   895→(`app/rs/kr64/`) covers the first 6 of those today; the rest are Roadmap items.

   928→## 8. Troubleshooting
   929→
   930→| Symptom | Cause | Fix |
   931→|---|---|---|
   932→| `make` fails with `unsupported reloc 256 against _GLOBAL_OFFSET_TABLE_` | Your host `gcc` is too new (Ubuntu 24.04 ships gcc-13; AOSP 8.1 expects gcc-9 or earlier). | Install an older GCC via `apt install gcc-9 g++-9` and `export HOST_CC=gcc-9 HOST_CXX=g++-9`. |
   933→| `make` fails with `Java version 17 found, expected 8` | OpenJDK 8 not on PATH. | `sudo apt install openjdk-8-jdk` then `export JAVA_HOME=/usr/lib/jvm/java-8-openjdk-amd64`. |
   934→| `make` dies with `ld: fatal error: out of memory` | The `libart.so` link step needs >12 GB RAM. | Add 16 GB swap (§3.6), or `export ART_BUILD_HOST_DEBUG=false` to skip debug symbols. |
   935→| `simg2img` not found | The `android-tools-fsutils` package isn't installed. | `sudo apt install android-tools-fsutils`. |
   936→| `repo init` fails with `fatal: manifest missing` | You didn't copy `default.xml` into `.repo/manifests/` (Option 1 in §3.2). | Follow Option 1's `mkdir -p .repo/manifests && cp ... .repo/manifests/twoyi.xml` step. |
   937→| Guest `init` runs but `/dev/qemu_pipe` never appears | The twoyi custom `init` (§3.8.1) didn't create it, and Patch 1 (§3.4.1) wasn't applied. | Apply Patch 1, OR have the host `libOpenglRender_aosp.so` create the socket itself (see note in §3.4.1). |
   938→| Guest boots to "Decrypting /data" and stalls | The GSI's `gatekeeperd` expects a real gatekeeper HAL. | Build from AOSP source (§3) instead of using a GSI; OR set `ro.crypto.state=unsupported` in `system/build.prop`. |
   939→| `adb -s localhost:22122` times out | The guest `adbd` didn't start, OR the host's `libadb.so` (closed-source) failed to connect. | Check `adb logcat \| grep -i adbd`; the closed-source `libadb.so` is Roadmap item #10 to replace. |
