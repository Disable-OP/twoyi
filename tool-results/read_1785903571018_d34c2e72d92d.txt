  1888→### Key findings
  1889→1. **Audio is a fixed-rate PCM pump, nothing fancier.** VM does zero compression, zero resampling, zero format negotiation. The wire protocol is just `{magic, direction, sample_rate, channels}` (16-byte header) followed by a raw byte stream. The 44 100/11 025 Hz hard-coding means twoyi's guest ROM **must** also expect those rates from its audio HAL module — if the GSI's `audio.primary.default.so` asks for 48 000 Hz, the host AudioTrack will still play it (Android resamples internally), but the guest's perception of its own sample rate will be wrong.
  1890→2. **AudioService and SensorService have different ownership patterns.** Audio is top-level (alongside Input/Display) because it has hard real-time requirements; Sensor is under `HALManager` because sensor events are bursty and low-rate. Twoyi should mirror this — `audio.rs` gets its own dedicated thread with no shared state, `sensors.rs` can share a dispatcher with future HALs.
  1891→3. **The sensor state machine is a 3-bit mask per index, not a boolean.** `SUPPORTED | ENABLED | ACTIVE` is needed because: a sensor may be supported by the host (bit 0 set) but not enabled by the guest (bit 1 clear); or enabled by the guest (bit 1 set) but not active because the VM is backgrounded (bit 2 clear). Twoyi's Rust dispatcher needs to track this same mask so it can correctly answer `CheckSensorsSupport` without actually registering a host listener.
  1892→4. **`nativeSensorChanged` is a down-call (Java→native), not an up-call.** The flow is: host `SensorManager` → Java `onSensorChanged` → `HALManager.SensorChanged` → `nativeSensorChanged(ptr, idx, ts, x, y, z)` (JNI) → Rust dispatcher pushes a 24-byte `SensorEvent` into a per-idx `mpsc::Sender` → pump thread drains it to the socket. The `EnableSensors`/`DisableSensors`/`CheckSensorsSupport`/`SetDelay` methods are up-calls (native→Java) — the guest triggers them via control messages on the socket.
  1893→5. **VM's `SetDelay` zeroes both the sampling period AND the max latency arrays.** This looks like a decompiler artifact but the bytecode matches. Twoyi should mirror this quirk for protocol compatibility, not "fix" it.
  1894→6. **No hidden-API bypass needed.** `AudioTrack`, `AudioRecord`, `SensorManager.registerListener`, `SensorEventListener.onSensorChanged` are all public API. The only manifest changes needed are `<uses-permission android:name="android.permission.RECORD_AUDIO" />` (for capture) and `<uses-permission android:name="android.permission.HIGH_SAMPLING_RATE_SENSORS" />` (API 31+, only for >200 Hz sensors).
  1895→7. **Latency budget for the user's rhythm game is the bottleneck.** VM uses `AudioTrack` in `MODE_STREAM` which gives ~125 ms host-side latency + ~80 ms guest AudioFlinger latency = ~200 ms total. For a rhythm game this is perceptible. The fix is `AudioTrack.Builder.setPerformanceMode(PERFORMANCE_MODE_LOW_LATENCY).setBufferSizeInFrames(192)` (API 26+) — drops to ~20 ms host-side. This is a Java-only change in `acquireAudioTrack`; the Rust pump doesn't care.
