   400→  │      │  AES algorithm = "AES" (Java default → AES/ECB/PKCS5Padding)
   401→  │      │  XOR uses the same 16-byte key (Vigenère-style, byte-wise)
   402→  │

   407→  │    else:
   408→  │       FileCopyUtils.copy(uri, out)           // HTTP download
   409→  │
   410→  │    extract: m5201WWWWoWWWWo(uri, cachePath, destDir, …):
   411→  │      │  queryParam = uri.getQueryParameter("m")
   412→  │      │  if "7z" AND Process.is64Bit():

   414→  │      │  else:

   443→## 5. IPC with the guest
   444→
   445→There are **three** IPC channels between host Java code and guest Android:
   446→
   447→### 5.1 Channel A — Unix domain socket (`/dev/event`)
   448→
   449→**Java side:** `com.android.vmcore.bridge.VMEventManager`
   450→
   451→In `m5115WWWWWWWW()` (called from `VMInstance.m5100WoWo` after the HAL services start), a background `Thread` is spawned that:
   452→
   453→1. Creates a `LocalServerSocket` bound to a filesystem path:
   454→   ```
   455→   <vMConfig.f8867WWWWWWWW>/dev/event
   456→   = /data/data/com.clone.android.dual.space/vm/vmN/dev/event
   457→   ```
   458→   (the literal suffix `/dev/event` is decoded from StringFog)
   459→2. Calls `accept()` in a loop until `f8990WWWoWWWo` (stop flag) is set or VM state goes to `-5`
   460→3. Wraps the accepted `LocalSocket`'s I/O streams in `DataInputStream` / `DataOutputStream`
   461→4. In a tight loop, calls `readUTF()` to read a single string per event, then splits it on the backtick separator `` ` `` (0x60):
   462→   ```
   463→   eventName`payload
   464→   ```
   465→   (e.g. `com.android.vmcore.action.BOOT_COMPLETED`)
   466→5. Dispatches each event to all registered `IVMEventCallback` instances — primary callback is `VMInstance.mo5013WWWWWWWW(eventName, payload)`.
   467→
   468→The event names (decoded from `com.android.vmcore.bridge.VMEvents` — there are ~25 of them):
   469→
   470→| Event name                                       | Direction       | Purpose                                           |
   471→|--------------------------------------------------|-----------------|---------------------------------------------------|
   472→| `com.android.vmcore.action.VM_SERVER_READY`      | guest → host    | Guest's IPC server is up                          |
   473→| `com.android.vmcore.action.ANDROID_OS_READY`     | guest → host    | OS is fully booted (post-zygote)                  |
   474→| `com.android.vmcore.action.BOOT_COMPLETED`       | guest → host    | sys.boot_completed=1 — sets VM state to 6         |
   475→| `com.android.vmcore.action.SHUTDOWN`             | guest → host    | Guest is shutting down — sets VM state to 7       |
   476→| `com.android.vmcore.action.SYNC_PROP_EVENT`      | bidirectional   | Set a System property in the guest                |
   477→| `com.android.vmcore.action.START_INSTALL_APP`    | host → guest    | Host asks guest to install an APK                 |
   478→| `com.android.vmcore.action.INSTALL_APP_RESULT`   | guest → host    | Guest reports install result                      |
   479→| `com.android.vmcore.action.START_UNINSTALL_APP`  | host → guest    | Host asks guest to uninstall an APK               |
   480→| `com.android.vmcore.action.UNINSTALL_APP_RESULT` | guest → host    | Guest reports uninstall result                    |
   481→| `com.android.vmcore.action.TASK_STACK_CHANGED`   | guest → host    | Guest's task stack changed (for recent tasks UI)  |
   482→| `com.android.vmcore.action.CLIPBOARD_DATA`       | bidirectional   | Clipboard sync between host and guest             |
   483→| `com.android.vmcore.action.OPEN_OUTER_PAGE`      | guest → host    | Guest requests opening a URL in host browser      |
   484→| `com.android.vmcore.action.TOGGLE_RECENTS`       | guest → host    | Guest requests recents panel                      |
   485→| `com.android.vmcore.action.SEND_KEY_EVENT`       | bidirectional   | Forward a KeyEvent                                |
   486→| `com.android.vmcore.action.SET_LOCALE_AND_TIME`  | host → guest    | Sync host locale/timezone to guest                |
   487→| `com.android.vmcore.action.SET_GLOBAL_SETTING`   | host → guest    | Set a `Settings.Global` value                     |
   488→| `com.android.vmcore.action.SHOW_NAVIGATION_EVENT`| guest → host    | Guest asks to show nav bar                        |
   489→| `com.android.vmcore.action.HIDE_NAVIGATION_EVENT`| guest → host    | Guest asks to hide nav bar                        |
   490→| `com.android.vmcore.action.SET_NAVIGATION_BAR_RTL`| host → guest   | Set nav bar RTL                                    |
   491→| `com.android.vmcore.action.KILL_APP`             | host → guest    | Kill a guest app by package name                  |
   492→| `com.android.vmcore.action.EXPAND_NOTIFICATIONS_PANEL`  | guest → host | Guest wants notification shade             |
   493→| `com.android.vmcore.action.COLLAPSE_NOTIFICATIONS_PANEL`| guest → host | Guest wants notification shade closed      |
   494→| `com.android.vmcore.action.EXECUTE_COMMAND`      | host → guest    | Execute a shell command in the guest              |
   495→
   496→The send side is `VMEventManager.m5116WWWoWWWo(eventName, payload)` which does `writeUTF(eventName + "`" + payload); flush()`.
   497→
   498→### 5.2 Channel B — Binder virtualization (`/vm%d/dev/binder`)
   499→
   500→**Java side:** `com.android.vmcore.service.BinderService`
   501→
   502→This is the most subtle channel. The guest Android's `servicemanager` needs to register with `android.os.ServiceManager` to find system services (`activity`, `package`, `window`, etc.). Virtual Master can't let the guest talk to the host's real `/dev/binder` (it would corrupt the host), so it creates a **per-VM virtual binder** at `/vm%d/dev/binder`.
   503→
   504→The setup is in `BinderService.m5206WWWWoWWWWo(vMApp, vmId)`:
   505→
   506→1. **Reflect into ActivityManager** (`m5207WWWWWWWW(vMApp)`):
   507→   - On API 26+: get the `IActivityTaskManager` interface, call `getID()` on it, then `mActivityTaskManager.getConfiguration()` etc. (this is the hidden-API path that the `me.weishu.reflection` bypass enables)
   508→   - On older APIs: get the legacy `IActivityManager` similarly
   509→   - Get a handle to the system `IBinder` for `android.app.IActivityManager`
   510→2. **Wrap the IBinder with a Java `Proxy`** that intercepts `transact()` calls. The proxy checks the calling thread ID; when the wrapped `transact()` is called from the same thread that called `peekService()` (in step 4), the proxy captures the integer return code into `iArr[0]`.
   511→3. **Install the proxy back** via reflection on `ActivityManager.IActivityTaskManager` (replacing the system's `IActivityTaskManager` field with the proxied one).
   512→4. **Call `peekService(vMApp, new Intent())`** — this triggers the proxy. The captured integer is the system's binder version.
   513→5. **Call native `setupBinder(vmId, binderVersion, 1, 2, "com.android.vmcore.service.IBinderService", parcelledIntent)`** — this is the JNI call into libvm.so that:
   514→   - Creates `/vm%d/dev/binder` (the per-VM virtual binder device, matches disassembly)
   515→   - Sets up a binder-redirect mapping so the guest's `servicemanager` calls for `activity`/`package`/`window`/etc. are proxied back to the host's `BinderService.f9244WWWWoWWWWo` (the `IBinderService.Stub` instance) — which the host then fulfills (or passes through to the real system service with the host's identity)
   516→6. **`bindService(Intent(BinderService.class), serviceConnection, BIND_AUTO_CREATE)`** — waits up to 5 seconds for `onServiceConnected`, returns `-502` on timeout.
   517→
   518→The `IBinderService` AIDL (in `com.android.vmcore.service.IBinderService` interface) is just a stub:
   519→
   520→```java
   521→public interface IBinderService extends IInterface {
   522→    abstract class Stub extends Binder implements IBinderService { … }
   523→}
   524→```
   525→
   526→So the guest makes a binder transaction → libvm.so's virtual binder intercepts it → routes it to the host's `BinderService` (the Java service) → the host fulfills it. This is how the guest's `Context.startActivity()` ends up calling host `VMDisplayActivity.onDialNumberEvent()` for example.
   527→
   528→### 5.3 Channel C — `/dev/qemu_pipe` (GL transport)
   529→
   530→**Java side:** none (entirely in native).
   531→
   532→The guest's SurfaceFlinger speaks the emugl `qemu_pipe` protocol to ship GL commands to the host's `libvm.so`, which has its own EGL context created on the `Surface` we passed in via `nativeAddSurface(...)`. This is the same mechanism as twoyi (see `VIRTUAL_MASTER_FULL_ANALYSIS.md`). There is no Java code involved.
   533→
   534→### 5.4 Other HAL services (each is a `LocalSocket`-or-virtual-dev bridge)
   535→
   536→`com.android.vmcore.hal.HALManager` is created per-VM in `VMInstance.m5100WoWo()`:
   537→
   538→```java
   539→this.f8933WWWWWWWW = new HALManager(vMApp, vMInstance);
   540→this.f8933WWWWWWWW.startHALMgr();
   541→```
   542→
   543→Inside, `HALManager.nativeSetup(vmId)` returns a `long` pointer to a native HAL dispatcher. The dispatcher then calls back into Java via private methods (named `CameraConnect`, `CameraDisconnect`, `CameraStart`, `CameraStop`, `CameraFocus`, `CameraFrame`, `CameraFlash`, `CameraList`, `EnableSensors`, `DisableSensors`, `CheckSensorsSupport`, `ExecPhoneCommand`, `SetLocation`, `GetWifiScanResults`, `SetWifiEnabled`, …). These JNI callbacks let the guest access host hardware (camera, sensors, GPS, WiFi scan, phone state, battery) as if it were native.
   544→
   545→The full HAL composition:
   546→
   547→| HAL Service           | Java Class                                | What it does                                                          |
   548→|-----------------------|-------------------------------------------|-----------------------------------------------------------------------|
   549→| Display               | `DisplayService`                          | Surface registration (see §3)                                         |
   550→| Input (touch)         | `InputService`                            | Touch event forwarding                                                |
   551→| Audio                 | `AudioService`                            | Audio capture/playback (via `AudioRecord` / `AudioTrack`)             |
   552→| Camera                | `CameraService` (in HALManager)           | Camera1 API proxy (open/start/stop/focus/zoom)                        |
   553→| Sensor                | `SensorService` (in HALManager)           | 12 sensor types (accel/gyro/mag/…) via `SensorManager`                |
   554→| Location              | `LocationService`                         | GPS pass-through + fake-location support                              |
   555→| WiFi scan             | `WiFiService`                             | `WifiManager.getScanResults()` proxy                                  |
   556→| Phone                 | `PhoneService`                            | SIM state, signal strength, SMS, dial (via `TelephonyManager`)        |
   557→| Battery               | `BatteryService`                          | Battery level/charging state (via `ACTION_BATTERY_CHANGED` receiver)  |
   558→| Network               | `NetlinkManager`                          | Virtual network interface (`tun0`) with MAC/IP/gateway/DNS             |
   559→| HW control            | `HWControlService`                        | Hardware buttons (power/volume)                                       |

   705→## 7. Differences from twoyi
   706→
   707→This section is the most important for the twoyi project. Here are the architectural choices Virtual Master made that twoyi did (or didn't):
   708→
   709→| Aspect                          | Twoyi (current)                          | Virtual Master                                                  |
   710→|---------------------------------|------------------------------------------|------------------------------------------------------------------|
   711→| **Native library**              | `libvm.so` + `libOpenglRender.so` + `libloader.so` (3 libs) | Single `libvm.so` (all-in-one)                                  |
   712→| **Application class**           | `io.twoyi.TwoyiApplication`              | `com.android.vmapp.VMApp` (with reflection bypass + Firebase)   |
   713→| **Display activity**            | `io.twoyi.Render2Activity`               | `com.android.vmapp.vm.VMDisplayActivity`                        |
   714→| **Boot progress UI**            | `BootLogTexture` (TextureView overlay)   | `VMStartActivity0..3` (Lottie animation + status text)           |
   715→| **Surface type**                | `TextureView` (originally) / SurfaceView (new) | `SurfaceView` (wrapped in `VMSurfaceView extends FrameLayout`) |
   716→| **Surface→native API**          | AOSP emugl `initOpenGLRenderer()` + `createOpenGLSubwindow()` (global singleton) | **Custom per-VM `DisplayService.nativeAddSurface(ptr, surfaceId, surface, w, h, rot)`** |
   717→| **Multi-VM support**            | No (single VM)                           | **Yes** — up to 4 concurrent VMs (VMStartActivity0..3, taskAffinity `.vm0..3`) |
   718→| **State machine**               | Implicit (boot log lines)                | **Explicit**: 11 states (-5..7) with EventBus events            |
   719→| **Touch input**                 | Unix socket `/dev/input/touch`           | Same path; Java side: `InputService.nativeOnTouchEvent`         |

   737→### 7.1 Key takeaways for twoyi
   738→
   739→1. **Per-VM renderer pointer.** Virtual Master's `DisplayService.nativeSetup(vmId, dpi)` returns a `long` that's then passed to every subsequent `nativeAddSurface`/`nativeRemoveSurface`/`nativeStartService` call. This is a much cleaner API than twoyi's global-singleton emugl. **Recommendation: refactor twoyi's `libOpenglRender` to take a per-instance handle.**
   740→
   741→2. **Surface-passing is explicit, not via NativeActivity.** Virtual Master shows you don't need `NativeActivity` — just implement `SurfaceHolder.Callback` and call a custom `nativeAddSurface(surface, w, h, rotation)` from `surfaceCreated`. **Recommendation: adopt this pattern in twoyi — it's simpler and supports multiple surfaces.**
   742→
   743→3. **The boot state machine matters.** Twoyi currently uses an implicit boot log (line-by-line text). Virtual Master's 11-state explicit machine with EventBus events gives the UI much better feedback ("Installing…", "Fixing FS…", "Starting services…", "OS booting…", "OS ready"). **Recommendation: add a state enum to `TwoyiStatusManager` and emit status events.**
   744→
   745→4. **Binder virtualization is the hardest piece.** Virtual Master has it, twoyi doesn't. The Java side is small (`BinderService` ~400 lines) but the native `setupBinder()` JNI is significant — it creates a per-VM `/vm%d/dev/binder` and routes the guest's `servicemanager` calls back to the host. Without this, the guest's `servicemanager` would either fail to start or talk to the host's servicemanager (which is what twoyi does, with limitations — the guest's `getSystemService(ACTIVITY_SERVICE)` returns the *host's* ActivityManager, which is why twoyi's guest can launch host apps but not its own).
   746→
   747→5. **ROM download + on-the-fly AES decryption is elegant.** The `CipherOutputStream` wraps `FileOutputStream`, so the cleartext ROM never touches disk during download. **Recommendation: consider this for twoyi if we ever distribute ROMs server-side.**
   748→
   749→6. **Multi-VM support is straightforward.** Per-VM data dir (`vm/vmN/fs`), per-VM SharedPreferences (`vm_config_N.xml`), per-VM task affinity, per-VM renderer pointer. **Recommendation: adopt this directory layout in twoyi for future multi-VM support.**
   750→
   751→7. **The ROM catalog + `pad://` URI scheme.** Virtual Master separates the *logical* ROM ID (`pad://rom_7_1_2`) from the *physical* download URL (resolved via API call). This lets them swap mirrors without changing the app. **Recommendation: not urgent for twoyi (we bundle the ROM), but useful if we ever ship a "ROM store".**
