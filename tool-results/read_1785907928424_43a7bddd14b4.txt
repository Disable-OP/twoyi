   300→   300→
   301→   301→From `VM_JAVA_ANALYSIS.md` §2.3 (startup pipeline) and `VM_ROM_ANALYSIS.md` §4.3:
   302→   302→
   303→   303→Eight `BugNFixTask` classes (`com.android.vmcore.startup.Bug1FixTask` … `Bug8FixTask`) apply ROM-version-specific patches to the extracted filesystem before boot. The pipeline (state 4) is:
   304→   304→
   305→   305→```
   306→   306→ApplyOverlaysTask → Bug1FixTask → … → Bug8FixTask → CleanLogTask →
   307→   307→SuperuserTask → XposedTask → GooglePlayTask → MagiskTask →
   308→   308→BuildTmpfsTask → BuildVMPropTask → BuildExecPathTask
   309→   309→```
   310→   310→
   311→   311→Notable patches inferred from path constants decoded in `VM_ROM_ANALYSIS.md` §4:
   312→   312→- **`app_process32`/`app_process64` shims** — rewrite the symlinks at `/system/bin/app_process32`, `/system/bin/app_process32_xposed`, `/system/bin/app_process64`, `/system/bin/app_process64_xposed` so they point at the host's `app_process` binary (avoiding the need to ship a full ART runtime).
   313→   313→- **`libui.so` ABI selection** — replace `/system/lib/libui.so` with `libui10.so` (Android 10 variant), `libui51.so` (Android 5.1), or `libhostlibui.so`/`libhostlibui_10.so` (the host-aware shim) depending on ROM version.
   314→   314→- **`build.prop` patching** — `BuildVMPropTask` writes `/system/build.prop` with the host's actual build fingerprint, `Build.ID`, and a synthetic kernel version. This makes `Build.FINGERPRINT` inside the guest match the host (required by SafetyNet / Play Integrity basic attestation).
   315→   315→- **`init.rc` patching** — `MagiskTask` injects magisk service entries into `/system/etc/init/hw/init.rc`. The same mechanism is presumably used to inject the `libkr64.so` LD_PRELOAD.
   316→   316→- **`PATH` and exec dirs** — `BuildExecPathTask` sets the guest's `PATH` to include `/system/bin:/system/xbin:/system/sbin:/vendor/bin:/system/apex/com.android.runtime/bin`.

   320→   320→## 3. What twoyi needs to boot GSIs (concrete implementation plan)
   321→   321→
   322→   322→This is the actionable section. Each subsection has: (a) what VM does, (b) what twoyi currently does, (c) what to build, (d) which files to create or modify, (e) acceptance criteria.

   324→   324→### 3.1 Kernel replacement daemon (the big one)
   325→   325→
   326→   326→**What VM does.** `libkr64.11.so` (2.0 MB) runs as a separate process via `libkrloader64.so` and creates 20+ virtual devices via `mknodat` + `bind` (see §2.4).
   327→   327→
   328→   328→**What twoyi currently does.** No kernel replacement. Touch input is `app/rs/src/input.rs` — creates `/dev/input/touch` and `/dev/input/key0` as plain AF_UNIX sockets in the rootfs.    329→   329→
   330→   330→**What to build.** A new Rust crate `app/rs/kr64/` that produces a PIE executable `libkr64.so` (mirroring VM's name). It will:
   331→   331→1. Be launched as a separate process by `core.rs` (currently `core.rs` does `Command::new("./init").spawn()` — change to `Command::new("./libkr64.so").arg(vmId).arg(dataDir).arg(romDir).arg(kernelPath).arg(configPath).arg(logLevel).arg(socketFd).spawn()` first, then have `libkr64.so` itself fork+exec `./init` with `LD_PRELOAD=libkr64.so`).
   332→   332→2. Use the existing PIE pattern from `app/rs/src/interp.c` and `app/rs/.cargo/config.toml` — copy them into `app/rs/kr64/`.
   333→   333→3. Create all 20+ devices listed in §2.4 table.
   334→   334→4. Install the seccomp filter (§3.4).
   335→   335→5. Install the `/proc` emulator (§3.5).
   336→   336→6. Install the shadowhook-equivalent (§3.6) — at minimum hook `open`/`openat` and `mount`.
   337→   337→

   361→   361→### 3.2 Binder virtualisation (the hard one)
   362→   362→
   363→   363→**What VM does.** `libvm.so` (in the Java app process) creates `/vm%d/dev/binder` via the `setupBinder()` JNI, and the Java `BinderService` wraps the host's `IActivityManager` with a `java.lang.reflect.Proxy` so the guest's `servicemanager` lookups are proxied back into the host app (see §2.5).
   364→   364→
   365→   365→**What twoyi currently does.** Uses the host's `/dev/binder` directly. The guest's `servicemanager` registers with the host's `servicemanager`. This means the guest's `getSystemService(ACTIVITY_SERVICE)` returns the *host's* ActivityManager — the guest can launch host apps but not its own. This is why twoyi can't have its own package manager.
   366→   366→
   367→   367→**What to build.** Two pieces:
   368→   368→
   369→   369→**(a) Native binder proxy in Rust** — `app/rs/kr64/src/binder_proxy.rs`:
   370→   370→- Open `/dev/binder` on the host side.
   371→   371→- Create `/vm%d/dev/binder` as a char device via `mknodat(S_IFCHR, …)`.
   372→   372→- Accept `BINDER_WRITE_READ` / `BINDER_VERSION` / `BINDER_SET_MAX_THREADS` ioctls from the guest.
   373→   373→- Parse the binder transaction header.
   374→   374→- For transactions targeting `android.app.IActivityManager` / `android.app.IActivityTaskManager` / `android.content.pm.IPackageManager` / `android.view.IWindowManager` — route them to the Java side via the event socket.
   375→   375→- For transactions targeting `android.os.IServiceManager` — synthesise responses (return a fake service handle for each well-known service name).
   376→   376→- For all other transactions — proxy directly to the host binder.
   377→   377→
   378→   378→**(b) Java-side binder service** — `app/src/main/java/io/twoyi/service/BinderService.java`:
   379→   379→- Copy VM's `BinderService.m5206WWWWoWWWWo` structure (see §2.5).
   380→   380→- Reflect into `ActivityManager` to get the system `IActivityManager` IBinder.
   381→   381→- Wrap with a `Proxy`.
   382→   382→- Add a `setupBinder()` JNI that calls into `libkr64.so`.
   383→   383→- Implement `IBinderService.Stub` with the AIDL interface `io.twoyi.service.IBinderService`.
   384→   384→
   385→   385→**Files to create.**
   386→   386→- `app/src/main/java/io/twoyi/service/BinderService.java`
   387→   387→- `app/src/main/java/io/twoyi/service/IBinderService.aidl` — AIDL stub (interface descriptor `"io.twoyi.service.IBinderService"`).
   388→   388→- `app/src/main/java/io/twoyi/FreeReflection.java` — copy the FreeReflection trick (or use ` Reflection_exemptAll` from `me.weishu.reflection.BootstrapClass` — bundle the dex).
   389→   389→- `app/rs/kr64/src/binder_proxy.rs` (above).
   390→   390→
   391→   391→**Files to modify.**
   392→   392→- `app/src/main/java/io/twoyi/TwoyiApplication.java` — add `FreeReflection.exemptAll()` in `attachBaseContext` (currently twoyi doesn't do this — VM does).
   393→   393→- `app/src/main/java/io/twoyi/utils/RomManager.java` — add a `setupBinder()` call in `ensureBootFiles()` (currently only kills orphans, etc.).
   394→   394→
   395→   395→**Acceptance criteria.**
   396→   396→- After boot, `adb shell service list` inside the guest shows `android.app.IActivityManager: […]` resolving to the twoyi proxy, not the host's.
   397→   397→- `adb shell am start -n com.android.settings/.Settings` inside the guest starts the guest's Settings, not the host's.
   398→   398→- `adb shell pm list packages` inside the guest lists only guest-installed packages, not the host's.
   399→   399→
   400→   400→**MVP skip.** If implementing full binder virtualisation is too much, an initial GSI boot can run with the host's binder shared (as today). The guest will boot but every `getSystemService()` call returns host services — so the guest's `system_server` won't be able to register itself. This will likely crash early. Recommend implementing at least the `IActivityManager` and `IPackageManager` proxies as the minimum.

   402→   402→### 3.3 Graphics buffer management (`/dev/gb` and `/dev/gb2`)
   403→   403→
   404→   404→**What VM does.** `libkr64.11.so` (A 11 only) creates `/dev/gb` and `/dev/gb2` as char devices (via `mknodat S_IFCHR` at `0x11d770`, decoded with keys 0xe0 and 0x0c). These expose a `gralloc`-like ioctl interface for allocating graphics buffers. The guest's `surfaceflinger` calls these ioctls to allocate buffers for compositing; the host returns a buffer handle that maps to either an ashmem region or a host `AHardwareBuffer`.
   405→   405→
   406→   406→The presence of two devices (`gb` + `gb2`) suggests:
   407→   407→- `/dev/gb` is the **framework gralloc** (used by surfaceflinger, accessed via `/dev/binder`).
   408→   408→- `/dev/gb2` is the **vendor gralloc** (used by HALs, accessed via `/dev/vndbinder`).
   409→   409→
   410→   410→This split matches Android 11's gralloc HAL layout where `android.hardware.graphics.allocator@4.0` (framework) and `android.hardware.graphics.allocator-V1-ndk` (vendor) are separate services.
   411→   411→
   412→   412→**What twoyi currently does.** No gralloc emulation. The `libOpenglRender_aosp.so` (the rebuilt AOSP emugl renderer at `/home/z/my-project/app/src/main/jniLibs/x86_64/libOpenglRender_aosp.so`) implements its own buffer management via the `ColorBuffer` class in `app/rs/openglrenderer/src/gralloc.rs`. The guest's SurfaceFlinger has no gralloc HAL, so it crashes on the first composite.
   413→   413→
   414→   414→**What to build.** `app/rs/kr64/src/gb.rs`:
   415→   415→- Create `/dev/gb` and `/dev/gb2` as char devices.
   416→   416→- Implement these ioctls (the exact numbers can be inferred from `android.hardware.graphics.allocator@4.0` HAL header in AOSP `hardware/interfaces/graphics/allocator/4.0/IAllocator.hal`):
   417→   417→  - `ALLOCATE` — allocate a buffer of given width/height/format/usage. Return a buffer handle that's a host `AHardwareBuffer` (we already have these via `libEGL.so`).
   418→   418→  - `DUMP_DEBUG_INFO` — return a fake debug string.
   419→   419→  - `GET_ALL_ALLOCATOR_FUNCTIONS` — return function pointers for the gralloc module.
   420→   420→
   421→   421→For the MVP, we can route gralloc allocation through the existing `libOpenglRender_aosp.so` ColorBuffer infrastructure — each guest gralloc allocation creates a host-side `ColorBuffer` and returns its ID as the buffer handle.
   422→   422→
   423→   423→**Files to create.**
   424→   424→- `app/rs/kr64/src/gb.rs` — char device + ioctls.
   425→   425→- `app/rs/openglrenderer/src/gralloc.rs` — already has `ColorBuffer`; add a `from_guest_handle(u64) -> ColorBuffer` lookup.
   426→   426→
   427→   427→**Files to modify.**
   428→   428→- `app/rs/kr64/src/devices.rs` — register `/dev/gb` and `/dev/gb2`.
   429→   429→
   430→   430→**Acceptance criteria.**
   431→   431→- After boot, `adb shell dumpsys SurfaceFlinger` inside the guest shows a non-zero buffer count.
   432→   432→- The guest's launcher renders its first frame (visible via the Surface registered through `nativeAddSurface`).

   434→   434→### 3.4 Seccomp filter
   435→   435→
   436→   436→**What VM does.** Installs a `SECCOMP_SET_MODE_FILTER` BPF program with a SIGSYS handler that emulates blocked syscalls (see §2.7).
   437→   437→
   438→   438→**What twoyi currently does.** No seccomp. The guest can call any syscall the host kernel allows. This is unsafe and also means the guest sees the host's `/proc`, `/sys`, etc. (no isolation).
   439→   439→
   440→   440→**What to build.** `app/rs/kr64/src/seccomp.rs`:
   441→   441→
   442→   442→1. **Allowlist of syscalls** — start from Android's own seccomp policy (in AOSP at `system/seccomp/policy.txt`). For twoyi we need to also allow the syscalls that `libkr64.so` intercepts (so they trap to our SIGSYS handler).
   443→   443→
   444→   444→2. **Blocklist (trap-to-SIGSYS)** — these syscalls are blocked and emulated:
   445→   445→   - `open`/`openat` for `/proc/…`, `/sys/…`, `/dev/…` paths (intercepted by the proc emulator)
   446→   446→   - `mount`/`umount`/`umount2` (intercepted by the mount_mgr)
   447→   447→   - `pivot_root`/`chroot` (intercepted to redirect to the per-VM rootfs)
   448→   448→   - `reboot` (intercepted to send a shutdown event)
   449→   449→   - `swapon`/`swapoff` (intercepted to be no-ops)
   450→   450→   - `acct` (intercepted to be a no-op)
   451→   451→   - `sethostname`/`setsid` (intercepted for the per-VM hostname)
   452→   452→
   453→   453→3. **SIGSYS handler** — `sigaction(SIGSYS, …)`:
   454→   454→   - Read the syscall number from `ucontext->uc_mcontext`.
   455→   455→   - Log `BLOCKED.SYSCALL.FAILED: <nr>`.
   456→   456→   - Dispatch to the appropriate emulator function.
   457→   457→   - Set the return value in `ucontext->uc_mcontext.regs[0]`.
   458→   458→   - Increment the instruction pointer past the syscall instruction.
   459→   459→   - Return.
   460→   460→
   461→   461→**Files to create.**
   462→   462→- `app/rs/kr64/src/seccomp.rs`
   463→   463→- `app/rs/kr64/src/bpf_filter.rs` — the compiled BPF program (generate with `libseccomp` or hand-write).
   464→   464→
   465→   465→**Files to modify.**
   466→   466→- `app/rs/kr64/src/main.rs` — call `seccomp::init()` after all devices are created and before `fork`+`exec` of the guest `init`.
   467→   467→
   468→   468→**Acceptance criteria.**
   469→   469→- After boot, `adb shell cat /proc/self/status` inside the guest returns a synthesised status (not the host's).
   470→   470→- After boot, `adb shell mount` inside the guest shows only guest mounts.
   471→   471→- After boot, `adb shell reboot` inside the guest sends a shutdown event (doesn't actually reboot the host).
   472→   472→
   473→   473→### 3.5 `/proc` emulator
   474→   474→
   475→   475→**What VM does.** Intercepts `open("/proc/…")` and synthesises content (see §2.8).
   476→   476→
   477→   477→**What twoyi currently does.** Uses the host's `/proc`. The guest sees the host's process list, mounts, cmdline, version — which breaks the guest's `init` (it expects `androidboot.hardware=…` on the cmdline) and leaks host info.
   478→   478→
   479→   479→**What to build.** `app/rs/kr64/src/proc_emu.rs`:
   480→   480→
   481→   481→- Create `/dev/vmproc` as a char device (per VM's design).
   482→   482→- Hook `open`/`openat` via shadowhook (or via the seccomp SIGSYS trap — see §3.4).
   483→   483→- When the path matches `/proc/…`, redirect to `/dev/vmproc` + an ioctl that selects the virtual file.
   484→   484→- Implement these synthesised files (per §2.8 table):
   485→   485→  - `/proc/cmdline` — `androidboot.hardware=twoyi androidboot.bootdevice=/dev/block/vdc androidboot.serialno=…`
   486→   486→  - `/proc/version` — `Linux version 4.14.x-perf-g… (build@host) …` (match what the GSI expects)
   487→   487→  - `/proc/self/maps` — filtered host maps (only show guest-mapped regions)
   488→   488→  - `/proc/self/status` — synthesised with the guest's PID/UID/GID
   489→   489→  - `/proc/self/mounts` — only guest mounts
   490→   490→  - `/proc/self/exe` — symlink to `/system/bin/init` (the guest's init, not the host's)
   491→   491→  - `/proc/net/if_inet6/` — based on `NetlinkManager`'s virtual interfaces
   492→   492→  - `/proc/sys/kernel/kptr_restrict` — `1`
   493→   493→  - `/proc/sys/vm/mmap_rnd_bits` — `16`
   494→   494→
   495→   495→**Files to create.**
   496→   496→- `app/rs/kr64/src/proc_emu.rs`
   497→   497→
   498→   498→**Files to modify.**
   499→   499→- `app/rs/kr64/src/devices.rs` — register `/dev/vmproc`.
   500→   500→- `app/rs/kr64/src/seccomp.rs` — add `open`/`openat` to the trap list (or use shadowhook instead).
   501→   501→
   502→   502→**Acceptance criteria.**
   503→   503→- After boot, `adb shell cat /proc/cmdline` inside the guest returns the synthesised cmdline.
   504→   504→- After boot, `adb shell cat /proc/version` inside the guest returns a Linux version string matching the GSI's expected kernel.
   505→   505→- The guest's `init` doesn't crash on `open("/proc/cmdline")`.
   506→   506→
   507→   507→### 3.6 Inline hooking (shadowhook equivalent)
   508→   508→
   509→   509→**What VM does.** Embeds `shadowhook v1.0.8` (ByteDance's inline hook library) — hooks the dynamic linker's `do_dlopen` so guest `dlopen` calls can be redirected (see `VM_KR64_ANALYSIS.md` §4.1).
   510→   510→
   511→   511→**What twoyi currently does.** No hooking. The guest's `dlopen` calls go to the system linker, which loads from `/system/lib64/` (the host's system).
   512→   512→
   513→   513→**What to build.** Two options:
   514→   514→
   515→   515→**(a) Use shadowhook directly** — there's a Rust binding `shadowhook-sys` (https://crates.io/crates/shadowhook-sys). Add it to `app/rs/kr64/Cargo.toml`. Hook:
   516→   516→- `do_dlopen` in the linker (so guest `dlopen` loads from the per-VM rootfs).
   517→   517→- `open`/`openat` in libc (for `/proc` emulation).
   518→   518→- `mount`/`umount` (for the mount_mgr).
   519→   519→- `__system_property_get` (for property emulation).
   520→   520→
   521→   521→**(b) Use LD_PRELOAD** — simpler, less invasive. Set `LD_PRELOAD=libkr64.so` when exec'ing the guest. Override the libc functions in `libkr64.so` itself. This is what VM probably does for some hooks (shadowhook is for hooks they can't override via LD_PRELOAD because the function is already loaded).
   522→   522→
   523→   523→Recommend (b) for the MVP — it's simpler and works for all the hooks we need.
   524→   524→
   525→   525→**Files to create.**
   526→   526→- `app/rs/kr64/src/hooks.rs` — LD_PRELOAD overrides for `open`, `openat`, `mount`, `umount`, `__system_property_get`, `dlopen`.
   527→   527→
   528→   528→**Files to modify.**
   529→   529→- `app/rs/kr64/src/main.rs` — set `LD_PRELOAD=libkr64.so` in the env before `execve("./init")`.
   530→   530→
   531→   531→**Acceptance criteria.**
   532→   532→- After boot, `adb shell ls /system/lib64/` inside the guest shows the guest's libraries (not the host's).
   533→   533→- After boot, `adb shell getprop ro.build.fingerprint` returns the guest's fingerprint.
   534→   534→
   535→   535→### 3.7 ROM extraction (GSI-aware)
   536→   536→
   537→   537→**What VM does.** Downloads `rom.zip` (a ZIP), decrypts with AES-128-ECB, extracts via ZIP or 7-Zip into `<vmDataDir>/fs/` (see §2.2). The extracted tree is already flattened (e.g. `/system/product/...` is a directory inside `/system/`, not a separate mount).
   538→   538→
   539→   539→**What twoyi currently does.** `RomManager.java` extracts a pre-built `rootfs.7z` (Android 8.1 only) into `/data/data/io.twoyi/rootfs/`. The format is a flat directory tree, not a multi-partition GSI.
   540→   540→
   541→   541→**What to build.** `app/src/main/java/io/twoyi/utils/GsiExtractor.java`:
   542→   542→
   543→   543→1. **Input**: a GSI `system.img` (ext4 or sparse-ext4) + optionally `product.img`, `system_ext.img`, `boot.img` (for the ramdisk).
   544→   544→2. **Extract `system.img`**:
   545→   545→   - If sparse: `simg2img system.img system.raw.img` (use the `libsparse` Rust crate or shell out to `simg2img`).
   546→   546→   - If ext4: mount via `fuse2fs` (no root needed) or extract via `rust-ext4` crate (https://crates.io/crates/ext4).
   547→   547→   - Walk the filesystem and copy files into `<vmDataDir>/fs/system/`.
   548→   548→3. **Extract `product.img`** (if present) → `<vmDataDir>/fs/system/product/` (note: Treble flattens product under system on the device).
   549→   549→4. **Extract `system_ext.img`** (if present) → `<vmDataDir>/fs/system/system_ext/`.
   550→   550→5. **Extract `boot.img`** ramdisk (if present):
   551→   551→   - `boot.img` = header + kernel + ramdisk (gzip/lz4) + second stage.
   552→   552→   - Use the `bootimage` Rust crate to parse.
   553→   553→   - Extract the ramdisk and unpack with `cpio -idmv` (shell out).
   554→   554→   - Place into `<vmDataDir>/fs/ramdisk/`.
   555→   555→6. **Synthesise a minimal `vendor.img`** if the user didn't supply one:
   556→   556→   - Pre-built at `app/src/main/assets/vendor.img` — contains stub HALs for `vibrator`, `graphics.allocator`, `graphics.mapper`, `graphics.composer`, `audio`, `camera`, `sensors`, `gatekeeper`, `keymaster`, `health`, `power`.
   557→   557→   - Each HAL is a tiny binary that returns success for all calls.
   558→   558→   - Extract into `<vmDataDir>/fs/vendor/`.
   559→   559→7. **Apply init patches**:

   578→   578→### 3.8 Init configuration
   579→   579→
   580→   580→**What VM does.** Eight `BugNFixTask` classes patch the extracted filesystem (see §2.9). Notably:
   581→   581→- `BuildVMPropTask` rewrites `/system/build.prop` with the host's build fingerprint.
   582→   582→- `MagiskTask` patches `/system/etc/init/hw/init.rc` to inject magisk service entries.
   583→   583→- `FixCPUArchTask` rewrites `app_process32`/`app_process64` symlinks.
   584→   584→- `BuildTmpfsTask` mounts tmpfs on `/tmp`, `/dev`, etc.
   585→   585→
   586→   586→**What twoyi currently does.** Patches `services.jar` for the `PackageInstallerSession` bug (`patchServicesJarForPackageInstaller`). No other init patches.
   587→   587→
   588→   588→**What to build.** A `GsiInitPatcher` Java class that applies these patches to the extracted GSI:
   589→   589→
   590→   590→1. **`/system/build.prop`** — overwrite these properties:
   591→   591→   - `ro.build.fingerprint` — set to the host's `Build.FINGERPRINT` (so Play Integrity basic attestation passes).
   592→   592→   - `ro.build.id` — set to the host's `Build.ID`.
   593→   593→   - `ro.build.version.incremental` — set to the host's `Build.VERSION.INCREMENTAL`.
   594→   594→   - `ro.product.cpu.abi` — set to the host's primary ABI (`x86_64` or `arm64-v8a`).
   595→   595→   - `ro.hardware` — set to `twoyi` (matches what `/proc/cmdline` returns).
   596→   596→2. **`/system/etc/init/hw/init.rc`** — apply these patches:
   597→   597→   - Remove all `mount ext4 …` and `mount f2fs …` lines (the filesystems are already mounted by libkr64).
   598→   598→   - Remove the `service flash_recovery` block (no recovery partition).
   599→   599→   - Add `setenv LD_PRELOAD /system/lib64/libkr64.so` to the `service zygote` block.
   600→   600→   - Add a new `service twoyi_event /system/bin/twoyi_event` that connects to the host's event socket and signals `BOOT_COMPLETED`.
   601→   601→3. **`/vendor/etc/init/*.rc`** — remove all `service` blocks that start HALs we don't implement (camera HAL, sensors HAL if not proxying). Replace with stub services that exit 0 immediately.
   602→   602→4. **`/system/bin/app_process64`** — replace with a wrapper script that execs the host's `app_process64` with `LD_PRELOAD` set:
   603→   603→   ```sh
   604→   604→   #!/system/bin/sh
   605→   605→   exec /system/bin/linker64 /system/lib64/libkr64.so --preload /system/bin/app_process64_real "$@"
   606→   606→   ```
   607→   607→   (Or better — keep the original `app_process64` binary from the GSI, but preload `libkr64.so` via `LD_PRELOAD` in the zygote service in init.rc.)
   608→   608→5. **`/system/etc/prop.default`** — apply the same patches as `/system/build.prop`.
   609→   609→6. **`/vendor/build.prop`** — set `ro.vendor.build.fingerprint` to match.
   610→   610→
   611→   611→**Files to create.**
   612→   612→- `app/src/main/java/io/twoyi/utils/GsiInitPatcher.java` — implements the above patches.
   613→   613→- `app/src/main/java/io/twoyi/utils/setup/` — port VM's `Bug1FixTask` … `Bug8FixTask` classes from `/home/z/my-project/vm-java-src/sources/com/android/vmcore/startup/`.
   614→   614→
   615→   615→**Files to modify.**
   616→   616→- `app/src/main/java/io/twoyi/utils/RomManager.java` — call `GsiInitPatcher.patch()` after `GsiExtractor.extract()`.
   617→   617→
   618→   618→**Acceptance criteria.**
   619→   619→- After patching, `grep "mount ext4" <vmDataDir>/fs/system/etc/init/hw/init.rc` returns no matches.
   620→   620→- After patching, `cat <vmDataDir>/fs/system/build.prop | grep ro.build.fingerprint` returns the host's fingerprint.
   621→   621→- After patching, `cat <vmDataDir>/fs/system/etc/init/hw/init.rc | grep LD_PRELOAD` shows the libkr64 preload.

   623→   623→### 3.9 HAL virtualisation
   624→   624→
   625→   625→**What VM does.** Full HAL proxy via `HALManager` (display, input, audio, camera, sensor, location, wifi, phone, battery, network) — see `VM_JAVA_ANALYSIS.md` §5.4 table.
   626→   626→
   627→   627→**What twoyi currently does.** Display (via `libOpenglRender`), input (touch + key), and that's it. No audio, camera, sensor, location, wifi, phone, battery, or network HALs.
   628→   628→
   629→   629→**What to build.** The minimum viable HAL set for a GSI to boot:
   630→   630→
   631→   631→| HAL | Priority | Implementation |
   632→   632→|---|---|---|
   633→   633→| `graphics.allocator` / `graphics.mapper` / `graphics.composer` | **Critical** | Implement via `/dev/gb` + `/dev/gb2` (see §3.3) |
   634→   634→| `audio` (`audio.primary`, `audio.a2dp`, `audio.usb`) | **High** | Stub: return success for all `init`/`standby` calls; route `createTrack`/`createRecordBuffer` to host `AudioTrack`/`AudioRecord` via the event socket |
   635→   635→| `keymaster` / `gatekeeper` | **High** | Stub: return a fixed key for all operations (will fail SafetyNet but allow boot) |
   636→   636→| `health` | Medium | Stub: return 100 % charged |
   637→   637→| `power` | Medium | Stub: return success for all calls |
   638→   638→| `vibrator` | Medium | Stub: no-op |
   639→   639→| `sensors` (12 types) | Low (for boot) | Stub: return empty sensor list; the GSI will boot without sensors, just no auto-rotate |
   640→   640→| `camera` | Low | Stub: return "no cameras available" |
   641→   641→| `gps` / `location` | Low | Stub: return last-known location from host |
   642→   642→| `wifi` | Low | Stub: return disconnected |
   643→   643→| `telephony` | Low | Stub: return no SIM |
   644→   644→| `bluetooth` | Low | Stub: return disabled |
   645→   645→
   646→   646→**For each stub HAL**, the implementation is:
   647→   647→1. A small Rust binary in `app/rs/hals/<name>/` that implements the HIDL/AIDL interface and returns stubs.
   648→   648→2. Place at `<vmDataDir>/fs/vendor/bin/hw/android.hardware.<name>-service.twoyi`.
   649→   649→3. Add a VINTF manifest entry at `<vmDataDir>/fs/vendor/etc/vintf/manifest/twoyi-<name>.xml`:
   650→   650→   ```xml
   651→   651→   <manifest version="1.0" type="hal">
   652→   652→       <name>android.hardware.<name></name>
   653→   653→       <version>4.0</version>
   654→   654→       <interface>
   655→   655→           <name>I<Name></name>
   656→   656→           <instance>default</instance>
   657→   657→       </interface>
   658→   658→   </manifest>
   659→   659→   ```
   660→   660→4. Add an init.rc entry at `<vmDataDir>/fs/vendor/etc/init/twoyi-<name>.rc`:
   661→   661→   ```
   662→   662→   service twoyi-<name> /vendor/bin/hw/android.hardware.<name>-service.twoyi

   665→   665→       group system
