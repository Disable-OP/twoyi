    16→## Executive Summary
    17→
    18→The user's hypothesis was correct: **the legacy blob has substantially different function LOGIC, not just different symbols.** There are 7 distinct categories of logic differences discovered:
    19→
    20→1. **`RenderWindow` abstraction layer** (legacy-only) — wraps `FrameBuffer`; not in AOSP source.
    21→2. **`GraphicBuffer` class + `startGBServer()` function** (legacy-only) — implements a graphics-buffer proxy server that receives `AHardwareBuffer` file descriptors from the guest over a Unix socket. **This is the twoyi `/dev/gb` equivalent** referenced in the GSI boot plan.
    22→3. **`dl*_ex` real wrappers** (legacy-only logic) — Android-7+-aware dlopen/dlsym/dlclose/dlerror implementations that work around Android's library-namespace restrictions by reading `/proc/self/maps` and trying 5 hardcoded system library paths. **AOSP build's versions are 4-byte stubs that just `b dlopen@plt`.**
    23→4. **Three hardcoded `/data/data/io.twoyi/rootfs/opengles{,2,3}` socket paths** referenced by 3 different legacy functions:
    24→   - `RenderServer::create` → `opengles2` (renderer command socket, server side)
    25→   - `GraphicBuffer::create` → `opengles3` (graphics buffer socket)
    26→   - `UnixStream::listen` → `opengles` (legacy renderer-side listen path)
    27→   The AOSP build I made instead builds these paths at runtime from `$TWOYI_ROOTFS` env var (with default `/data/data/io.twoyi/rootfs`).
    28→5. **Different `FrameBuffer::initialize` signature** — legacy takes `(int, int, int, int, int, bool, bool)` (width, height, rgba, two bool flags); AOSP takes `(int, int, OnPostFn, void*)` (width, height, post-callback, callback-context). The legacy was built from a different AOSP branch.
    29→6. **`set_emugl_crash_reporter`, `set_emugl_logger`, `set_emugl_cxt_logger`** (legacy-only) — emugl logging APIs that aren't in the AOSP source I built from.
    30→7. **Extra system-library dlopen** in `startGBServer`: legacy opens `libandroid.so` and looks up `AHardwareBuffer_recvHandleFromUnixSocket` + `android::AHardwareBuffer_to_ANativeWindowBuffer` for the graphics-buffer proxy.
    31→
    32→**Section size delta confirmed:** the legacy .text is **375,728 bytes larger** than AOSP's .text (611,496 vs 235,768). This is composed of:
    33→- Statically-linked GL/GLES translator libs (no `libEGL.so` / `libGLESv1_CM.so` / `libGLESv2.so` in legacy's NEEDED list)
    34→- libc++ with locale support (money_get, time_get, moneypunct, etc. — ~30 KB)
    35→- libgcc unwinder (`_Unwind_*` — ~2 KB)
    36→- libc++abi (`__cxa_demangle`, `__cxa_*` — ~5 KB)
    37→- Legacy-only twoyi code (`RenderWindow`, `GraphicBuffer`, `startGBServer`, `dl*_ex`, `TextureResize` — ~10 KB)
    38→- Different/newer AOSP emugl branch code (different `FrameBuffer::initialize` signature, `set_emugl_*` logger APIs, `FbConfigList` class — ~5 KB)
    39→
    40→**Architectural difference:** LEGACY has a layered architecture `startOpenGLRenderer → initOpenGLRenderer → RenderWindow/FrameBuffer`; AOSP has a flat architecture where `startOpenGLRenderer == initOpenGLRenderer` (both call `FrameBuffer::initialize` directly). The AOSP build's `startOpenGLRenderer` inlines the EGL/GL dispatch init that the legacy does inside `initLibrary`.
    41→
    42→**Bottom line:** The AOSP-built `.so` is functionally equivalent for **basic rendering** (it exports all 6 twoyi-required symbols with matching signatures and links the system EGL/GLES dynamically), but it **lacks 4 important pieces** of legacy functionality: (1) the `GraphicBuffer` `/dev/gb` proxy, (2) the Android-7+ dlopen workaround, (3) the RenderWindow abstraction, and (4) the emugl crash-reporter/logger hooks. The AOSP build is therefore suitable as a **drop-in replacement for headless rendering**, but **not** for full GSI boot (which needs the GraphicBuffer `/dev/gb` server for SurfaceFlinger).

   246→## §4. Function-by-Function Disassembly Comparison
   247→
   248→### §4.1 `startOpenGLRenderer` — entry-point comparison
   249→
   250→**Signature (from `renderer_bindings.rs`):**
   251→```rust
   252→fn startOpenGLRenderer(win: *mut c_void, width: c_int, height: c_int,
   253→                       xdpi: c_int, ydpi: c_int, fps: c_int) -> c_int;
   254→```
   255→
   256→**LEGACY (372 B at 0x052ff0) — full flow:**
   257→
   258→```
   259→1. Save callee-saved regs (x19-x26, x29, x30).
   260→2. Load log-tag string at 0xdc000+0xd56 (likely "OpenglRender").
   261→3. Call __android_log_print(3, tag, "startOpenGLRenderer(%d, %d, %p, %d, %d)", w, h, win, ...)
   262→4. Load g_renderer_state pointer, set state = 2 (initializing).
   263→5. Call initLibrary()   # initializes EGL/GLES dispatch tables
   264→6. Log "initLibrary returned %d"
   265→7. Set g_renderer_state |= 0x100
   266→8. Load a function-pointer table from .data.rel.ro at 0x10bbc0
   267→   (likely the post-callback vtable).
   268→9. Call initOpenGLRenderer(width, height, xdpi, ydpi, fps,
   269→                           1, callback_table, 0x100, ctx, ctx)
   270→   # 10 args — passes the user-provided win implicitly via globals set later
   271→10. Log "initOpenGLRenderer returned %d"
   272→11. Load FrameBuffer::s_theFrameBuffer (global at 0x108000+1592 = 0x108638)
   273→12. If non-null:
   274→       fb->m_nativeWindow (offset +376) = win
   275→       fb->m_subwindow   (offset +264) = NULL
   276→       Call FrameBuffer::resetSubWindow(win, 0, 0, w, h, w, h, 1.0, 0.0)
   277→       # IMMEDIATELY sets up the EGLSurface on the user's window
   278→    else:
   279→       Log error "FrameBuffer not initialized"
   280→13. Return 0 (always returns 0 in legacy — caller doesn't check return value)
   281→```
   282→
   283→**AOSP-arm64 (264 B at 0x0464e8) — full flow:**
   284→
   285→```
   286→1. Save x19, x20, x21, x29, x30.
   287→2. Load s_renderThread global (at 0x7e000+1408 = 0x7ee80).
   288→3. If s_renderThread != NULL, return 0 (already initialized).
   289→4. Store win in s_nativeWindow global (at 0x81000+432 = 0x811b0).
   290→5. Call init_egl_dispatch()
   291→   If failed: log "init_egl_dispatch failed" via fwrite(stderr, ..., 46, 1) → return 0
   292→6. Call init_gl_dispatch()
   293→   If failed: log via __android_log_print(6, ...) → return 0
   294→7. Call init_gl2_dispatch()  # failure non-fatal
   295→8. Call FrameBuffer::initialize(width, height, NULL, NULL)

   298→10. Call RenderServer::create(port)
   299→    If returns NULL: log "RenderServer::create failed" → return 0

   304→**Key differences:**
   305→
   306→| Aspect | LEGACY | AOSP |
   307→|---|---|---|
   308→| Layered architecture | `startOpenGLRenderer` → `initOpenGLRenderer` → `FrameBuffer::initialize` | `startOpenGLRenderer` → `FrameBuffer::initialize` directly (skips `initOpenGLRenderer`) |
   309→| Logging | `__android_log_print` at every step (5 log calls) | `fwrite(stderr, ...)` or `__android_log_print` only on failure |
   310→| Dispatch init | Done in `initLibrary()` (called from `startOpenGLRenderer`) | Done inline in `startOpenGLRenderer` |
   311→| RenderServer::create | Called inside `initOpenGLRenderer` (not visible in `startOpenGLRenderer`) | Called directly from `startOpenGLRenderer` |
   312→| Native window storage | Stores in `fb->m_nativeWindow` (offset +376) AND zeros `fb->m_subwindow` (offset +264) | Stores in standalone global `s_nativeWindow` |
   313→| Auto-create subwindow | YES — immediately calls `FrameBuffer::resetSubWindow(win, 0,0,w,h,w,h,1.0,0.0)` after init | NO — caller must call `resetSubWindow` separately |
   314→| Return value | Always returns 0 | Returns 1 on success, 0 on failure |
   315→
   316→**The AOSP build's behavior matches the Rust `renderer_bindings.rs` caller expectation** — twoyi's `core.rs` calls `startOpenGLRenderer` then `resetSubWindow` separately. The LEGACY blob's auto-reset behavior means twoyi's separate `resetSubWindow` call would be a no-op (it re-sets the same window). This is benign but worth noting.

   549→  1. `AHardwareBuffer_recvHandleFromUnixSocket` — receives a graphics buffer file descriptor over a Unix socket

   553→

   558→### §5.2 `dlopen_ex` (LEGACY-ONLY logic, 548 B at 0x0570a8)
   559→
   560→**Full disassembly decoded:**
   561→
   562→```
   563→1. Setup stack canary
   564→2. Load g_sdk_int cached global at 0x10b000+28 = 0x10b01c
   565→3. If g_sdk_int <= 0:
   566→     # First call — read SDK version from system property
   567→     memset(stack_buf, 0, 92)
   568→     __system_property_get("ro.build.version.sdk", stack_buf)  # property name at 0xdd23b
   569→     g_sdk_int = atoi(stack_buf)
   570→4. If g_sdk_int < 24 (Android 7.0 Nougat):
   571→     # Plain dlopen — no namespace restrictions
   572→     Return dlopen(filename, flag)
   573→5. Else (Android 7.0+):
   574→     # Work around Android namespace restrictions
   575→     # Check if filename starts with '/' (absolute path)
   576→     If filename[0] == '/':
   577→         # Already absolute — try as-is
   578→         # Call internal helper at dlerror_ex+0x90 (the /proc/self/maps scanner)
   579→         handle = check_loaded(filename)
   580→         If handle != NULL: return handle
   581→     Else:

   583→         paths = [
   584→             "/system/lib64/",                    # at 0xdd270
   585→             "/apex/com.android.runtime/lib64/",  # at 0xdd27f
   586→             "/apex/com.android.art/lib64/",      # at 0xdd2a0

   588→             "/vendor/lib64/",                    # at 0xdd2c9

   590→         for prefix in paths:
   591→             full_path = prefix + filename  # via __strcat_chk
   592→             handle = check_loaded(full_path)

   595→     Return dlopen(filename, flag)
   596→6. Verify stack canary, return
   597→```
   598→
   599→**The internal helper at `dlerror_ex+0x90`** (let's call it `check_loaded`) is at 0x57470+0x90 = 0x57500, but I noticed it's called as `bl dlerror_ex+0x90` which is `bl 0x57470+0x90 = 0x57500` (wait, looking again — it's `bl 57470` which calls `dlerror_ex` itself, but at a non-zero offset. Actually the disassembly shows `bl 57470 <dlerror_ex@@Base+0x90>` — this means the call target is 0x57470 which is the START of `dlerror_ex+0x90`'s code. Hmm, but `dlerror_ex` starts at 0x573e0, so 0x573e0+0x90 = 0x57470. So this is a separate function starting at 0x57470 — but objdump labels it relative to `dlerror_ex` because there's no symbol for it. This is the `check_loaded` helper.)
   600→
   601→The `check_loaded` helper reads `/proc/self/maps` (string at 0xdd250) and looks for `r-xp` and `r--p` mappings (strings at 0xdd262 and 0xdd267) to determine if a library is already loaded. If found, it returns the existing handle (avoiding a duplicate dlopen that would fail due to namespace restrictions).
   602→
   603→**This is a sophisticated Android-7+ library-namespace workaround.** It exists because Android 7.0 introduced library namespaces (per `https://developer.android.com/about/versions/nougat/android-7.0-changes#ndk`) that prevent apps from `dlopen`ing system libraries by name. The legacy blob works around this by:
   604→1. Trying the 5 standard system library paths directly
   605→2. Checking `/proc/self/maps` to find already-loaded libraries and reuse their handles
   606→
   607→**The AOSP build's `dlopen_ex` is just `b dlopen@plt` (4 bytes)** — no Android-7+ workaround. This means the AOSP build will FAIL to `dlopen("libandroid.so")` on Android 7+ devices when `startGBServer` (if it existed) tried to load it. **However, since the AOSP build doesn't have `startGBServer` at all, this is currently moot.**

   609→### §5.3 `dlsym_ex` (LEGACY-ONLY logic, 276 B at 0x0572cc)
   610→
   611→**Disassembly decoded:**
   612→
   613→```
   614→1. Setup stack canary
   615→2. Read g_sdk_int (cached)
   616→3. If g_sdk_int < 24:
   617→     Return dlsym(handle, symbol)
   618→4. Else:
   619→     # Custom symbol-table lookup
   620→     Load handle->num_symbols (offset +24)

   730→**Implementation in AOSP build's `UnixStream.cpp`:**
   731→```cpp
   732→static std::string make_unix_path(unsigned int port) {
   733→    const char* rootfs = getenv("TWOYI_ROOTFS");
   734→    if (!rootfs || !*rootfs) rootfs = "/data/data/io.twoyi/rootfs";
   735→    const char* suffix = port == 0 ? "opengles" :
   736→                         port == 1 ? "opengles2" :
   737→                                     "opengles3";
   738→    return std::string(rootfs) + "/" + suffix;
   739→}
   740→```
   741→

   746→## §7. ELF Dependency Comparison
   747→
   748→### §7.1 NEEDED shared libraries
   749→
   750→| Library | LEGACY | AOSP-arm64 | AOSP-x86_64 |
   751→|---|:-:|:-:|:-:|
   752→| `libEGL.so` | ✗ | ✓ | ✓ |
   753→| `libGLESv1_CM.so` | ✗ | ✓ | ✓ |
   754→| `libGLESv2.so` | ✗ | ✓ | ✓ |
   755→| `liblog.so` | ✓ | ✓ | ✓ |
   756→| `libc.so` | ✓ | ✓ | ✓ |
   757→| `libm.so` | ✓ | ✓ | ✓ |
   758→| `libdl.so` | ✓ | ✓ | ✓ |
   759→
   760→**Critical:** The LEGACY blob has the GL translators (libEGL, libGLESv1_CM, libGLESv2) **statically linked** — they're part of the 375 KB extra `.text`. The AOSP build dynamically links them, which is the correct Android pattern (uses the system EGL/GLES implementation).
   761→
   762→**Implication:** On Android, the AOSP build will use the device's actual GPU driver (e.g., Adreno, Mali, PowerVR), while the legacy blob uses a statically-linked desktop-GL translator that may not match the device's GL implementation. For twoyi's use case (rendering the guest's GL commands on the host GPU), the AOSP approach is **architecturally superior**.
   763→
   764→### §7.2 ARM64 vs x86_64 AOSP builds — functionally equivalent
   765→
   766→The AOSP-arm64 and AOSP-x86_64 builds have nearly identical:
   767→- Import counts (98 vs 94)
   768→- Export counts (1,227 vs 1,061 — small difference due to instruction-encoding variations in stubs)
   769→- NEEDED list (identical 7 libraries)
   770→- Twoyi-specific symbols (all 6 present in both, with similar sizes)
   771→- String layout (same `TWOYI_ROOTFS` env-var approach, same suffix strings)
   772→- Section sizes (`.text` 235,768 vs 227,538; `.rodata` 25,340 vs 33,544 — small differences due to x86_64 PIC addressing)
   773→
   774→**Conclusion:** The AOSP build is portable across arm64 and x86_64 with no functional differences.

   822→## §9. Recommendations
   823→
   824→### §9.1 Can the AOSP build replace the legacy blob?
   825→
   826→**For twoyi's current rendering use case (running a guest Android OS that renders GL via the qemu_pipe):** **YES.** The AOSP build exports all 6 required symbols with matching signatures, links the system EGL/GLES dynamically (better than the legacy's static translator), and supports the `TWOYI_ROOTFS` env var for custom data dirs.
   827→
   828→**For full GSI boot (SurfaceFlinger compositing real frames):** **NO.** The AOSP build lacks:
   829→1. `GraphicBuffer` class + `startGBServer()` — needed for the `/dev/gb` graphics buffer proxy
   830→2. Android-7+ `dlopen_ex` workaround — needed to `dlopen("libandroid.so")` for `AHardwareBuffer_recvHandleFromUnixSocket`
   831→3. The `opengles3` socket path string — referenced by the missing `GraphicBuffer::create`
