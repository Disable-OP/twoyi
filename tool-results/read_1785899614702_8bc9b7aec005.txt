   250→
   251→### 2.7 Seccomp filter
   252→
   253→From `VM_KR64_ANALYSIS.md` §12 and §11:
   254→
   255→`libkr64.so` installs a **seccomp filter** on the guest process. Strings decoded from `.data`:
   256→- `INIT.SECCOMP` (key 0xb4)
   257→- `init_seccomp` (key 0x67, A 11 only)
   258→- `__NR_rt_sigaction SIGSYS` (key 0x1a, A 11 only)
   259→- `BLOCKED.SYSCALL.FAILED` (key 0xc9)
   260→- `blocked syscall failed %d` (key 0xc2 / 0xe2)
   261→
   262→Mechanism:
   263→1. `libkr64.so` calls `prctl(PR_SET_NO_NEW_PRIVS, 1)` (4 paired `prctl` calls at `0x111e28`/`0x112694`/`0x11270c`/`0x112f78`).
   264→2. `libkr64.so` installs a SIGSYS handler via `sigaction(SIGSYS, …)` (the `__NR_rt_sigaction SIGSYS` string is the giveaway).
   265→3. `libkr64.so` installs a `SECCOMP_SET_MODE_FILTER` (syscall 277 on aarch64) BPF program via the `syscall()` wrapper.
   266→4. The BPF program traps forbidden syscalls (the ones that would let the guest escape its sandbox — e.g. `mount` without our hook, `chroot`, `pivot_root`, `reboot`, raw `swapon`/`swapoff`, `acct`, etc.).
   267→5. When a forbidden syscall is hit, the kernel delivers SIGSYS to the guest.
   268→6. The SIGSYS handler logs `BLOCKED.SYSCALL.FAILED: <syscall_nr>` and either:
   269→   - **Emulates** the syscall (returns 0 or a fake-success value), OR
   270→   - **Kills** the guest (via `_exit`).
   271→
   272→This is the core of VM's "kernel replacement" pattern: the seccomp filter turns syscalls into traps that the userspace daemon can intercept and synthesise, mimicking the kernel's behaviour for a controlled subset of syscalls.
   273→
   274→### 2.8 `/proc` emulation
   275→
   276→From `VM_KR64_ANALYSIS.md` §4.2 and §16:
   277→
   278→`libkr64.so` emulates `/proc` by intercepting `open("/proc/…")` calls (via shadowhook on `open`/`openat`). When the path matches one of these patterns, libkr64 synthesises the content:
   279→
   280→| Decoded path | Synthesised content |
   281→|---|---|
   282→| `/proc/self/exe` | Resolves to the guest's `/system/bin/init` (not the host's `app_process64`) |
   283→| `/proc/self/maps` | Per-VM map (filtered to show only guest mappings, not host's) — uses `/proc/maps_%d_%d` template (vmid, pid) |
   284→| `/proc/self/status` | Per-VM status — template `/proc/status_%d_%d` |
   285→| `/proc/self/mounts` | Per-VM mounts (only guest mounts, not host's) — template `/proc/mounts_%d_%d` |
   286→| `/proc/self/fd/%d` | Resolves to the per-VM view of FDs |
   287→| `/proc/cmdline` | Synthesised as `androidboot.hardware=… androidboot.bootdevice=…` (matches the GSI's expected cmdline) |
   288→| `/proc/version` | Synthesised as `Linux version 4.14.x …` (matches the GSI's expected kernel version) |
   289→| `/proc/mounts` | Alias for `/proc/self/mounts` |
   290→| `/proc/net/if_inet6/` | Synthesised based on `NetlinkManager`'s virtual interfaces |
   291→| `/proc/sys/kernel/kptr_restrict` | Returns `1` (A 11 hardening) |
   292→| `/proc/sys/vm/mmap_rnd_bits` | Returns `16` (A 11 hardening) |
   293→| `/proc/%d/%s` | Per-VM view of any process's `/proc/<pid>/<file>` |
   294→| `/proc/exe_%d` | Per-VM `exe` symlink for PID `<d>` |
   295→| `/proc/mnt_points` | Per-VM mount point list |
   296→
   297→The `/dev/vmproc` device (created via `mknodat` at `0x11d770`, decoded with keys 0x47/0x64/0x07) is the entry point — `open("/proc/…")` is redirected to `open("/dev/vmproc")` + an ioctl that selects which virtual file to read.
   298→
   299→### 2.9 Init configuration patches
   300→
   301→From `VM_JAVA_ANALYSIS.md` §2.3 (startup pipeline) and `VM_ROM_ANALYSIS.md` §4.3:
   302→
   303→Eight `BugNFixTask` classes (`com.android.vmcore.startup.Bug1FixTask` … `Bug8FixTask`) apply ROM-version-specific patches to the extracted filesystem before boot. The pipeline (state 4) is:
   304→
   305→```
   306→ApplyOverlaysTask → Bug1FixTask → … → Bug8FixTask → CleanLogTask →
   307→SuperuserTask → XposedTask → GooglePlayTask → MagiskTask →
   308→BuildTmpfsTask → BuildVMPropTask → BuildExecPathTask
   309→```
   310→
   311→Notable patches inferred from path constants decoded in `VM_ROM_ANALYSIS.md` §4:
   312→- **`app_process32`/`app_process64` shims** — rewrite the symlinks at `/system/bin/app_process32`, `/system/bin/app_process32_xposed`, `/system/bin/app_process64`, `/system/bin/app_process64_xposed` so they point at the host's `app_process` binary (avoiding the need to ship a full ART runtime).
   313→- **`libui.so` ABI selection** — replace `/system/lib/libui.so` with `libui10.so` (Android 10 variant), `libui51.so` (Android 5.1), or `libhostlibui.so`/`libhostlibui_10.so` (the host-aware shim) depending on ROM version.
   314→- **`build.prop` patching** — `BuildVMPropTask` writes `/system/build.prop` with the host's actual build fingerprint, `Build.ID`, and a synthetic kernel version. This makes `Build.FINGERPRINT` inside the guest match the host (required by SafetyNet / Play Integrity basic attestation).
   315→- **`init.rc` patching** — `MagiskTask` injects magisk service entries into `/system/etc/init/hw/init.rc`. The same mechanism is presumably used to inject the `libkr64.so` LD_PRELOAD.
   316→- **`PATH` and exec dirs** — `BuildExecPathTask` sets the guest's `PATH` to include `/system/bin:/system/xbin:/system/sbin:/vendor/bin:/system/apex/com.android.runtime/bin`.

   361→### 3.2 Binder virtualisation (the hard one)
   362→
   363→**What VM does.** `libvm.so` (in the Java app process) creates `/vm%d/dev/binder` via the `setupBinder()` JNI, and the Java `BinderService` wraps the host's `IActivityManager` with a `java.lang.reflect.Proxy` so the guest's `servicemanager` lookups are proxied back into the host app (see §2.5).
   364→
   365→**What twoyi currently does.** Uses the host's `/dev/binder` directly. The guest's `servicemanager` registers with the host's `servicemanager`. This means the guest's `getSystemService(ACTIVITY_SERVICE)` returns the *host's* ActivityManager — the guest can launch host apps but not its own. This is why twoyi can't have its own package manager.
   366→
   367→**What to build.** Two pieces:
   368→
   369→**(a) Native binder proxy in Rust** — `app/rs/kr64/src/binder_proxy.rs`:
   370→- Open `/dev/binder` on the host side.
   371→- Create `/vm%d/dev/binder` as a char device via `mknodat(S_IFCHR, …)`.
   372→- Accept `BINDER_WRITE_READ` / `BINDER_VERSION` / `BINDER_SET_MAX_THREADS` ioctls from the guest.
   373→- Parse the binder transaction header.
   374→- For transactions targeting `android.app.IActivityManager` / `android.app.IActivityTaskManager` / `android.content.pm.IPackageManager` / `android.view.IWindowManager` — route them to the Java side via the event socket.
   375→- For transactions targeting `android.os.IServiceManager` — synthesise responses (return a fake service handle for each well-known service name).
   376→- For all other transactions — proxy directly to the host binder.
   377→
   378→**(b) Java-side binder service** — `app/src/main/java/io/twoyi/service/BinderService.java`:
   379→- Copy VM's `BinderService.m5206WWWWoWWWWo` structure (see §2.5).
   380→- Reflect into `ActivityManager` to get the system `IActivityManager` IBinder.
   381→- Wrap with a `Proxy`.
   382→- Add a `setupBinder()` JNI that calls into `libkr64.so`.
   383→- Implement `IBinderService.Stub` with the AIDL interface `io.twoyi.service.IBinderService`.
   384→
   385→**Files to create.**
   386→- `app/src/main/java/io/twoyi/service/BinderService.java`
   387→- `app/src/main/java/io/twoyi/service/IBinderService.aidl` — AIDL stub (interface descriptor `"io.twoyi.service.IBinderService"`).
   388→- `app/src/main/java/io/twoyi/FreeReflection.java` — copy the FreeReflection trick (or use ` Reflection_exemptAll` from `me.weishu.reflection.BootstrapClass` — bundle the dex).
   389→- `app/rs/kr64/src/binder_proxy.rs` (above).
   390→
   391→**Files to modify.**
   392→- `app/src/main/java/io/twoyi/TwoyiApplication.java` — add `FreeReflection.exemptAll()` in `attachBaseContext` (currently twoyi doesn't do this — VM does).
   393→- `app/src/main/java/io/twoyi/utils/RomManager.java` — add a `setupBinder()` call in `ensureBootFiles()` (currently only kills orphans, etc.).
   394→
   395→**Acceptance criteria.**
   396→- After boot, `adb shell service list` inside the guest shows `android.app.IActivityManager: […]` resolving to the twoyi proxy, not the host's.
   397→- `adb shell am start -n com.android.settings/.Settings` inside the guest starts the guest's Settings, not the host's.
   398→- `adb shell pm list packages` inside the guest lists only guest-installed packages, not the host's.
   399→
   400→**MVP skip.** If implementing full binder virtualisation is too much, an initial GSI boot can run with the host's binder shared (as today). The guest will boot but every `getSystemService()` call returns host services — so the guest's `system_server` won't be able to register itself. This will likely crash early. Recommend implementing at least the `IActivityManager` and `IPackageManager` proxies as the minimum.

   402→### 3.3 Graphics buffer management (`/dev/gb` and `/dev/gb2`)
   403→
   404→**What VM does.** `libkr64.11.so` (A 11 only) creates `/dev/gb` and `/dev/gb2` as char devices (via `mknodat S_IFCHR` at `0x11d770`, decoded with keys 0xe0 and 0x0c). These expose a `gralloc`-like ioctl interface for allocating graphics buffers. The guest's `surfaceflinger` calls these ioctls to allocate buffers for compositing; the host returns a buffer handle that maps to either an ashmem region or a host `AHardwareBuffer`.
   405→
   406→The presence of two devices (`gb` + `gb2`) suggests:
   407→- `/dev/gb` is the **framework gralloc** (used by surfaceflinger, accessed via `/dev/binder`).
   408→- `/dev/gb2` is the **vendor gralloc** (used by HALs, accessed via `/dev/vndbinder`).
   409→
   410→This split matches Android 11's gralloc HAL layout where `android.hardware.graphics.allocator@4.0` (framework) and `android.hardware.graphics.allocator-V1-ndk` (vendor) are separate services.
   411→
   412→**What twoyi currently does.** No gralloc emulation. The `libOpenglRender_aosp.so` (the rebuilt AOSP emugl renderer at `/home/z/my-project/app/src/main/jniLibs/x86_64/libOpenglRender_aosp.so`) implements its own buffer management via the `ColorBuffer` class in `app/rs/openglrenderer/src/gralloc.rs`. The guest's SurfaceFlinger has no gralloc HAL, so it crashes on the first composite.
   413→
   414→**What to build.** `app/rs/kr64/src/gb.rs`:
   415→- Create `/dev/gb` and `/dev/gb2` as char devices.
   416→- Implement these ioctls (the exact numbers can be inferred from `android.hardware.graphics.allocator@4.0` HAL header in AOSP `hardware/interfaces/graphics/allocator/4.0/IAllocator.hal`):
   417→  - `ALLOCATE` — allocate a buffer of given width/height/format/usage. Return a buffer handle that's a host `AHardwareBuffer` (we already have these via `libEGL.so`).
   418→  - `DUMP_DEBUG_INFO` — return a fake debug string.
   419→  - `GET_ALL_ALLOCATOR_FUNCTIONS` — return function pointers for the gralloc module.
   420→
   421→For the MVP, we can route gralloc allocation through the existing `libOpenglRender_aosp.so` ColorBuffer infrastructure — each guest gralloc allocation creates a host-side `ColorBuffer` and returns its ID as the buffer handle.
   422→
   423→**Files to create.**
   424→- `app/rs/kr64/src/gb.rs` — char device + ioctls.
   425→- `app/rs/openglrenderer/src/gralloc.rs` — already has `ColorBuffer`; add a `from_guest_handle(u64) -> ColorBuffer` lookup.
   426→
   427→**Files to modify.**
   428→- `app/rs/kr64/src/devices.rs` — register `/dev/gb` and `/dev/gb2`.
   429→
   430→**Acceptance criteria.**
   431→- After boot, `adb shell dumpsys SurfaceFlinger` inside the guest shows a non-zero buffer count.
   432→- The guest's launcher renders its first frame (visible via the Surface registered through `nativeAddSurface`).

   434→### 3.4 Seccomp filter
   435→
   436→**What VM does.** Installs a `SECCOMP_SET_MODE_FILTER` BPF program with a SIGSYS handler that emulates blocked syscalls (see §2.7).
   437→
   438→**What twoyi currently does.** No seccomp. The guest can call any syscall the host kernel allows. This is unsafe and also means the guest sees the host's `/proc`, `/sys`, etc. (no isolation).
   439→
   440→**What to build.** `app/rs/kr64/src/seccomp.rs`:
   441→
   442→1. **Allowlist of syscalls** — start from Android's own seccomp policy (in AOSP at `system/seccomp/policy.txt`). For twoyi we need to also allow the syscalls that `libkr64.so` intercepts (so they trap to our SIGSYS handler).
   443→
   444→2. **Blocklist (trap-to-SIGSYS)** — these syscalls are blocked and emulated:
   445→   - `open`/`openat` for `/proc/…`, `/sys/…`, `/dev/…` paths (intercepted by the proc emulator)
   446→   - `mount`/`umount`/`umount2` (intercepted by the mount_mgr)
   447→   - `pivot_root`/`chroot` (intercepted to redirect to the per-VM rootfs)
   448→   - `reboot` (intercepted to send a shutdown event)
   449→   - `swapon`/`swapoff` (intercepted to be no-ops)
   450→   - `acct` (intercepted to be a no-op)
   451→   - `sethostname`/`setsid` (intercepted for the per-VM hostname)
   452→
   453→3. **SIGSYS handler** — `sigaction(SIGSYS, …)`:
   454→   - Read the syscall number from `ucontext->uc_mcontext`.
   455→   - Log `BLOCKED.SYSCALL.FAILED: <nr>`.
   456→   - Dispatch to the appropriate emulator function.
   457→   - Set the return value in `ucontext->uc_mcontext.regs[0]`.
   458→   - Increment the instruction pointer past the syscall instruction.
   459→   - Return.
   460→
   461→**Files to create.**
   462→- `app/rs/kr64/src/seccomp.rs`
   463→- `app/rs/kr64/src/bpf_filter.rs` — the compiled BPF program (generate with `libseccomp` or hand-write).
   464→
   465→**Files to modify.**
   466→- `app/rs/kr64/src/main.rs` — call `seccomp::init()` after all devices are created and before `fork`+`exec` of the guest `init`.
   467→
   468→**Acceptance criteria.**
   469→- After boot, `adb shell cat /proc/self/status` inside the guest returns a synthesised status (not the host's).
   470→- After boot, `adb shell mount` inside the guest shows only guest mounts.
   471→- After boot, `adb shell reboot` inside the guest sends a shutdown event (doesn't actually reboot the host).
   472→
   473→### 3.5 `/proc` emulator
   474→
   475→**What VM does.** Intercepts `open("/proc/…")` and synthesises content (see §2.8).
   476→
   477→**What twoyi currently does.** Uses the host's `/proc`. The guest sees the host's process list, mounts, cmdline, version — which breaks the guest's `init` (it expects `androidboot.hardware=…` on the cmdline) and leaks host info.
   478→
   479→**What to build.** `app/rs/kr64/src/proc_emu.rs`:
   480→
   481→- Create `/dev/vmproc` as a char device (per VM's design).
   482→- Hook `open`/`openat` via shadowhook (or via the seccomp SIGSYS trap — see §3.4).
   483→- When the path matches `/proc/…`, redirect to `/dev/vmproc` + an ioctl that selects the virtual file.
   484→- Implement these synthesised files (per §2.8 table):
   485→  - `/proc/cmdline` — `androidboot.hardware=twoyi androidboot.bootdevice=/dev/block/vdc androidboot.serialno=…`
   486→  - `/proc/version` — `Linux version 4.14.x-perf-g… (build@host) …` (match what the GSI expects)
   487→  - `/proc/self/maps` — filtered host maps (only show guest-mapped regions)
   488→  - `/proc/self/status` — synthesised with the guest's PID/UID/GID
   489→  - `/proc/self/mounts` — only guest mounts
   490→  - `/proc/self/exe` — symlink to `/system/bin/init` (the guest's init, not the host's)
   491→  - `/proc/net/if_inet6/` — based on `NetlinkManager`'s virtual interfaces
   492→  - `/proc/sys/kernel/kptr_restrict` — `1`
   493→  - `/proc/sys/vm/mmap_rnd_bits` — `16`
   494→
   495→**Files to create.**
   496→- `app/rs/kr64/src/proc_emu.rs`
   497→
   498→**Files to modify.**
   499→- `app/rs/kr64/src/devices.rs` — register `/dev/vmproc`.
   500→- `app/rs/kr64/src/seccomp.rs` — add `open`/`openat` to the trap list (or use shadowhook instead).
   501→
   502→**Acceptance criteria.**
   503→- After boot, `adb shell cat /proc/cmdline` inside the guest returns the synthesised cmdline.
   504→- After boot, `adb shell cat /proc/version` inside the guest returns a Linux version string matching the GSI's expected kernel.
   505→- The guest's `init` doesn't crash on `open("/proc/cmdline")`.

   507→### 3.6 Inline hooking (shadowhook equivalent)
   508→
   509→**What VM does.** Embeds `shadowhook v1.0.8` (ByteDance's inline hook library) — hooks the dynamic linker's `do_dlopen` so guest `dlopen` calls can be redirected (see `VM_KR64_ANALYSIS.md` §4.1).
   510→
   511→**What twoyi currently does.** No hooking. The guest's `dlopen` calls go to the system linker, which loads from `/system/lib64/` (the host's system).
   512→
   513→**What to build.** Two options:
   514→
   515→**(a) Use shadowhook directly** — there's a Rust binding `shadowhook-sys` (https://crates.io/crates/shadowhook-sys). Add it to `app/rs/kr64/Cargo.toml`. Hook:
   516→- `do_dlopen` in the linker (so guest `dlopen` loads from the per-VM rootfs).
   517→- `open`/`openat` in libc (for `/proc` emulation).
   518→- `mount`/`umount` (for the mount_mgr).
   519→- `__system_property_get` (for property emulation).
   520→
   521→**(b) Use LD_PRELOAD** — simpler, less invasive. Set `LD_PRELOAD=libkr64.so` when exec'ing the guest. Override the libc functions in `libkr64.so` itself. This is what VM probably does for some hooks (shadowhook is for hooks they can't override via LD_PRELOAD because the function is already loaded).
   522→
   523→Recommend (b) for the MVP — it's simpler and works for all the hooks we need.
   524→
   525→**Files to create.**
   526→- `app/rs/kr64/src/hooks.rs` — LD_PRELOAD overrides for `open`, `openat`, `mount`, `umount`, `__system_property_get`, `dlopen`.
   527→
   528→**Files to modify.**
   529→- `app/rs/kr64/src/main.rs` — set `LD_PRELOAD=libkr64.so` in the env before `execve("./init")`.
   530→
   531→**Acceptance criteria.**
   532→- After boot, `adb shell ls /system/lib64/` inside the guest shows the guest's libraries (not the host's).
   533→- After boot, `adb shell getprop ro.build.fingerprint` returns the guest's fingerprint.

   535→### 3.7 ROM extraction (GSI-aware)
   536→
   537→**What VM does.** Downloads `rom.zip` (a ZIP), decrypts with AES-128-ECB, extracts via ZIP or 7-Zip into `<vmDataDir>/fs/` (see §2.2). The extracted tree is already flattened (e.g. `/system/product/...` is a directory inside `/system/`, not a separate mount).
   538→
   539→**What twoyi currently does.** `RomManager.java` extracts a pre-built `rootfs.7z` (Android 8.1 only) into `/data/data/io.twoyi/rootfs/`. The format is a flat directory tree, not a multi-partition GSI.
   540→
   541→**What to build.** `app/src/main/java/io/twoyi/utils/GsiExtractor.java`:
   542→
   543→1. **Input**: a GSI `system.img` (ext4 or sparse-ext4) + optionally `product.img`, `system_ext.img`, `boot.img` (for the ramdisk).
   544→2. **Extract `system.img`**:
   545→   - If sparse: `simg2img system.img system.raw.img` (use the `libsparse` Rust crate or shell out to `simg2img`).
   546→   - If ext4: mount via `fuse2fs` (no root needed) or extract via `rust-ext4` crate (https://crates.io/crates/ext4).
   547→   - Walk the filesystem and copy files into `<vmDataDir>/fs/system/`.
   548→3. **Extract `product.img`** (if present) → `<vmDataDir>/fs/system/product/` (note: Treble flattens product under system on the device).
   549→4. **Extract `system_ext.img`** (if present) → `<vmDataDir>/fs/system/system_ext/`.
   550→5. **Extract `boot.img`** ramdisk (if present):
   551→   - `boot.img` = header + kernel + ramdisk (gzip/lz4) + second stage.
   552→   - Use the `bootimage` Rust crate to parse.
   553→   - Extract the ramdisk and unpack with `cpio -idmv` (shell out).
   554→   - Place into `<vmDataDir>/fs/ramdisk/`.
   555→6. **Synthesise a minimal `vendor.img`** if the user didn't supply one:
   556→   - Pre-built at `app/src/main/assets/vendor.img` — contains stub HALs for `vibrator`, `graphics.allocator`, `graphics.mapper`, `graphics.composer`, `audio`, `camera`, `sensors`, `gatekeeper`, `keymaster`, `health`, `power`.
   557→   - Each HAL is a tiny binary that returns success for all calls.
   558→   - Extract into `<vmDataDir>/fs/vendor/`.
   559→7. **Apply init patches**:
   560→   - Patch `/system/etc/init/hw/init.rc` to remove `mount` directives that would fail (e.g. `mount tmpfs tmpfs /tmp` is fine, `mount ext4 /dev/block/by-name/system /system` is not — remove these).
   561→   - Add `LD_PRELOAD=libkr64.so` to the zygote service.
   562→   - Patch `/vendor/etc/init/*.rc` similarly.
   563→
   564→**Files to create.**
   565→- `app/src/main/java/io/twoyi/utils/GsiExtractor.java`
   566→- `app/rs/gsi_extractor/Cargo.toml` — Rust crate for sparse/ext4/cpio parsing (call from Java via JNI).
   567→- `app/rs/gsi_extractor/src/lib.rs` — JNI entry points: `nativeExtractSystemImg(path, destDir)`, `nativeExtractProductImg`, `nativeExtractBootImg`.
   568→- `app/src/main/assets/vendor.img` — pre-built minimal vendor image (or a script to generate one from AOSP — see §5.7).
   569→
   570→**Files to modify.**
   571→- `app/src/main/java/io/twoyi/utils/RomManager.java` — replace `initRootfs()` with a call to `GsiExtractor.extract(context, gsiFile)`.
   572→
   573→**Acceptance criteria.**
   574→- Given an Android 11 x86_64 GSI `system.img` (from https://ci.android.com/builds/branches/aosp-master/grid), `GsiExtractor.extract()` produces a directory tree at `<vmDataDir>/fs/` containing `/system/bin/init`, `/system/etc/init/hw/init.rc`, `/system/product/`, `/system/system_ext/`, `/vendor/etc/vintf/manifest/`, etc.
   575→- `file <vmDataDir>/fs/system/bin/init` reports `ELF 64-bit LSB shared object, x86-64`.
   576→- The total size of the extracted tree is within 2x of the input `system.img` size (some files compress better as ext4 than as plain files).

   578→### 3.8 Init configuration
   579→
   580→**What VM does.** Eight `BugNFixTask` classes patch the extracted filesystem (see §2.9). Notably:
   581→- `BuildVMPropTask` rewrites `/system/build.prop` with the host's build fingerprint.
   582→- `MagiskTask` patches `/system/etc/init/hw/init.rc` to inject magisk service entries.
   583→- `FixCPUArchTask` rewrites `app_process32`/`app_process64` symlinks.
   584→- `BuildTmpfsTask` mounts tmpfs on `/tmp`, `/dev`, etc.
   585→
   586→**What twoyi currently does.** Patches `services.jar` for the `PackageInstallerSession` bug (`patchServicesJarForPackageInstaller`). No other init patches.
   587→
   588→**What to build.** A `GsiInitPatcher` Java class that applies these patches to the extracted GSI:
   589→
   590→1. **`/system/build.prop`** — overwrite these properties:
   591→   - `ro.build.fingerprint` — set to the host's `Build.FINGERPRINT` (so Play Integrity basic attestation passes).
   592→   - `ro.build.id` — set to the host's `Build.ID`.
   593→   - `ro.build.version.incremental` — set to the host's `Build.VERSION.INCREMENTAL`.
   594→   - `ro.product.cpu.abi` — set to the host's primary ABI (`x86_64` or `arm64-v8a`).
   595→   - `ro.hardware` — set to `twoyi` (matches what `/proc/cmdline` returns).
   596→2. **`/system/etc/init/hw/init.rc`** — apply these patches:
   597→   - Remove all `mount ext4 …` and `mount f2fs …` lines (the filesystems are already mounted by libkr64).
   598→   - Remove the `service flash_recovery` block (no recovery partition).
   599→   - Add `setenv LD_PRELOAD /system/lib64/libkr64.so` to the `service zygote` block.
   600→   - Add a new `service twoyi_event /system/bin/twoyi_event` that connects to the host's event socket and signals `BOOT_COMPLETED`.
   601→3. **`/vendor/etc/init/*.rc`** — remove all `service` blocks that start HALs we don't implement (camera HAL, sensors HAL if not proxying). Replace with stub services that exit 0 immediately.
   602→4. **`/system/bin/app_process64`** — replace with a wrapper script that execs the host's `app_process64` with `LD_PRELOAD` set:
   603→   ```sh
   604→   #!/system/bin/sh
   605→   exec /system/bin/linker64 /system/lib64/libkr64.so --preload /system/bin/app_process64_real "$@"
   606→   ```
   607→   (Or better — keep the original `app_process64` binary from the GSI, but preload `libkr64.so` via `LD_PRELOAD` in the zygote service in init.rc.)
   608→5. **`/system/etc/prop.default`** — apply the same patches as `/system/build.prop`.
   609→6. **`/vendor/build.prop`** — set `ro.vendor.build.fingerprint` to match.
   610→
   611→**Files to create.**
   612→- `app/src/main/java/io/twoyi/utils/GsiInitPatcher.java` — implements the above patches.
   613→- `app/src/main/java/io/twoyi/utils/setup/` — port VM's `Bug1FixTask` … `Bug8FixTask` classes from `/home/z/my-project/vm-java-src/sources/com/android/vmcore/startup/`.
   614→
   615→**Files to modify.**
   616→- `app/src/main/java/io/twoyi/utils/RomManager.java` — call `GsiInitPatcher.patch()` after `GsiExtractor.extract()`.
   617→
   618→**Acceptance criteria.**
   619→- After patching, `grep "mount ext4" <vmDataDir>/fs/system/etc/init/hw/init.rc` returns no matches.
   620→- After patching, `cat <vmDataDir>/fs/system/build.prop | grep ro.build.fingerprint` returns the host's fingerprint.
   621→- After patching, `cat <vmDataDir>/fs/system/etc/init/hw/init.rc | grep LD_PRELOAD` shows the libkr64 preload.

   623→### 3.9 HAL virtualisation
   624→
   625→**What VM does.** Full HAL proxy via `HALManager` (display, input, audio, camera, sensor, location, wifi, phone, battery, network) — see `VM_JAVA_ANALYSIS.md` §5.4 table.
   626→
