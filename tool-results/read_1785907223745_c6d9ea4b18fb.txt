  2133→### Key findings
  2134→1. **Battery is dramatically simpler than audio/sensors.** No `UnixListener`, no accept thread, no worker pool, no `ThreadPool`, no wire protocol, no `read_exact` helper, no per-connection state, no `try_clone()` sub-thread. The entire module is: create seven files + spawn one refresh thread. The 856 LOC (vs. audio.rs 1,423 / sensors.rs 2,294) reflects this — most of the line count is rustdoc + tests, not implementation. The implementation proper is ~350 LOC.
  2135→2. **The `BatteryDeviceView` duplication was the wrong abstraction.** The first draft duplicated all seven `update_*` methods on a `BatteryDeviceView<'a>` struct so the refresh thread could call them without owning a `BatteryDevice`. The cleaner solution is to lift `write_file_at(dir, name, value)` and `refresh_dir(dir)` to free functions — both `BatteryDevice::write_file` (a one-line delegate) and the spawn closure call them directly. This removed ~90 LOC and made the code easier to reason about (no second struct to keep in sync with `BatteryDevice`). The lesson generalises: when a thread needs to call instance methods but only owns a subset of the instance's state, lift the method body to a free function taking that subset as args.
  2136→3. **The 1 s sleep tick is the right granularity for the refresh loop.** A single `thread::sleep(Duration::from_secs(30))` would block `Drop::join()` for up to 30 s on shutdown, which would time out the `spawn_then_drop_joins_cleanly` test (default 60 s timeout) and feel sluggish in production. Sleeping in 1 s ticks and re-checking the shutdown flag between ticks means the thread observes shutdown within ~1 s. The cost is 30 extra `AtomicBool::load(Acquire)` calls per refresh cycle, which is negligible.
  2137→4. **The "charging" file should be derived from "status", not independently settable.** The Linux `power_supply` ABI has both a `status` file (string: Charging/Discharging/Full/Not charging) and a `charging` file (0/1) — they're redundant, and if they disagree the guest's battery HAL gets confused. The fix is to make `update_charging` take a `BatteryStatus` and derive the 0/1 from it, so the two files can never disagree. The `update_charging_derives_from_status` test asserts this invariant for all four status variants.
  2138→5. **The unit choice (mV for voltage, 1/10 °C for temperature) matches the JNI values 1:1.** The standard Linux `power_supply` ABI uses µV for `voltage_now`, but VM's file-based battery HAL uses mV (matching `android.os.BatteryManager`'s int fields). We mirror VM's choice so the JNI value and the file content are identical — no unit conversion needed, which means `jni_get_battery_voltage()` returning 4200 produces a file containing "4200", and `read_voltage()` reads 4200 back. If a future guest ROM's battery HAL expects µV, the fix is a one-line `* 1000` in `update_voltage`. Documented in `BATTERY_IMPL.md` §1.2.
  2139→6. **The HAL-DETAIL-1 analysis was accurate.** The "file-based battery" description in `HAL_VIRTUALIZATION_ANALYSIS.md` §4 and `DEVELOPMENT_ROADMAP.md` task 4.10 translated directly into the implementation. The only design decisions not specified by the analysis were: (a) the 30 s refresh interval (chosen to be within the guest's typical 1-minute poll cadence), (b) the 1 s sleep tick granularity (chosen for fast shutdown), (c) the `BatteryStatus` enum's `as_str()` returning "Not charging" (two words, matching the Linux ABI), and (d) the `Drop` impl not unlinking the sysfs files (chosen to avoid racing with guest open fds). All four decisions are documented in `BATTERY_IMPL.md` §4.
  2140→7. **The skeleton compiles and tests pass with zero external deps.** The crate still depends on only `libc`. No `jni` crate, no `bitflags` crate, no `log` crate. The JNI up-calls are stubbed as no-ops, the `BatteryStatus` enum is hand-rolled with `#[repr(u8)]`, and logging goes through the crate-local `info!`/`warning!`/`error!` macros (which expand to `eprintln!`). The battery skeleton can ship in the next APK build without pulling in any new dependencies.

  2195→1. **The twoyi rootfs layout is unusual: `init` lives at the rootfs root, not at `/system/bin/init`.** This was confirmed by reading `RomManager.romExist()` at line 182: `new File(getRootfsDir(context), "init")`. The cyanmint arm64 rootfs ships a custom twoyi `init` binary at the root that mknods essential devices, mounts `/proc` and `/sys`, sets environment variables, and exec's the real `/system/bin/init`. For the x86_64 build, the same pattern must be replicated — but the custom `init` must be an x86_64 ELF, not arm64. The guide includes a complete `twoyi_init.c` source (§3.8.1) that does exactly this, compiled with `gcc -static -O2 -o init twoyi_init.c`.
  2196→2. **The `sdk_gphone_x86_64-userdebug` lunch target is the right choice, not `aosp_x86_64-userdebug`.** The `sdk_gphone_*` targets include the goldfish HALs (`device/generic/goldfish-opengl`) that speak the QEMU pipe protocol twoyi's renderer also speaks. The bare `aosp_x86_64` target omits them and you'd have to add them back as a separate build. This is documented in §3.5 with the alternative targets listed for completeness.
  2197→3. **The pipe-path question has two sides: the guest creates `/dev/qemu_pipe`, the host binds `$TWOYI_ROOTFS/opengles`.** The host-side patch was already done in `AOSP_BUILD_RESULTS.md` §5.3 (`UnixStream.cpp` modified to build the path as `$TWOYI_ROOTFS/opengles{,2,3}`). The guest-side patch is new in this guide (§3.4.1) — the guest `init` must `mknod`/`bind` the `/dev/qemu_pipe` socket *before* `surfaceflinger` starts. Without both sides, the renderer can't connect.
  2198→4. **The `default.xml` manifest in the twoyi repo is the exact manifest to `repo init -m` against, not the upstream default.** Line 7 pins `revision="refs/tags/android-8.1.0_r81"`. Using `repo init -u https://android.googlesource.com/platform/manifest -b android-8.1.0_r81` is functionally identical (Option 2 in §3.2), but Option 1 (copying the twoyi `default.xml` into `.repo/manifests/twoyi.xml` and using `-m twoyi.xml`) lets you diff against future manifest changes and is the documented preferred path.
  2199→5. **The GSI path (Path B) is faster but lower fidelity.** A pre-built x86_64 GSI can be downloaded and converted in 35–55 minutes vs. 3.5–13 hours for a full AOSP build. But GSIs are built for Android 10+ and assume Treble HALs that twoyi's kernel-replacement daemon doesn't yet virtualise. The guide lists three specific caveats: no matching vendor.img (init logs many "service not found" errors), Android 10+ requires APEX (must pre-extract or patch `init.rc`), and bionic ABI mismatch (watch for `getrandom()`/`memfd_create()` syscall-number mismatches). For a first end-to-end smoke test, the GSI path is fine; for ongoing development, build from AOSP source.
  2200→6. **The `make` link step for `libart.so` can use 12+ GB RAM briefly.** On a 16 GB machine this will OOM. The guide includes the exact `fallocate` swap-creation commands (§3.6) and an `ART_BUILD_HOST_DEBUG=false` env var fallback to skip debug symbols.
  2201→7. **AOSP 8.1's host-side build tools require OpenJDK 8, despite the host running Ubuntu 22.04.** On Ubuntu 22.04 this is in the `universe` repo; on 24.04 you must install it from a PPA. The guide's `apt-get install` command (§2.3) includes `openjdk-8-jdk` and the troubleshooting table (§8) covers the "Java version 17 found, expected 8" error.
