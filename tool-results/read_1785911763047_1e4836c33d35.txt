    19→## 1. Project context — why this fork?
    20→
    21→### 1.1 The original Twoyi
    22→
    23→Twoyi (Chinese: 两仪, pronounced *"two-yi"*) is a **rootless Android-on-Android
    24→container** created by **weishu** (the author of Taichi/EdXposed). Instead of
    25→running Android in a virtual machine (like Waydroid does on Linux, or QEMU on
    26→desktop), Twoyi runs an entire second Android userland **inside one normal
    27→Android app process**. The host device does **not** need to be rooted, unlocked,
    28→or modified in any way — the container runs purely as a `targetSdk=28` APK that
    29→you install from a normal `.apk` file.
    30→
    31→The trick works because Android is, at the bottom, just a Linux process tree
    32→sitting on top of a kernel. Twoyi ships a complete Android 8.1 userland
    33→(`init`, `zygote`, `system_server`, framework JARs, ART runtime, HALs) as a
    34→folder inside the app's private data directory, then exec's `./init` from
    35→that folder the same way the real Android boot sequence does. The result is a
    36→*second* Android instance that shares the host kernel but has its own
    37→`system_server`, package manager, surface flinger, and even its own `adbd`.
    38→
    39→The original repository is **`github.com/twoyi/twoyi`** — archived in April
    40→2023 with the maintainer's note *"Due to the complexity of the project and
    41→lack of any revenue, the project has been discontinued."* At the time of
    42→archiving it had **1,911 stars** and ~100 forks.
    43→

   111→## 3. Three-layer architecture
   112→
   113→```
   114→┌──────────────────────────────────────────────────────────────────────┐
   115→│  GUEST LAYER  (rootfs, unpacked to /data/data/io.twoyi/rootfs/)      │
   116→│                                                                      │
   117→│   ./init  ─►  zygote  ─►  system_server  ─►  system services          │
   118→│                                                                      │
   119→│   - SurfaceFlinger renders to a virtual framebuffer                  │
   120→│   - OpenGL ES encoder writes GL commands to /dev/qemu_pipe           │
   121→│   - EventHub reads input from /dev/input/touch + /dev/input/key0     │
   122→│   - installd + PackageManager manage in-container APKs               │
   123→│   - adbd listens on TCP 22122 (connected to by host's libadb.so)     │
   124→└──────────────────────────────────────────────────────────────────────┘
   125→                                  ▲ ▼
   126→                          (sockets + pipes)
   127→                                  ▲ ▼
   128→┌──────────────────────────────────────────────────────────────────────┐
   129→│  NATIVE LAYER  (libtwoyi.so + libloader.so + libOpenglRender.so)     │
   130→│                                                                      │
   131→│   JNI entry (lib.rs) ─► core.rs dispatches to:                       │
   132→│     • input.rs           — virtual uinput touch + key devices         │
   133→│     • renderer_bindings  — FFI to legacy libOpenglRender.so           │
   134→│     • renderer_new/      — open-source Rust renderer (QEMU pipe)     │
   135→│   Spawns the guest: `./init` with TYLOADER env                       │
   136→└──────────────────────────────────────────────────────────────────────┘
   137→                                  ▲ ▼
   138→                              JNI boundary
   139→                                  ▲ ▼
   140→┌──────────────────────────────────────────────────────────────────────┐
   141→│  APP LAYER  (Java, package io.twoyi)                                 │
   142→│                                                                      │
   143→│   TwoyiApplication  →  ProfileManager + RomManager.ensureBootFiles   │
   144→│                     →  TwoyiSocketServer (abstract LocalSocket)      │
   145→│                                                                      │
   146→│   SettingsActivity (launcher) ──► Render2Activity                    │
   147→│       │                                                                  │
   148→│       ├─ SurfaceHolder.Callback → Renderer.init / resetWindow         │
   149→│       ├─ View.OnTouchListener   → Renderer.handleTouch                │
   150→│       └─ onBackPressed          → Renderer.sendKeycode                │
   151→│                                                                      │
   152→│   Installer       — runs libadb.so → adb connect localhost:22122     │
   153→│   TwoyiDocumentsProvider — Storage Access Framework for file share   │
   154→│   TwoyiStatusManager / TwoyiMessenger — boot latch + IPC             │
   155→└──────────────────────────────────────────────────────────────────────┘
   156→```

   160→## 4. The app layer (Java)
   161→
   162→### 4.1 Entry point — `TwoyiApplication.java`
   163→
   164→Every Android app's real entry point is `Application.attachBaseContext()`,
   165→which runs before any `Activity` is created. Twoyi uses this to do five
   166→things in strict order:
   167→
   168→1. `ProfileManager.initializeProfiles()` — make sure `profiles/default/rootfs/`
   169→   exists and that `<datadir>/rootfs` is a symlink pointing to the active
   170→   profile's rootfs.
   171→2. `RomManager.ensureBootFiles()` — the **boot hygiene** routine. It runs
   172→   four sub-steps that fix three real-world bugs: orphan container processes,
   173→   missing `/data/local/tmp`, and a DEX-level bug in Android 8.0's
   174→   `PackageInstallerSession`.
   175→3. `TwoyiSocketServer.getInstance(base).start()` — opens an abstract
   176→   SEQPACKET `LocalSocket` named `TWOYI_SOCK` and waits for the guest to
   177→   send control messages.
   178→4. `AppCenter.start(...)` — Microsoft AppCenter crash analytics.
   179→5. Compute and cache the status-bar height.
   180→
   181→### 4.2 The launcher — `SettingsActivity.java`
   182→
   183→In this fork the **Settings activity is the LAUNCHER intent**. Users land
   184→in a settings screen and must explicitly tap "Launch Container" to start
   185→`Render2Activity`. This lets users configure profiles, display size, DPI,
   186→and renderer choice *before* committing to a boot.
   187→
   188→### 4.3 The container host — `Render2Activity.java`
   189→
   190→`Render2Activity` is where the magic happens. Its lifecycle:
   191→
   192→1. **`onCreate`** — checks `TwoyiStatusManager.isStarted()`. If the guest
   193→   is already running, it calls `RomManager.reboot()` to avoid a double-boot.
   194→2. **`bootSystem()`** — checks `RomManager.romExist()`. If missing, prompts
   195→   the user to pick a `.tar` file via `ACTION_GET_CONTENT`. If present,
   196→   calls `RomManager.clearDalvikCacheIfNeeded()` and `addView(mSurfaceView)`.
   197→3. **`SurfaceHolder.Callback.surfaceCreated`** — sets renderer type and
   198→   debug mode from profile settings, computes scaled DPI, calls
   199→   `Renderer.init(surface, loaderPath, vw, vh, xdpi, ydpi, fps)`.
   200→4. **`surfaceChanged`** — `Renderer.resetWindow(...)`.
   201→5. **`onTouch`** — applies scale matrix to transform surface-space
   202→   coordinates into virtual-display-space, then `Renderer.handleTouch(...)`.
   203→6. **`onBackPressed`** — `Renderer.sendKeycode(KEYCODE_HOME)`.
   204→7. **`showBootingProcedure()`** — waits up to 60s for `BOOT_COMPLETED`.
   205→
   206→### 4.4 ROM management — `RomManager.java`
   207→
   208→The densest Java file (746 lines) contains the most clever hack: a
   209→**DEX-level binary patcher** for the guest's `services.jar`.
   210→
   211→#### 4.4.1 `ensureBootFiles()` — the boot hygiene routine
   212→
   213→```java
   214→killOrphanProcess();            // ps -ef | awk '$3==1' | xargs kill -9
   215→ensureDataLocalTmp(context);    // mkdir -p + chmod 777 on rootfs/data/local/tmp
   216→patchServicesJarForPackageInstaller(context);  // see §4.4.2
   217→// create dev/input, dev/socket, dev/maps dirs in rootfs
   218→createLoaderSymlink(context);   // <datadir>/loader64 → libloader.so
   219→saveLastKmsg(context);
   220→```
   221→
   222→#### 4.4.2 `patchServicesJarForPackageInstaller()` — DEX surgery
   223→
   224→The bug: Android 8.0 (SDK 26) `PackageInstallerSession.openWriteInternal()`
   225→calls `target.delete()` then `Os.stat(target)`. When `offsetBytes == 0` (a
   226→fresh install), the file was just deleted, so `Os.stat()` throws
   227→`ErrnoException(ENOENT)`. SDK 26 doesn't handle `ENOENT` and re-throws as
   228→`IOException("stat failed: ENOENT...")`. This breaks every in-container
   229→APK install. AOSP fixed this in SDK 27.
   230→
   231→The patch: **rewrites two bytes inside `classes.dex`** to convert the
   232→`throw v_ioe` instruction into `const/4 v_stat, 0`, mirroring the SDK 27
   233→behavior. Both instructions are exactly 2 bytes:
   234→
   235→| Original | Patched |
   236→|---|---|
   237→| `throw vN` = `0x27 0xNN` | `const/4 vM, 0` = `0x12 0x0M` |
   238→
   239→The algorithm finds the string `"stat failed: "` in the DEX string pool,
   240→locates the `throw` instruction via the `move-exception` catch handler,
   241→patches it in place, recomputes DEX checksums, and writes the patched
   242→`classes.dex` back into `services.jar`. The patch is idempotent — a flag
   243→file records the patched JAR's mod-time so it doesn't re-patch unless
   244→the JAR has been replaced.
   245→
   246→### 4.5 IPC — `TwoyiSocketServer` + `TwoyiMessenger`
   247→
   248→Host and guest communicate over an **abstract SEQPACKET LocalSocket**
   249→named `TWOYI_SOCK`. Three message prefixes:
   250→
   251→| Message | Action |
   252→|---|---|
   253→| `BOOT_COMPLETED` | `TwoyiStatusManager.markStarted()` — releases the boot latch |
   254→| `SWITCH_HOST` | toggle between host home and guest home |
   255→| `SETTINGS` | open SettingsActivity from inside the guest |
   256→
   257→> **Bug fixed in this branch:** the original `start0()` recursed into
   258→> `start()` on every `IOException` with a fixed 1-second sleep. If the
   259→> bind kept failing (e.g. SELinux denial), the cached executor pool
   260→> would accumulate one blocked thread per retry and eventually starve
   261→> the app. This branch replaces the recursion with
   262→> `EXECUTOR.submit(() -> start0(attempt+1))`, caps retries at 5, and
   263→> uses exponential backoff (1s → 2s → 4s → 8s → 16s, capped at 30s)
   264→> plus 0-50% jitter.
   265→
   266→### 4.6 App installation — `Installer.java`
   267→
   268→To install an APK *inside the guest*, Twoyi runs its own bundled
   269→`libadb.so` (a stripped Android `adb` binary) and uses `adb connect` +
   270→`adb install`. The flow:
   271→
   272→1. Spawn `libadb.so -P 9563 nodaemon server` in the background.
   273→2. `adb -P 9563 connect localhost:22122`.
   274→3. `adb -P 9563 -s localhost:22122 install -t -r --no-streaming <apk>`.
   275→   The `--no-streaming` flag is critical: streaming install pipes the
   276→   APK through `abb_exec` to a staging directory that the container's
   277→   `installd` may not have created yet.
   278→4. Parse stdout for `Success` or `Failure [...]`.
   279→
   280→### 4.7 Work Profile Support — Dynamic Data Directory
   281→
   282→**Commit:** `9c4b907` (`feat: dynamic data directory for work profile support`)
   283→
   284→Earlier twoyi hardcoded the app's data path as `/data/data/io.twoyi/` in
   285→**eight** places across the Rust crate (`core.rs`, `input.rs`,
   286→`socket_monitor.rs`). This broke when the app was installed in an Android
   287→**work profile** (managed profile / Android for Work), where the data
   288→directory is `/data/user/<uid>/io.twoyi/` instead of `/data/data/io.twoyi/`.
   289→A work-profile install is the common case for "clone a second instance of
   290→twoyi inside a corporate container", so the hardcodes were a real blocker.
   291→
   292→The fix replaces all eight hardcodes with a runtime-resolved path. The
   293→Java side asks Android for the real data dir, hands it to Rust once via
   294→JNI, and every subsequent path computation derives from that.
   295→
   296→#### 4.7.1 The Rust API
   297→
   298→`app/rs/src/core.rs` exposes a thread-safe single-assignment cell holding
   299→the data dir:
   300→
   301→```rust
   302→static DATA_DIR: OnceLock<String> = OnceLock::new();
   303→
   304→pub fn set_data_dir(dir: String) {
   305→    let _ = DATA_DIR.set(dir);
   306→}
   307→
   308→pub fn get_data_dir() -> &'static str {
   309→    DATA_DIR.get().map(|s| s.as_str()).unwrap_or("/data/data/io.twoyi")
   310→}
   311→```
   312→
   313→The `unwrap_or` fallback preserves backwards compatibility with older
   314→Java builds that don't call `setDataDir` — they continue to work exactly
   315→as before.
   316→
   317→Derived path helpers are now functions, not constants:
   318→
   319→| Helper | Returns |
   320→|---|---|
   321→| `get_rootfs_dir()` | `{data_dir}/rootfs` |
   322→| `get_log_path()` | `{data_dir}/log.txt` |
   323→| `get_touch_path()` | `{data_dir}/rootfs/dev/input/touch` |
   324→| `get_key_path()` | `{data_dir}/rootfs/dev/input/key0` |
   325→| `get_opengles_paths()` | `Vec<String>` of `{rootfs}/opengles{,2,3}` |
   326→
   327→`input.rs` replaced its `const TOUCH_PATH` / `const KEY_PATH` constants
   328→with calls into `core::get_touch_path()` / `core::get_key_path()`.
   329→`socket_monitor.rs` removed three hardcoded `opengles*` paths from the
   330→static `SOCKET_PATHS` array and rebuilds the list lazily from
   331→`core::get_opengles_paths()`.
   332→
   333→#### 4.7.2 The JNI bridge
   334→
   335→`Renderer.java` declares the new native method:
   336→
   337→```java
   338→public static native void setDataDir(String dataDir);
   339→```
   340→
   341→`Render2Activity.surfaceCreated()` calls it **before** `Renderer.init()`:
   342→
   343→```java
   344→Renderer.setDataDir(getDataDir().getAbsolutePath());
   345→Renderer.init(surface, loaderPath, vw, vh, xdpi, ydpi, fps);
   346→```
   347→
   348→`lib.rs` registers the method on `io/twoyi/Renderer` as
   349→`setDataDir(Ljava/lang/String;)V` and forwards the argument to
   350→`core::set_data_dir()`. There is no reset path — `OnceLock` is
   351→single-assignment by design; the data dir does not change for the
   352→lifetime of the process.
   353→
   354→#### 4.7.3 How `libOpenglRender.so` follows suit
   355→
   356→The AOSP-built renderer (§5.4) honors the same convention through an
   357→**environment variable** rather than a function call: `UnixStream.cpp`'s
   358→`make_unix_path()` reads `TWOYI_ROOTFS` (defaulting to
   359→`/data/data/io.twoyi/rootfs`) and builds the three `opengles{,2,3}`
   360→socket paths from it. `core.rs::init_renderer()` exports
   361→`TWOYI_ROOTFS=<data_dir>/rootfs` into the child environment when it
   362→spawns the guest's `./init`, so the renderer and the guest agree on the
   363→socket locations regardless of where the OS actually put the app's data.

   367→## 5. The native layer (Rust + AOSP C++)
   368→
   369→The native side is **three Cargo crates plus one AOSP C++ build**:
   370→
   371→| Crate | Source | Output | Purpose |
   372→|---|---|---|---|
   373→| `twoyi` | `app/rs/` | `libtwoyi.so` | JNI entry, renderer dispatch, input system, guest spawn |
   374→| `loader` | `app/rs/loader/` | `libloader.so` (+ `_new`) | Open-source replacement for legacy `libloader.so` |
   375→| `openglrenderer` | `app/rs/openglrenderer/` | `libOpenglRender.so` (Rust impl, `_new` variant) | Open-source Rust renderer (alternative to the AOSP build) |
   376→| `kr64` | `app/rs/kr64/` | `libkr64.so` (+ `kr64` binary) | **Skeleton** kernel-replacement daemon (see §5.5) |
   377→| *AOSP emugl* | `download/aosp-built/` (rebuilt from `platform/sdk` commit `7a712acc`) | `libOpenglRender.so` (final, shipped) | AOSP-source renderer with ported legacy pieces (see §5.4) |
   378→
   379→> The AOSP-source `libOpenglRender.so` (§5.4) is the **shipped** renderer;
   380→> the Rust `openglrenderer` crate (§5.3) is an alternative open-source
   381→> implementation kept around for experimentation and as the default on
   382→> x86_64 (where the legacy arm64-only blob cannot run).
   383→
   384→### 5.1 `libtwoyi.so` — `app/rs/`
   385→
   386→`JNI_OnLoad` registers 8 native methods on class `io/twoyi/Renderer`:
   387→`init`, `resetWindow`, `removeWindow`, `handleTouch`, `sendKeycode`,
   388→`setRendererType`, `setDebugRenderer`, `setDebugLogDir`.
   389→
   390→`core::init_renderer()` is the heart of the native side:
   391→
   392→1. Acquires the `ANativeWindow` from the Java `Surface`.
   393→2. Uses `RENDERER_STARTED.compare_exchange(false, true)` as a one-shot
   394→   guard. On first call:
   395→   - `input::start_input_system(virtual_width, virtual_height)` — spawns
   396→     the touch and key device threads.
   397→   - `thread::spawn` — starts the renderer (Old blob or New Rust impl).
   398→   - `Command::new("./init").current_dir("/data/data/io.twoyi/rootfs").env("TYLOADER", loader_path).spawn()`
   399→     — **this is where the guest actually boots**.
   400→3. On subsequent calls: just calls `resetSubWindow`/`reset_window` to
   401→   update the window pointer without re-booting.
   402→
   403→### 5.1.1 Input system — `input.rs`
   404→
   405→Two virtual input devices are created as **unix domain sockets** that the
   406→guest's `EventHub` connects to:
   407→
   408→- `/data/data/io.twoyi/rootfs/dev/input/touch` — multi-touch device
   409→  named `vtouch` with proper Type-B protocol (ABS_MT_SLOT, TRACKING_ID, etc.).
   410→- `/data/data/io.twoyi/rootfs/dev/input/key0` — keyboard device
   411→  named `vkey`.
   412→
   413→> **Bug fixed in this branch:** `send_key_code` previously ignored its
   414→> `keycode` argument and always emitted `KEY_BACK`, regardless of what
   415→> Java passed in. This happened to work for the only caller
   416→> (`onBackPressed → KEYCODE_HOME`) because Android falls back when
   417→> `KEY_HOME` is not in the keyboard's capability bitmap, but it broke
   418→> any future caller (volume, recents, power, etc.).
   419→>
   420→> This branch adds `android_keycode_to_linux()` mapping for the
   421→> navigation-relevant Android `KeyEvent.KEYCODE_*` constants to their
   422→> Linux `KEY_*` equivalents, and `generate_key_device()` now advertises
   423→> every supported key in `key_bitmask` via the new `set_key_bit()`
   424→> helper. The legacy `info.key_bitmask[14] = 0x1C` is removed.
   425→
   426→### 5.1.2 The PIE hack
   427→
   428→Three pieces cooperate to make `libtwoyi.so` simultaneously loadable as
   429→a JNI library and executable as a standalone binary:
   430→
   431→1. `src/interp.c` — places `/system/bin/linker64` in the `.interp` ELF section.
   432→2. `build.rs` — compiles `interp.c` via the `cc` crate.
   433→3. `build_rs.sh` — sets `RUSTFLAGS` to `-C link-arg=-pie` etc. and runs
   434→   `cargo xdk -t <abi> -o ../src/main/jniLibs build --release`.
   435→
   436→The result: `./libtwoyi.so --help` works from a shell, AND
   437→`System.loadLibrary("twoyi")` works from Java.
   438→
   439→### 5.2 `libloader.so` — open-source replacement
   440→
   441→A thin wrapper around `dlopen`/`dlsym`/`dlclose`. The build script
   442→(`build.sh`) builds it for `arm64-v8a` and (since this branch) `x86_64`,
   443→copies the output to `libloader_new.so`, and `chmod +x` so it can be
   444→executed directly as `loader64`.
   445→
   446→### 5.3 `libOpenglRender.so` — open-source Rust renderer (alternative)
   447→
   448→A standalone Rust crate exposing the same six-function C ABI as the
   449→legacy blob. Architecture mirrors `renderer_new/` inside `libtwoyi.so`:
   450→`pipe.rs` (QEMU pipe), `opengles.rs` (GL protocol), `gralloc.rs`
   451→(ANativeWindow buffer management).
   452→
   453→This is the **fallback / x86_64-default** renderer. On arm64 the AOSP
   454→build in §5.4 is preferred (it is more complete — it has the
   455→`startGBServer` graphics-buffer proxy the Rust impl doesn't yet
   456→implement). On x86_64 the Rust impl is forced on by
   457→`core.rs::effective_renderer_type()` because the legacy blob is arm64-
   458→only and the AOSP build of `startGBServer` depends on
   459→`AHardwareBuffer_recvHandleFromUnixSocket` which historically wasn't
   460→wired up on x86_64 emulator images.

   464→### 5.4 Open-Source `libOpenglRender.so` — AOSP rebuild
   465→
   466→**Commits:** `47f8335` (initial build) + `eb13449` (port missing legacy
   467→pieces). **Source:** AOSP `platform/sdk` at commit
   468→`7a712acc02282985dcd32feb81284e1f2b19ec7e`, Apache-2.0 licensed.
   469→**Artifacts:** `download/aosp-built/libOpenglRender_aosp_{arm64,x86_64}.so`.
   470→
   471→The legacy closed-source `libOpenglRender.so` shipped by upstream twoyi
   472→is a 1,059,128-byte (1.06 MB) arm64-only blob. Disassembly
   473→(`download/TWOYI_DISASSEMBLY_ANALYSIS.md`) proved via demangled symbol
   474→table cross-reference that it's a lightly-modified build of AOSP
   475→`emugl` — so we rebuilt it from source. The result is a 605–611 KB
   476→`.so` for both ABIs (an ~43% size reduction) that links the device's
   477→real system `libEGL.so` / `libGLESv1_CM.so` / `libGLESv2.so`
   478→dynamically instead of bundling desktop-GL translator libraries.
   479→
   480→#### 5.4.1 Build pipeline
   481→
   482→1. **Sparse-checkout the emugl tree** from `platform/sdk`:
   483→   `emulator/opengl/{shared,host/libs/{GLESv1_dec,GLESv2_dec,Translator,
   484→   renderControl_dec},host/tools/emugen,system}`.
   485→2. **Build the `emugen` host tool** (AOSP's wire-protocol code generator)
   486→   from 5 source files with host `g++ -std=c++11 -O2 -D_GNU_SOURCE
   487→   -include unistd.h` — the `-include unistd.h` is needed because
   488→   `main.cpp` calls `getopt()` without including the header on glibc ≥ 11.
   489→3. **Generate the decoder sources** by running `emugen -D` three times:
   490→   `renderControl`, `gl`, `gl2`. Each invocation produces six files
   491→   (`<base>_dec.{cpp,h}`, `<base>_opcodes.h`,
   492→   `<base>_server_context.{cpp,h}`, `<base>_server_proc.h`).
   493→4. **Write the Android compat shim layer** under `compat/`. The AOSP
   494→   emugl source includes several Android platform-private headers that
   495→   the NDK doesn't ship. Each is reimplemented with POSIX primitives:
   496→
   497→   | Header | Implementation |
   498→   |---|---|
   499→   | `cutils/threads.h` | `pthread_key_t` + `pthread_mutex_t` |
   500→   | `cutils/atomic.h` | `__atomic_*` GCC/Clang builtins |
   501→   | `cutils/log.h` | `__android_log_print` from `liblog` |
   502→   | `cutils/sockets.h` | raw `AF_UNIX`/`AF_INET` sockets |
   503→   | `utils/{threads,Errors,Vector,List,String8,KeyedVector,RefBase}.h` | `pthread` + `std::vector` / `std::list` / `std::string` / `std::map` wrappers |
   504→
   505→5. **Apply the twoyi-specific patches** (see §5.4.2 below).
   506→6. **Build with CMake + NDK r27c** (`clang 18.0.3`, `cmake 3.22.1`):
   507→   `-DANDROID -DHAVE_ANDROID_OS=1 -DWITH_GLES2 -include assert.h -O2
   508→   -fno-rtti -std=c++11`. **No `-fvisibility=hidden`** — the legacy blob
   509→   exports all symbols, and we need the C-ABI entry points visible.
   510→   Stripped with `llvm-strip -x` (keep dynamic symbols only).
   511→

   602→### 5.5 Kernel Replacement Daemon (`kr64`) — skeleton
   603→
   604→**Commit:** `570e95e` (`feat(kr64): kernel replacement daemon skeleton`).
   605→**Source:** `app/rs/kr64/` (3,084 lines across 9 files).
   606→**Design doc:** `download/KR64_SKELETON.md`.
   607→
   608→This is the **Rust port of Virtual Master's `libkr64.so`** — the most
   609→architecturally significant piece of VM's container model (see §9 for
   610→the full reverse-engineering). In VM, `libkr64.so` is a standalone ELF
   611→executable disguised as a `.so` (with `.interp` pointing at a custom
   612→`libkrloader64.so`); the kernel exec's it, and it materialises a
   613→per-VM virtual `/dev` tree, installs a seccomp filter, emulates `/proc`,
   614→sets up the mount namespace, then `execve`s the guest's
   615→`/system/bin/init`. Without an equivalent daemon, twoyi can only boot
   616→its ancient custom 8.1 ROM — it cannot boot a Treble GSI (see §10).
   617→
   618→The current `kr64` crate is a **skeleton**: it compiles, has 26 passing
   619→unit tests, and a working end-to-end smoke test on Linux. It is **not**
   620→integrated into the build yet (it is not a member of the parent
   621→workspace; `build_rs.sh` does not yet build it).
   622→
   623→#### 5.5.1 Files
   624→
   625→| File | Lines | Purpose |
   626→|------|-------|---------|
   627→| `Cargo.toml` | 39 | `crate-type = ["cdylib", "rlib"]` + `[[bin]]`. Deps: `libc` only (no `log`, `once_cell`, `nix` — per task spec). Build-dep: `cc` for `interp.c`. |
   628→| `build.rs` | 88 | Compiles `interp.c`; emits PIE linker flags (`-Wl,-e,kr64_main`, `-Wl,--undefined=interp`). Android-only: `--dynamic-linker=/system/bin/linker64`. |
   629→| `interp.c` | 40 | Forces a `.interp` section (PT_INTERP) so `libkr64.so` is directly executable via the PIE-as-cdylib trick. On Android: `/system/bin/linker64`. On Linux host: no override (so `cargo test` runs). |
   630→| `src/main.rs` | 38 | Binary entry point. Thin wrapper around `kr64::run(args)`. |
   631→| `src/lib.rs` | 652 | Crate root. `Config` struct, `parse_args()`, `run()` daemon entry point, `kr64_main` cdylib entry, `info!` / `warning!` / `error!` macros (eprintln-based, no `log` crate). |
   632→| `src/devices.rs` | 405 | Virtual `/dev` tree: `qemu_pipe`, `touch`, `key0`, `event`, `gb`, `gb2` via `UnixListener::bind`. |
   633→| `src/seccomp.rs` | 831 | BPF seccomp filter + SIGSYS handler. Allow ~80 syscalls, trap `mount` / `umount2` / `swapon` / `reboot` / etc., kill on `ptrace` / `kexec_load` / `init_module` / `pivot_root`. |

   636→
   637→#### 5.5.2 What it does at runtime
   638→
   639→```
   640→kr64 --rootfs <fs_dir> --data-dir <data_dir> [--vmid N]
   641→     [--width W --height H --dpi D] [--init /system/bin/init]
   642→     [--no-seccomp] [--no-namespaces] [--rw-rom] [--log-level debug]
   643→```
   644→
   645→1. `parse_args()` builds a `Config`.
   646→2. `devices::create_all_devices()` binds the six MVP Unix sockets:
   647→   `{rootfs}/dev/qemu_pipe`, `{rootfs}/dev/input/touch`,
   648→   `{rootfs}/dev/input/key0`, `{data_dir}/dev/event`, `{rootfs}/dev/gb`,
   649→   `{rootfs}/dev/gb2`.
   650→3. `proc_emu::populate_proc()` writes synthesised static files into
   651→   `{rootfs}/proc/`.
   652→4. `run()` `fork()`s. The child calls `mount_mgr::setup_mounts()` →
   653→   `seccomp::install()` → `execve(init_path)`. The parent runs the
   654→   device-accept threads and `waitpid()`s on the child.
   655→
   656→#### 5.5.3 The PIE-as-cdylib trick (matches VM)
   657→
   658→`libkr64.so` is **directly executable** via the same trick as
   659→`libtwoyi.so` (§5.1.2) — `interp.c` puts `/system/bin/linker64` in the
   660→`.interp` section, and `build.rs` sets `-Wl,-e,kr64_main` so the linker
   661→entry point is `kr64_main` (the cdylib entry exported by `lib.rs`).
   662→This matches VM's approach exactly, except twoyi uses the **system**
   663→`linker64` instead of a custom `libkrloader64.so` — simpler, but loses
   664→VM's elevated-privilege early bootstrap.
   665→
   666→On the Linux host (for `cargo test`), `interp.c`'s `#ifdef __ANDROID__`
   667→gate emits a plain `.rodata` symbol instead of overriding `.interp`,
   668→so the test binary runs under the default `/lib64/ld-linux-x86-64.so.2`.
   669→
   670→#### 5.5.4 Seccomp + SIGSYS handler
   671→
   672→The BPF program is structured as:
   673→
   674→```
   675→  1. ld arch                  // load audit arch
   676→  2. jeq EXPECTED_ARCH, jt=0, jf=N     // wrong arch → kill
   677→  3. ld nr                    // load syscall number
   678→  4. for each allowed syscall: jeq + ret ALLOW
   679→  5. for each trapped syscall: jeq + ret TRAP
   680→  6. for each killed  syscall: jeq + ret KILL_PROCESS
   681→  7. ret ALLOW                // default: allow
   682→  8. ret KILL_PROCESS         // wrong-arch target
   683→```
   684→
   685→Uses `jt=0, jf=1` (fall-through on match, skip 1 on miss) so the 8-bit
   686→`jt` / `jf` offsets never overflow regardless of set size.
   687→
   688→The SIGSYS handler reinterprets the `*mut siginfo_t` through a
   689→`#[repr(C)] struct SigsysSiginfo` (mirroring the kernel's
   690→`__sifields.__sigsys` layout — `signo`, `errno`, `code`, `_pad`,
   691→`call_addr`, `syscall`, `arch`) to read `si_syscall` (the `libc` crate
   692→doesn't expose it as a method). It then classifies the syscall, sets
   693→the return-value register (`x0` on aarch64, `rax` on x86_64), and
   694→advances PC past the syscall instruction (4 bytes on aarch64, 2 bytes
   695→on x86_64). Trapped syscalls currently return 0 (success); the
   696→production version needs to dispatch `mount` → `mount_mgr::bind_mount()`,
   697→`umount2` → unbind, `reboot` → `-EPERM`, etc.
   698→
   699→#### 5.5.5 What's NOT here yet (follow-ups)
   700→
   701→1. **Full device inventory** — VM creates 20+ devices (`/dev/vmproc`,
   702→   `/dev/__kmsg__`, `/dev/__properties__`, `/dev/ashmem`,
   703→   `/dev/socket/*`, `/dev/block/vdc`, `/dev/fuse`, netlink sockets, …).
   704→   Skeleton has 6.
   705→2. **Binder virtualisation** — per-VM `/dev/binder` + Java-side
   706→   `IActivityManager` proxy. Not started. (Hardest piece — see §10.2.)
   707→3. **`/proc` dynamic files** — `/proc/self/maps`, `/proc/self/status`,
   708→   `/proc/<pid>/…` require shadowhook interception of `open` / `openat`.
   709→   Skeleton uses static files only.
   710→4. **Per-syscall emulation** — `seccomp::emulate_syscall()` returns 0
   711→   for all trapped syscalls.
   712→5. **`mknodat`-based socket creation** — skeleton uses
   713→   `UnixListener::bind()` (creates the socket file as a side effect);
   714→   VM uses `mknodat(S_IFSOCK)` + `bind()` (requires `CAP_MKNOD`).
   715→6. **GSI ROM extractor** — the daemon expects the rootfs to already
   716→   contain `/system`, `/vendor`, etc.
   717→7. **Workspace integration** — `kr64` is not yet a member of the
   718→   parent `twoyi` Cargo workspace; `build_rs.sh` doesn't build it yet.

   724→### 6.1 ROM layout
   725→
   726→Once unpacked, `rootfs/` is a fairly standard Android system tree:
   727→
   728→```
   729→rootfs/
   730→├── init                    ← the binary core.rs exec's
   731→├── init.rc                 ← boot script
   732→├── rom.ini                 ← ROM metadata (author, version, md5, code)
   733→├── system/framework/services.jar   ← patched by RomManager (§4.4.2)
   734→├── vendor/default.prop     ← host locale + timezone + DPI
   735→├── data/local/tmp/         ← created by ensureDataLocalTmp (chmod 777)
   736→├── data/dalvik-cache/      ← wiped on host OTA (clearDalvikCacheIfNeeded)
   737→├── dev/input/{touch,key0}  ← unix sockets (input.rs)
   738→└── sdcard/                 ← exposed via TwoyiDocumentsProvider
   739→```

   742→

   744→plus twoyi-specific forks in the `twoyi/*` GitHub organization
   745→(`Magisk`, `Superuser`, `platform_art`, `system_vold`,

   751→### 6.3 Boot sequence (end-to-end)
   752→
   753→```
   754→T+0ms    Application.attachBaseContext
   755→         ├─ ProfileManager.initializeProfiles
   756→         ├─ RomManager.ensureBootFiles
   757→         ├─ TwoyiSocketServer.start (async)
   758→T+100ms  SettingsActivity.onCreate (user sees settings)
   759→T+???    User taps "Launch Container"
   760→T+0      Render2Activity.onCreate
   761→         ├─ reset TwoyiStatusManager
   762→         ├─ load profile display settings (W×H×DPI)
   763→         ├─ setupSurfaceViewLayout (letterboxing)
   764→         └─ bootSystem
   765→             ├─ RomManager.romExist? yes → continue
   766→             ├─ clearDalvikCacheIfNeeded (~100ms if cache exists)
   767→             └─ mRootView.addView(mSurfaceView, 0)
   768→T+50ms   surfaceCreated
   769→         └─ Renderer.init(...)  → JNI → core::init_renderer
   770→             ├─ input::start_input_system (touch + key threads)
   771→             ├─ thread::spawn (renderer thread)
   772→             └─ Command::new("./init").spawn()  ← GUEST BOOTS
   773→T+200ms  Guest init starts: parse init.rc, mount tmpfs, start ueventd,
   774→         start zygote, fork system_server, start core services...
   775→T+3-30s  Guest sends "BOOT_COMPLETED" over TWOYI_SOCK
   776→         → boot latch released → user sees guest home screen
   777→```

   839→
   840→GitHub Codespaces run on Azure VMs that do NOT expose `/dev/kvm` to the

   842→sources confirm this:
   843→
   844→- [devcontainers/images#884](https://github.com/devcontainers/images/issues/884)
   845→- [dotnet/runtime#77851](https://github.com/dotnet/runtime/issues/77851)
   846→- [bgplabs.net/4-codespaces](https://bgplabs.net/4-codespaces)
   847→- [github/community#160591](https://github.com/orgs/community/discussions/160591)
   848→
   849→`check-kvm.sh` runs on codespace creation to verify this empirically —
   850→if `/dev/kvm` is unavailable, the test scripts use redroid (Android-in-
   851→container, no KVM needed) instead.

   961→
   962→**APK analyzed:** `com.clone.android.dual.space` v3.2.53
   963→(`Virtual Master` — a competing closed-source rootless
   964→Android-on-Android container, much more advanced than twoyi).
   965→
   966→Six reverse-engineering reports (totalling ~4,000 lines) live under
   967→`download/`: `VM_ROM_ANALYSIS.md`, `VM_JAVA_ANALYSIS.md`,
   968→`VM_DEEP_DISASSEMBLY.md`, `VM_KR64_ANALYSIS.md`,

   972→### 9.1 What VM does that twoyi doesn't
   973→
   974→| Capability | Twoyi (this branch) | Virtual Master v3.2.53 |
   975→|---|---|---|
   976→| **Kernel-replacement daemon** | ❌ Skeleton only (§5.5) | ✅ `libkr64.so` — standalone ELF disguised as `.so`, custom `libkrloader64.so` interpreter, 20+ virtual devices, mount namespaces, seccomp+SIGSYS, `/proc` emulation, shadowhook v1.0.8 (ByteDance) |
   977→| **Binder virtualization** | ❌ Uses host binder | ✅ Per-VM `/vm%d/dev/binder` + Java `IActivityManager` proxy via `BinderService.setupBinder()` JNI |

  1001→
  1002→Decoded from `libkr64.so`'s XOR-obfuscated `.data` section (per-string
  1003→keys, recovered via brute-force single-byte XOR scan). Each socket path
  1004→lives under `<vmDataDir>/vm/vm%d/dev/`:

  1006→| Device | Path | Purpose |
  1007→|---|---|---|

  1010→| Daemon log | `/dev/__krlog__` | `libkr64`'s own log stream |
  1011→| Property area | `/dev/__properties__` | mmap'd system properties |
  1012→| Shared memory | `/dev/ashmem`, `/dev/ashmemsim` | Binder transactions, SurfaceFlinger |
  1013→| Mount markers | `/dev/.busybox`, `/dev/.coldboot_done` | Boot-progress sentinels |
  1014→| Process-pid socket | `/dev/socket/process_pid` | Per-VM PID coordination |
  1015→| Logger sockets | `/dev/socket/logdw`, `/dev/socket/logdr` | `logd` wire interface |
  1016→| Touch input | `/dev/input/touch` | Same path as twoyi |
  1017→| QEMU pipe | `/dev/qemu_pipe` (Android 7), `/dev/goldfish_pipe` (Android 11) | GL transport |
  1018→| Graphics buffer | `/dev/gb`, `/dev/gb2` (Android 11 only) | `AHardwareBuffer` FD-passing proxy |
  1019→| Block device | `/dev/block/vdc` (Android 11) | Virtual disk |
  1020→| FUSE | `/dev/fuse` (Android 11) | Filesystem-in-userspace |
  1021→| HAL power supply | `/dev/hal/power_supply%s` (Android 11) | Battery HAL shim |
  1022→| Binder | `/vm%d/dev/binder` | Per-VM binder driver proxy |
  1023→| Netlink sockets | `/vm%d/dev/netlink_server`, `/vm%d/dev/netlink_client/nl_dhcp_%d_%d`, `/vm%d/dev/netlink_client/netdevice_%d_%d` | Network HAL |
  1024→
  1025→Twoyi's `kr64` skeleton (§5.5) currently materialises 6 of these
  1026→(`qemu_pipe`, `touch`, `key0`, `event`, `gb`, `gb2`). The full
  1027→inventory is a follow-up task.

  1029→### 9.4 The VM boot state machine
  1030→
  1031→`com.android.vmcore.VMInstance.f8940WWoWWo` — 11 states:
  1032→
  1033→```
  1034→-5 = STOPPING            0 = STOPPED          4 = BOOTING
  1035→-4 = BOOT_FAILED         1 = CHECKING_ENV     5 = RUNNING
  1036→-3 = SVC_FAILED           2 = INSTALLING       6 = BOOT_COMPLETED
  1037→-2 = INSTALL_FAILED      3 = STARTING_SVC     7 = SHUTDOWN
  1038→-1 = ENV_FAILED
  1039→```
  1040→
  1041→Each transition fires an EventBus `VMStatusEvent`. The two task
  1042→pipelines:
  1043→
  1044→- **SetupTasks** (state 2): `PrepareFs → InstallFs → FixFs → CleanFs →
  1045→  ChmodFs → CleanCache → FixCPUArch → LoadVMProp`.
  1046→- **StartupTasks** (state 4): `ApplyOverlays → Bug1..Bug8 → CleanLog →
  1047→  Superuser → Xposed → GooglePlay → Magisk → BuildTmpfs → BuildVMProp →
  1048→  BuildExecPath`.
  1049→
  1050→Then `startOS(vmId, dpi, kernelPath)` JNI call (kernelPath = `dataDir +
  1051→"/lib64"`).
  1052→
  1053→> Twoyi's implicit boot-log-line approach (see §4.5) is technically
  1054→> sufficient but provides no programmatic state to the UI. Adopting
  1055→> VM's explicit state machine is recommended (see §11.4 below).
  1056→
  1057→### 9.5 The three IPC channels to the guest
  1058→
  1059→| Channel | Mechanism | Used for |
  1060→|---|---|---|
  1061→| A | Unix domain socket at `<vmDataDir>/dev/event` (Java `LocalServerSocket`) | 25+ event types (`BOOT_COMPLETED`, `SHUTDOWN`, `START_INSTALL_APP`, `CLIPBOARD_DATA`, `SEND_KEY_EVENT`, `EXECUTE_COMMAND`, …). Messages are UTF-8 strings of form `eventName` + backtick + `payload`. |
  1062→| B | Binder virtualization via `BinderService.setupBinder(vmId, ...)` JNI | Creates per-VM `/vm%d/dev/binder`, proxies host's `android.app.IActivityManager` IBinder through a Java `Proxy` so the guest's `servicemanager` thinks it's talking to a real OS. |
  1063→| C | `/dev/qemu_pipe` (native-only) | GL transport — same mechanism as twoyi. |
  1064→
  1065→Twoyi has channel C and a stripped-down channel A (only `BOOT_COMPLETED`,
  1066→`SWITCH_HOST`, `SETTINGS`). Twoyi does not have channel B at all.
  1067→
  1068→### 9.6 Key correction to earlier analysis
  1069→
  1070→The earlier `VIRTUAL_MASTER_ANALYSIS.md` claimed VM uses `NativeActivity`
  1071→and `TextureView`. The deeper `VM_JAVA_ANALYSIS.md` corrected this: VM
  1072→uses **`VMDisplayActivity extends BaseActivity`** (a regular
  1073→`AppCompatActivity`) and **`SurfaceView`**. The earlier claim was based
  1074→on the presence of `ANativeActivity_onCreate` in `libvm.so`'s exports —
  1075→but that symbol is just NDK app-glue boilerplate that doesn't get
  1076→called.

  1080→## 10. GSI Boot Roadmap
  1081→
  1082→**Definitive plan:** `download/GSI_BOOT_PLAN.md` (997 lines, 9
  1083→sub-projects with file paths, acceptance criteria, and a recommended
  1084→milestone order). This section is the executive summary.
  1085→
  1086→### 10.1 What a GSI is
  1087→
  1088→A **GSI (Generic System Image)** is an Android `system.img` conforming
  1089→to the Treble HAL interface contract (introduced in Android 8.0,
  1090→Project Treble). It ships `system.img` + `product.img` +
  1091→`system_ext.img` (and a `boot.img` for kernel+ramdisk). The `vendor.img`
  1092→must be supplied by the device. In a container, we reuse the host
  1093→kernel — but we still must synthesise everything else a Treble boot
  1094→expects (`/dev/binder`, `/dev/hwbinder`, `/dev/vndbinder`,
  1095→`/dev/ashmem` or `/dev/dm-user`, `/dev/__properties__`, `init`,
  1096→`servicemanager`, `surfaceflinger`, a gralloc HAL, the HALs declared in
  1097→`/vendor/etc/vintf/manifest/*.xml`, and a procfs/sysfs that look real).
  1098→
  1099→### 10.2 The 9 sub-projects
  1100→
  1101→| § | Sub-project | Twoyi location | Status |
  1102→|---|---|---|---|
  1103→| 3.1 | **Kernel-replacement daemon** | `app/rs/kr64/` (§5.5) | 🟡 Skeleton done (6 of 20+ devices) |
  1104→| 3.2 | **Binder virtualization** | `app/rs/kr64/src/binder_proxy.rs` + Java `BinderService.java` (new) | 🔴 Not started (hardest piece) |
  1105→| 3.3 | **Graphics buffer management** (`/dev/gb` + `/dev/gb2`) | `app/rs/kr64/src/gb.rs` (new) + the ported `startGBServer` in `libOpenglRender.so` (§5.4.3) | 🟡 Skeleton done in renderer; not wired to `FrameBuffer::createColorBuffer` yet |
  1106→| 3.4 | **Seccomp filter** | `app/rs/kr64/src/seccomp.rs` | 🟡 Skeleton done (filter + SIGSYS handler exist; `emulate_syscall()` returns 0) |
  1107→| 3.5 | **`/proc` emulator** | `app/rs/kr64/src/proc_emu.rs` | 🟡 Skeleton done (static files only; no shadowhook interception) |
  1108→| 3.6 | **Inline hooking** | `app/rs/kr64/src/hooks.rs` (new) — LD_PRELOAD for MVP, simpler than shadowhook | 🔴 Not started |

  1127→| 2–3 | GSI extractor + GSI init patcher |

  1129→| 4–5 | `/dev/gb` + `/dev/gb2` (wire §5.4.3's `GraphicBuffer::Main` into `FrameBuffer::createColorBuffer`) |
  1130→| 5–6 | Stub HALs → boot to launcher |
  1131→| 6–8 | `/proc` emulator + seccomp |
  1132→| 8–12 | Binder virtualization (the hardest piece) |
  1133→| 12+ | Audio / camera / sensors / gps / wifi / telephony / bluetooth HAL proxies |
  1134→
  1135→**Total estimate:** 8–12 weeks for an MVP that boots to launcher; 16–24
  1136→weeks for full VM parity.
  1137→
  1138→### 10.5 x86_64 path
  1139→
  1140→All infrastructure is in place on x86_64:
  1141→
  1142→- Codespace has KVM (AMD EPYC 7763, EastUs, seccomp:0).
  1143→- AOSP x86_64 renderer is built (605 KB — §5.4).
  1144→- Rust crates already build for x86_64.
  1145→- x86_64 GSIs are downloadable from `ci.android.com`.
  1146→
  1147→The x86_64 boot flow is the same as arm64 except the GSI must be x86_64
  1148→(there is no binary translation in the container path — twoyi shares the
  1149→host kernel).
  1150→
  1151→> A separate **KVM alternative** is documented in GSI_BOOT_PLAN §5.5:
  1152→use `crosvm` or QEMU to boot the GSI in a real VM. Much simpler
  1153→conceptually but requires an Android-common kernel and a different
  1154→overall architecture. Out of scope for the container path.
  1155→

  1247→## 12. Setting up a development environment
  1248→
  1249→```bash
  1250→# 1. Clone the fork
  1251→git clone https://github.com/Disable-OP/twoyi.git
  1252→cd twoyi
  1253→
  1254→# 2. EITHER set up locally:
  1255→curl https://sh.rustup.rs -sSf | sh
  1256→rustup target add aarch64-linux-android x86_64-linux-android
  1257→cargo install cargo-xdk
  1258→# Install Android Studio with SDK Platform 31 + NDK r27c
  1259→# Download rootfs.7z from cyanmint releases → app/src/main/assets/rootfs.7z
  1260→./gradlew assembleRelease
  1261→
  1262→# 2. OR spin up a Codespace:
  1263→#    - On GitHub: Code → Codespaces → Create codespace on main (or this branch)
  1264→#    - Select 4-core / 16 GB / 32 GB machine
  1265→#    - Wait ~5 min for postCreateCommand to finish
  1266→#    - Run: ./.devcontainer/scripts/check-kvm.sh
  1267→#    - Run: ./.devcontainer/scripts/run-redroid.sh
  1268→#    - Run: ./.devcontainer/scripts/test-twoyi.sh
  1269→#    - Run: ./.devcontainer/scripts/analyze-screenshots.sh
  1270→
  1271→# 3. (Optional) Build only one ABI for faster iteration:
  1272→./gradlew assembleRelease -Pabis=arm64-v8a
  1273→
  1274→# 4. (Optional) Rebuild only the Rust side:
  1275→cd app/rs && ./build_rs.sh --release arm64-v8a x86_64
  1276→```
