    11→## TL;DR
    12→
    13→Virtual Master is a fully-Java-orchestrated Android-in-Android container that boots a downloaded AOSP/Treble ROM inside a per-VM data directory. The whole stack is driven from `com.android.vmapp.VMApp` (Application) → `com.android.vmcore.VMManager` → `com.android.vmcore.VMInstance` (the per-VM state machine), with a single native library `libvm.so` doing all the heavy lifting.
    14→
    15→**Key architectural facts (correcting/refining the previous disassembly reports):**
    16→
    17→1. **No `NativeActivity`** — Virtual Master uses its own `VMDisplayActivity extends BaseActivity`. A `SurfaceView` (NOT `TextureView`) is created programmatically and the `android.view.Surface` object is passed to the native renderer through a custom JNI API `DisplayService.nativeAddSurface(ptr, surfaceId, surface, w, h, rotation)`. This is a **per-VM renderer pointer pattern**, NOT the AOSP emugl `initOpenGLRenderer()`/`createOpenGLSubwindow()` global-singleton pattern used by twoyi.
    18→
    19→2. **Single native library:** `System.loadLibrary("vm")` loads `libvm.so`. ALL JNI bindings — display, input, audio, HAL, binder virtualization, OS boot, process management — live in this one `.so`.
    20→
    21→3. **Boot sequence is a Java state machine.** `VMInstance.f8940WWoWWo` walks 11 states (`-5..7`); each state transition fires an `EventBus` `VMStatusEvent` that the UI subscribes to. The actual OS launch is a single JNI call: `VMInstance.startOS(int vmId, int dpi, String libPath)`.
    22→
    23→4. **ROM is downloaded and decrypted on the fly** with `AES/ECB/PKCS5Padding` (key `%z89aviCM0KkbEs9`) or XOR (same key) — chosen by the URI's `e=` query parameter. The downloaded stream is piped through `CipherOutputStream` so the cleartext never touches disk; it's then extracted (ZIP or 7z) directly into the VM's `/fs` directory.
    24→
    25→5. **Two IPC channels to the guest:**
    26→   - **Unix domain socket** at `<vmDataDir>/dev/event` (Java side: `LocalServerSocket`). The guest connects and exchanges UTF-8 strings of the form `eventName`+backtick+`payload`. 25+ event types (`BOOT_COMPLETED`, `SHUTDOWN`, `START_INSTALL_APP`, `CLIPBOARD_DATA`, `SEND_KEY_EVENT`, `EXECUTE_COMMAND`, …).
    27→   - **Binder virtualization** via native `setupBinder(vmId, ...)`. This installs a per-VM `/vm%d/dev/binder` and proxies the host's `android.app.IActivityManager` IBinder through a Java `Proxy` so the guest's `servicemanager` thinks it's talking to a real OS.

    31→## 1. Application class & native library load
    32→
    33→**File:** `com/android/vmapp/VMApp.java`
    34→
    35→### `attachBaseContext(Context)` — hidden-API bypass
    36→
    37→On Android 9+ (SDK ≥ 28), Virtual Master loads a tiny embedded DEX (base64-encoded, ~3 KB) that contains `me.weishu.reflection.BootstrapClass.exemptAll()` — the well-known [FreeReflection](https://github.com/tiann/FreeReflection) trick. The dex is written to `codeCacheDir/<timestamp>.dex`, loaded with `DexFile.loadClass()`, then `exemptAll()` is reflectively invoked. This bypasses the hidden-API restrictions on `dalvik.system.*` and `android.os.Process.*` calls that VMInstance/DisplayService/BinderService need.
    38→
    39→### `onCreate()` — Java-side initialization order
    40→
    41→1. Initialize `SharedPreferences` (device-protected storage on API 24+)
    42→2. Set app locale, Firebase RemoteConfig defaults
    43→3. Initialize Google Ads SDK (`m7.f15885WWWW = new m7(this, ...)`)
    44→4. Initialize billing (`C1603WWWWWWWW`) and register a `ConnectivityManager.NetworkCallback`
    45→5. Register an `IntentFilter` for `PACKAGE_ADDED/REMOVED/REPLACED` with `dataScheme=package`
    46→6. Initialize Crashlytics (`C2467WWWWWWWW.m13936WWWWoWWWWo().m13950WWWW(this)`)
    47→7. **Load the native library** (synchronized on `VMManager.class`):
    48→   ```java
    49→   System.loadLibrary("vm");                   // decoded from StringFog
    50→   VMManager.f8948WWWWWWWW = new VMManager(this);
    51→   ```
    52→8. For each existing `VMInstance` (read from data dir), create a `VMExtension` (per-VM lifecycle helper) and stash it in `SparseArray<VMExtension>`
    53→9. On Android 12+ (SDK ≥ 31), additionally set up `o2.WoWo` (a privacy/notification module)
    54→10. Register `ComponentCallbacks` and activity-lifecycle callbacks for memory management
    55→
    56→The base64 string for `me.weishu.reflection.BootstrapClass` is on line 134 of `VMApp.java` (`byte[] decode = Base64.decode(...)`) — it is one of the longest lines in the file (~3,961 chars). To extract: copy the base64 string between `Base64.decode("` and `")` on that line.

    60→## 2. The launch flow — from launcher icon to first rendered frame
    61→
    62→### 2.1 The four `VMStartActivityN` classes
    63→
    64→The `AndroidManifest.xml` declares four almost-identical activities:
    65→
    66→```xml
    67→<activity android:name="com.android.vmapp.vm.VMStartActivity0"
    68→          android:taskAffinity=".vm0" android:launchMode="singleTask"/>
    69→<activity android:name="com.android.vmapp.vm.VMStartActivity1"
    70→          android:taskAffinity=".vm1" android:launchMode="singleTask"/>
    71→<activity android:name="com.android.vmapp.vm.VMStartActivity2"
    72→          android:taskAffinity=".vm2" android:launchMode="singleTask"/>
    73→<activity android:name="com.android.vmapp.vm.VMStartActivity3"
    74→          android:taskAffinity=".vm3" android:launchMode="singleTask"/>
    75→```
    76→
    77→The launcher dispatches on `vmId % 4` so that each VM gets its own task affinity (avoids Android's single-task collisions). The static helper is `VMStartActivity0.m5016WWWW(Context, int vmId, boolean forceBoot, boolean restart)` — it picks the right activity class, stuffs the extras `vm_id`, `force_boot`, `restart` into the Intent, and starts it.
    78→
    79→### 2.2 The state machine
    80→
    81→`VMInstance` has a single int field `f8940WWoWWo` that holds the VM state. State values (decoded from `VMStartActivity0.onVMStatusEvent()` string-resource lookups and `VMInstance.m5100WoWo()`):
    82→
    83→| State | Name (UI string)              | Meaning                                                  |
    84→|------:|-------------------------------|----------------------------------------------------------|
    85→| -5    | (stopping)                    | Shutting down — `VMStatusEvent(-5, …)` posted            |
    86→| -4    | `vm_status_start_failed`      | Boot task returned false (kernel path / prop error)      |
    87→| -3    | `vm_status_start_svc_failed`  | HAL/Display/Input/Audio/Netlink service start failed     |
    88→| -2    | `vm_status_install_failed`    | Setup task (PrepareFs/InstallFs/…) returned false        |
    89→| -1    | `vm_status_env_failed`        | Pre-flight check failed (CPU/SDK/path)                   |
    90→|  0    | `STOPPED`                     | Cold — never started, or fully shut down                 |
    91→|  1    | `vm_status_checking_env`      | Pre-flight checks (CPU arch, data-dir path, SDK version) |
    92→|  2    | `vm_status_installing_N`      | Running setup pipeline (PrepareFs → LoadVMProp)          |
    93→|  3    | `vm_status_starting_svc`      | Starting HAL/Input/Audio/Display/Netlink services        |
    94→|  4    | `vm_status_starting`          | Running startup pipeline (ApplyOverlays → BuildExecPath) |
    95→|  5    | `vm_status_os_booting`        | `startOS()` JNI returned; waiting for `BOOT_COMPLETED`   |
    96→|  6    | `vm_status_os_ready1`         | Guest signalled `BOOT_COMPLETED` via event socket        |
    97→|  7    | `vm_status_os_ready2`         | Guest signalled `SHUTDOWN` (clean exit)                  |
    98→
    99→### 2.3 Boot sequence (in `VMInstance.m5100WoWo(boolean restart)`)
   100→
   101→The method runs on a dedicated `HandlerThread` (named `"VMInstance"`, see `m5098WoWo()`). Step by step:
   102→
   103→```
   104→state 0 (STOPPED) → state 1 (STARTING)
   105→  ├─ CPU check: CPUUtils.m5240/m5242 (must be armv7-a/armv8-a)
   106→  ├─ Data-dir check: dataDir must start with "/data/user/" or "/data/data/"
   107→  ├─ SDK check: Build.VERSION.SDK_INT >= RomConfig.minimum_sdk_int
   108→  ├─ App-version check: app version >= RomConfig.minimum_app_ver
   109→  ├─ clearZombieProcess + killProcess loop (m5056) — clean up any stale guest pids
   110→  │
   111→  └─ If ROM changed or first boot → state 2 (INSTALLING):
   112→       │
   113→       │   Sequential setup pipeline (each task returns boolean):
   114→       │   ├─ PrepareFsTask   — chmod the existing fs dir to DEFAULT_LINK_PERM
   115→       │   ├─ InstallFsTask   — download & extract the ROM (see §4)
   116→       │   ├─ FixFsTask       — fix fs paths/symlinks
   117→       │   ├─ CleanFsTask     — remove stale cache/tmp files
   118→       │   ├─ ChmodFsTask     — NativeHelper.chmodRecursively(fsDir, 0xA1FF)
   119→       │   ├─ CleanCacheTask  — clear caches
   120→       │   ├─ FixCPUArchTask  — rewrite /system/bin/app_process{32,64}_xposed shims
   121→       │   └─ LoadVMPropTask  — parse /system/build.prop into VMConfig.f8870 (HashMap)
   122→       │
   123→       └─ Set f8919WWWW=true (installed flag), persist RomConfig to prefs
   124→       │
   125→       └─ BinderService setup (state ~3 implicitly):
   126→       │   ├─ BinderService.m5206WWWWoWWWWo(vMApp, vmId)
   127→       │   │     ├─ Get IBinder for android.app.IActivityManager (via reflection)
   128→       │   │     ├─ Wrap it with a Java Proxy that intercepts getCallingPid()
   129→       │   │     ├─ Call native setupBinder(vmId, …, "com.android.vmcore.service.IBinderService", parcelledIntent)
   130→       │   │     └─ bindService(BinderService.class) — wait up to 5s for onServiceConnected
   131→       │   │
   132→       │   ├─ new InputService(this) → nativeStartService  (touch input)
   133→       │   ├─ new AudioService(this) → start              (microphone + audio)
   134→       │   ├─ new HALManager(this)   → startHALMgr        (camera/sensor/location/wifi/phone/battery)
   135→       │   ├─ new DisplayService(this) → nativeStartService(w, h)
   136→       │   ├─ new NetlinkManager(this) → start             (virtual network tun0)
   137→       │   └─ VMEventManager.m5115WWWWWWWW()               (start the LocalServerSocket thread)
   138→       │
   139→       └─ state 4 (BOOTING): run startup pipeline (sequential, each task returns boolean):
   140→            ├─ ApplyOverlaysTask  — copy /system/product overlay files
   141→            ├─ Bug1FixTask … Bug8FixTask  — ROM-version-specific patches
   142→            ├─ CleanLogTask       — clear /proc/self/fd/2 logs
   143→            ├─ SuperuserTask      — extract superuser.zip → /system/...
   144→            ├─ XposedTask         — extract xposed.zip → /system/...
   145→            ├─ GooglePlayTask     — extract play.zip (GApps) → /system/...
   146→            ├─ MagiskTask         — extract magisk.zip → /system/sbin/..., patch init.rc
   147→            ├─ BuildTmpfsTask     — mount tmpfs on /tmp, /dev, etc. (via native)
   148→            ├─ BuildVMPropTask    — write /system/build.prop (PIE/build fingerprint)
   149→            └─ BuildExecPathTask  — set PATH and exec dirs
   150→
   151→       └─ state 5 (RUNNING):
   152→            int pid = startOS(vmId, dpi, kernelPath);   // JNI → libvm.so
   153→            //  - vmId:       vMConfig.f8866WWWWWWWW (0..N)
   154→            //  - dpi:        vMConfig.f8895WWWoWWWo.f8847WWWWWWWW (RomConfig.minimum_sdk_int? actually DPI)
   155→            //  - kernelPath: vMConfig.f8903WWoWWo  = dataDir + "/lib64"
   156→            //                (where libvm.so + libkr64.so live)
   157→            f8938WWWoWWWo = pid;  // save guest pid
   158→            if (pid < 0) → state -4, errorCode = -pid + 117000
   159→
   160→       └─ Native libvm.so now spawns the guest init in a child process; the
   161→          guest's servicemanager → /vm%d/dev/binder (per-VM virtual binder);
   162→          guest's SurfaceFlinger → /dev/qemu_pipe (GL transport); guest's
   163→          EventHub → /dev/input/touch; guest's AudioFlinger → /dev/audio.
   164→
   165→       └─ Guest eventually calls back through the /dev/event socket with:
   166→            "com.android.vmcore.action.BOOT_COMPLETED`<payload>"
   167→          → VMInstance.mo5013WWWWWWWW(...) sets state = 6.
   168→```

   170→### 2.4 Transition to the display activity
   171→
   172→`VMStartActivity0.onVMStatusEvent(VMStatusEvent)` is an `@InterfaceC2472WWWWWWWW(threadMode = MAIN)` EventBus subscriber. When `state >= 5` (or `state >= 7` if user opted for "restart") AND the user-permission flow has completed, it calls `m5021WWoWWo()` which:
   173→
   174→```java
   175→Intent intent = new Intent(this, VMDisplayActivity.class);
   176→intent.addFlags(32768);        // FLAG_ACTIVITY_REORDER_TO_FRONT
   177→intent.addFlags(67108864);     // FLAG_ACTIVITY_NO_ANIMATION
   178→startActivity(intent);
   179→finish();
   180→```
   181→
   182→The display activity is created, and `onCreate` does:
   183→
   184→```java
   185→if (vMInstance.f8940WWoWWo < 5) finish();   // safety check
   186→FrameLayout frameLayout = new FrameLayout(this);
   187→VMSurfaceView vMSurfaceView = new VMSurfaceView(this);
   188→vMSurfaceView.setVM(vMInstance);             // <-- bind to the VM
   189→frameLayout.addView(vMSurfaceView, MATCH_PARENT);
   190→setContentView(frameLayout);
   191→```
   192→
   193→### 2.5 The first frame
   194→
   195→The `VMSurfaceView` extends `FrameLayout` and **creates a real `SurfaceView` as a child** (NOT TextureView):
   196→
   197→```java
   198→// VMSurfaceView.m5233WWWWoWWWWo(context)
   199→SurfaceView sv = new SurfaceView(context);
   200→sv.getHolder().addCallback(this);   // SurfaceHolder.Callback
   201→sv.setOnTouchListener(this);
   202→addView(sv, new LayoutParams(MATCH_PARENT, MATCH_PARENT));
   203→```
   204→
   205→When the framework calls back `surfaceCreated(holder)` (or `surfaceChanged`):
   206→
   207→```java
   208→// VMSurfaceView.m5235WWWoWWWo(SurfaceHolder)
   209→Surface surface = holder.getSurface();
   210→if (surface != null && surface.isValid()) {
   211→    int w = surfaceView.getWidth();
   212→    int h = surfaceView.getHeight();
   213→    int rotation = f9291WWWW;  // 0/90/180/270, computed in onMeasure()
   214→
   215→    if (vMInstance.f8945WoWo == null) {
   216→        vMInstance.f8945WoWo = new DisplayService(vMInstance);
   217→    }
   218→    // Step 1: detach any previous surface for this id
   219→    vMInstance.f8945WoWo.m5126WWWWoWWWWo(hashCode());
   220→    // Step 2: attach the new Surface to the native renderer
   221→    vMInstance.f8945WoWo.m5127WWWWWWWW(hashCode(), surface, w, h, rotation);
   222→}
   223→```
   224→
   225→`DisplayService.m5127WWWWWWWW()` is just a thin JNI wrapper:
   226→
   227→```java
   228→// DisplayService.java (full content, de-obfuscated)
   229→public class DisplayService {
   230→    private long ptr;  // native DisplayService handle, returned by nativeSetup
   231→
   232→    public DisplayService(VMInstance vm) {
   233→        VMConfig cfg = vm.f8937WWWoWWWo;
   234→        this.ptr = nativeSetup(cfg.f8866WWWWWWWW,           // vmId
   235→                               cfg.f8895WWWoWWWo.f8847WWWWWWWW);  // dpi
   236→    }
   237→
   238→    private native long  nativeSetup(int vmId, int dpi);
   239→    private native int   nativeStartService(long ptr, int width, int height);
   240→    private native int   nativeStopService(long ptr);
   241→    private native boolean nativeAddSurface(long ptr, int surfaceId,
   242→                                            Surface surface,
   243→                                            int width, int height, float rotation);
   244→    private native boolean nativeRemoveSurface(long ptr, int surfaceId);
   245→    private native float  nativeGetFPS(long ptr);
   246→    private native void   nativeDispose(long ptr);
   247→}
   248→```
   249→
   250→So the **Java→native rendering call chain** is:
   251→
   252→```
   253→Android Framework creates Surface
   254→  → SurfaceHolder.Callback.surfaceCreated(holder)
   255→  → VMSurfaceView.m5235WWWoWWWo(holder)
   256→  → DisplayService.m5127WWWWWWWW(hashCode, surface, w, h, rotation)
   257→  → DisplayService.nativeAddSurface(ptr, hashCode, surface, w, h, rotation)
   258→  → libvm.so::nativeAddSurface  (JNI)
   259→     (inside libvm.so, this is where the Surface gets bound to the
   260→      per-VM emugl renderer and the QEMU pipe starts producing frames
   261→      onto it — see VIRTUAL_MASTER_FULL_ANALYSIS.md §1)
   262→```
   263→
   264→The `hashCode()` of the `VMSurfaceView` is used as a unique `surfaceId` so multiple surfaces can coexist (e.g. preview + fullscreen) — Virtual Master actually uses this in `VMBigPreviewCardView` and `VMSmallPreviewCardView` to render a small live preview of the VM in the launcher before the user opens it.

   268→## 3. Rendering pipeline — how the Surface reaches the native renderer
   269→
   270→### 3.1 Why Virtual Master does NOT use `android.app.NativeActivity`
   271→
   272→There is **no NativeActivity** in the AndroidManifest.xml. The previous disassembly report (VIRTUAL_MASTER_FULL_ANALYSIS.md) said "NativeActivity → libvm.so" but the Java side contradicts that: the activity is `com.android.vmapp.vm.VMDisplayActivity`, a regular `AppCompatActivity` subclass. The renderer entry-point `nativeAddSurface(...)` is invoked manually from `SurfaceHolder.Callback.surfaceCreated()` — Virtual Master doesn't rely on the framework's `NativeActivity` Surface-binding protocol.
   273→
   274→### 3.2 Why a `SurfaceView` and not a `TextureView`
   275→
   276→`VMSurfaceView` (the public container) is a `FrameLayout` that wraps a `SurfaceView`. This gives the best performance because:
   277→
   278→- A `SurfaceView`'s Surface is backed by a separate hardware-composited layer (Flinger `SurfaceControl`), bypassing the View hierarchy's GPU compositing.
   279→- `SurfaceView.getHolder().setFixedSize(w, h)` lets the renderer fix the buffer size at the guest's actual framebuffer resolution (e.g. 720×1280) even when the View is scaled to fit the host's screen.
   280→- The `Surface` object is directly passed to the native EGL context via `nativeAddSurface(...)`.
   281→
   282→### 3.3 Aspect-ratio handling (VMSurfaceView.onMeasure)
   283→
   284→`onMeasure()` reads the VM's `VMResConfig` (resolution from `vMConfig.f8900WWWoWWWo`), computes the right scale factor + 90/180/270° rotation, and sets `SurfaceView.LayoutParams` margins to letterbox/pillarbox the content. The selected rotation is then sent to the native renderer as the `rotation` parameter of `nativeAddSurface()`.
   285→
   286→### 3.4 Touch input
   287→
   288→`VMSurfaceView.onTouch()` is a multi-touch handler. For each `MotionEvent`:
   289→
   290→1. Get the pointer ID, x, y, event time
   291→2. If rotation != 0, transform (x, y) by the inverse rotation
   292→3. Divide by the scale factor (so coordinates are in guest's framebuffer space)
   293→4. Forward to `VMInstance.f8941WWoWWo.m5131WWWWWWWW(action, pointerId, eventTimeNanos, x, y)` — which is `InputService.nativeOnTouchEvent(ptr, action, pointerId, eventTime, x, y)`.
   294→
   295→So the input pipeline is:
   296→
   297→```
   298→Touch on screen
   299→  → VMSurfaceView.onTouch(view, event)
   300→  → m5234WWWWWWWW(action, pointerIndex, event)
   301→  → InputService.m5131WWWWWWWW(action, pid, t, x, y)
   302→  → InputService.nativeOnTouchEvent(ptr, action, pid, t, x, y)
   303→  → libvm.so writes the touch event to /dev/input/touch
   304→  → guest's EventHub reads it
   305→```
   306→
   307→### 3.5 Key press handling
   308→
   309→`VMDisplayActivity.onKeyDown/onKeyUp` intercepts KEYCODE_BACK (4), VOLUME_UP (24), VOLUME_DOWN (25), and VOLUME_MUTE (164) and forwards them to the guest via `vMInstance.m5086WWoWWo(keyCode, action)` (which is `RunnableC1621WWWWWWWW` posted on the VM handler thread — eventually `nativeOnKeyEvent` or similar).

   348→│   └── libOpenglRender.so?               ← (maybe — see disassembly report)
   349→├── vm/
   350→│   └── vmN/                              ← per-VM data dir (f8867WWWWWWWW)
   351→│       ├── fs/                           ← extracted ROM filesystem (f8868WWWWWWWW)
   352→│       │   ├── system/                   ← system partition
   353→│       │   │   ├── build.prop

   377→### 4.3 Download + decrypt + extract pipeline
   378→
   379→The installer is `com.android.vmcore.installer.ImageInstallerV1`. The flow:
   380→
   381→```
   382→InstallFsTask.mo5036WWWoWWWo(vMApp, vMInstance)
   383→  │
   384→  │  For each uri in romConfig.rom_uri:
   385→  │    ImageInstallerV1.m5205WWWoWWWo(vMConfig, uris, destDir, installOptions)
   386→  │      └─ parallel executor (cachedThreadPool, parallelism=-4):
   387→  │           for each uri: m5204WWWWWWWW(vMConfig, uri, destDir, installOptions)
   388→  │
   389→  │  m5204WWWWWWWW(vMConfig, uri, destDir, installOptions):
   390→  │    cachePath = cacheDir / (uri.lastPathSegment + "_" + vmId)
   391→  │    FileDeleteUtils.delete(cachePath)
   392→  │
   393→  │    out = m5202WWWWWWWW(uri, cachePath, installOptions):
   394→  │      │  queryParam = uri.getQueryParameter("e")
   395→  │      │  if "n":  → BufferedOutputStream(FileOutputStream(cachePath))    // no encryption
   396→  │      │  if "x":  → BufferedOutputStream(XOROutputStream(FOS, KEY))     // XOR with KEY
   397→  │      │  else  :  → BufferedOutputStream(CipherOutputStream(FOS, AES-ECB-PKCS5, KEY))
   398→  │      │
   399→  │      │  KEY = "%z89aviCM0KkbEs9"  (decoded from StringFog)
   400→  │      │  AES algorithm = "AES" (Java default → AES/ECB/PKCS5Padding)
   401→  │      │  XOR uses the same 16-byte key (Vigenère-style, byte-wise)
   402→  │
   403→  │    if uri starts with "asset:///":
   404→  │       AssetsUtils.copy(uri, out)             // read from APK assets
   405→  │    elif uri contains "!/":
   406→  │       FileCopyUtils.copy(file_uri, internal_path, out)   // user-imported ROM
   407→  │    else:
   408→  │       FileCopyUtils.copy(uri, out)           // HTTP download
   409→  │
   410→  │    extract: m5201WWWWoWWWWo(uri, cachePath, destDir, …):
   411→  │      │  queryParam = uri.getQueryParameter("m")
   412→  │      │  if "7z" AND Process.is64Bit():
   413→  │      │     AndUn7z.extract(cachePath, destDir, …)        // 7zip extraction
   414→  │      │  else:
   415→  │      │     ZipHelper.extract(cachePath, destDir, …, /* aesInline = false */)
   416→  │
   417→  │    FileDeleteUtils.delete(cachePath)         // clean up downloaded archive
   418→  │
   419→  └─ vMInstance.m5077WWWoWWWo(overlays)          // remember overlay URIs for ApplyOverlaysTask
   420→```

   435→### 4.5 ROM catalog and `pad://` URI scheme
   436→
   437→The bundled ROM catalog (in `r3/C3947WWWWWWWW.java`, decoded by the previous agent) registers six `RomModel` entries with synthetic URIs `pad://rom_4_2_2`, `pad://rom_5_1_1`, `pad://rom_7_1_2_32`, `pad://rom_7_1_2`, `pad://rom_9_0_0`, `pad://rom_11_0_0`.    443→## 5. IPC with the guest
   444→
   445→There are **three** IPC channels between host Java code and guest Android:
   446→
   447→### 5.1 Channel A — Unix domain socket (`/dev/event`)
   448→
   449→**Java side:** `com.android.vmcore.bridge.VMEventManager`
   450→
   451→In `m5115WWWWWWWW()` (called from `VMInstance.m5100WoWo` after the HAL services start), a background `Thread` is spawned that:
   452→
   453→1. Creates a `LocalServerSocket` bound to a filesystem path:
   454→   ```
   455→   <vMConfig.f8867WWWWWWWW>/dev/event
   456→   = /data/data/com.clone.android.dual.space/vm/vmN/dev/event
   457→   ```
   458→   (the literal suffix `/dev/event` is decoded from StringFog)
   459→2. Calls `accept()` in a loop until `f8990WWWoWWWo` (stop flag) is set or VM state goes to `-5`
   460→3. Wraps the accepted `LocalSocket`'s I/O streams in `DataInputStream` / `DataOutputStream`
   461→4. In a tight loop, calls `readUTF()` to read a single string per event, then splits it on the backtick separator `` ` `` (0x60):
   462→   ```
   463→   eventName`payload
   464→   ```
   465→   (e.g. `com.android.vmcore.action.BOOT_COMPLETED`)
   466→5. Dispatches each event to all registered `IVMEventCallback` instances — primary callback is `VMInstance.mo5013WWWWWWWW(eventName, payload)`.
   467→
   468→The event names (decoded from `com.android.vmcore.bridge.VMEvents` — there are ~25 of them):
   469→
   470→| Event name                                       | Direction       | Purpose                                           |
   471→|--------------------------------------------------|-----------------|---------------------------------------------------|
   472→| `com.android.vmcore.action.VM_SERVER_READY`      | guest → host    | Guest's IPC server is up                          |
   473→| `com.android.vmcore.action.ANDROID_OS_READY`     | guest → host    | OS is fully booted (post-zygote)                  |
   474→| `com.android.vmcore.action.BOOT_COMPLETED`       | guest → host    | sys.boot_completed=1 — sets VM state to 6         |
   475→| `com.android.vmcore.action.SHUTDOWN`             | guest → host    | Guest is shutting down — sets VM state to 7       |
   476→| `com.android.vmcore.action.SYNC_PROP_EVENT`      | bidirectional   | Set a System property in the guest                |
   477→| `com.android.vmcore.action.START_INSTALL_APP`    | host → guest    | Host asks guest to install an APK                 |
   478→| `com.android.vmcore.action.INSTALL_APP_RESULT`   | guest → host    | Guest reports install result                      |
   479→| `com.android.vmcore.action.START_UNINSTALL_APP`  | host → guest    | Host asks guest to uninstall an APK               |
   480→| `com.android.vmcore.action.UNINSTALL_APP_RESULT` | guest → host    | Guest reports uninstall result                    |
   481→| `com.android.vmcore.action.TASK_STACK_CHANGED`   | guest → host    | Guest's task stack changed (for recent tasks UI)  |
   482→| `com.android.vmcore.action.CLIPBOARD_DATA`       | bidirectional   | Clipboard sync between host and guest             |
   483→| `com.android.vmcore.action.OPEN_OUTER_PAGE`      | guest → host    | Guest requests opening a URL in host browser      |
   484→| `com.android.vmcore.action.TOGGLE_RECENTS`       | guest → host    | Guest requests recents panel                      |
   485→| `com.android.vmcore.action.SEND_KEY_EVENT`       | bidirectional   | Forward a KeyEvent                                |
   486→| `com.android.vmcore.action.SET_LOCALE_AND_TIME`  | host → guest    | Sync host locale/timezone to guest                |
   487→| `com.android.vmcore.action.SET_GLOBAL_SETTING`   | host → guest    | Set a `Settings.Global` value                     |
   488→| `com.android.vmcore.action.SHOW_NAVIGATION_EVENT`| guest → host    | Guest asks to show nav bar                        |
   489→| `com.android.vmcore.action.HIDE_NAVIGATION_EVENT`| guest → host    | Guest asks to hide nav bar                        |
   490→| `com.android.vmcore.action.SET_NAVIGATION_BAR_RTL`| host → guest   | Set nav bar RTL                                    |
   491→| `com.android.vmcore.action.KILL_APP`             | host → guest    | Kill a guest app by package name                  |
   492→| `com.android.vmcore.action.EXPAND_NOTIFICATIONS_PANEL`  | guest → host | Guest wants notification shade             |
   493→| `com.android.vmcore.action.COLLAPSE_NOTIFICATIONS_PANEL`| guest → host | Guest wants notification shade closed      |
   494→| `com.android.vmcore.action.EXECUTE_COMMAND`      | host → guest    | Execute a shell command in the guest              |
   495→
   496→The send side is `VMEventManager.m5116WWWoWWWo(eventName, payload)` which does `writeUTF(eventName + "`" + payload); flush()`.
   497→
   498→### 5.2 Channel B — Binder virtualization (`/vm%d/dev/binder`)
   499→
   500→**Java side:** `com.android.vmcore.service.BinderService`
   501→
   502→This is the most subtle channel. The guest Android's `servicemanager` needs to register with `android.os.ServiceManager` to find system services (`activity`, `package`, `window`, etc.). Virtual Master can't let the guest talk to the host's real `/dev/binder` (it would corrupt the host), so it creates a **per-VM virtual binder** at `/vm%d/dev/binder`.
   503→
   504→The setup is in `BinderService.m5206WWWWoWWWWo(vMApp, vmId)`:
   505→
   506→1. **Reflect into ActivityManager** (`m5207WWWWWWWW(vMApp)`):
   507→   - On API 26+: get the `IActivityTaskManager` interface, call `getID()` on it, then `mActivityTaskManager.getConfiguration()` etc. (this is the hidden-API path that the `me.weishu.reflection` bypass enables)
   508→   - On older APIs: get the legacy `IActivityManager` similarly
   509→   - Get a handle to the system `IBinder` for `android.app.IActivityManager`
   510→2. **Wrap the IBinder with a Java `Proxy`** that intercepts `transact()` calls. The proxy checks the calling thread ID; when the wrapped `transact()` is called from the same thread that called `peekService()` (in step 4), the proxy captures the integer return code into `iArr[0]`.
   511→3. **Install the proxy back** via reflection on `ActivityManager.IActivityTaskManager` (replacing the system's `IActivityTaskManager` field with the proxied one).
   512→4. **Call `peekService(vMApp, new Intent())`** — this triggers the proxy. The captured integer is the system's binder version.
   513→5. **Call native `setupBinder(vmId, binderVersion, 1, 2, "com.android.vmcore.service.IBinderService", parcelledIntent)`** — this is the JNI call into libvm.so that:
   514→   - Creates `/vm%d/dev/binder` (the per-VM virtual binder device, matches disassembly)
   515→   - Sets up a binder-redirect mapping so the guest's `servicemanager` calls for `activity`/`package`/`window`/etc. are proxied back to the host's `BinderService.f9244WWWWoWWWWo` (the `IBinderService.Stub` instance) — which the host then fulfills (or passes through to the real system service with the host's identity)
   516→6. **`bindService(Intent(BinderService.class), serviceConnection, BIND_AUTO_CREATE)`** — waits up to 5 seconds for `onServiceConnected`, returns `-502` on timeout.
   517→
   518→The `IBinderService` AIDL (in `com.android.vmcore.service.IBinderService` interface) is just a stub:
   519→
   520→```java
   521→public interface IBinderService extends IInterface {
   522→    abstract class Stub extends Binder implements IBinderService { … }
   523→}
   524→```
   525→
   526→So the guest makes a binder transaction → libvm.so's virtual binder intercepts it → routes it to the host's `BinderService` (the Java service) → the host fulfills it. This is how the guest's `Context.startActivity()` ends up calling host `VMDisplayActivity.onDialNumberEvent()` for example.
   527→
   528→### 5.3 Channel C — `/dev/qemu_pipe` (GL transport)
   529→
   530→**Java side:** none (entirely in native).
   531→
   532→The guest's SurfaceFlinger speaks the emugl `qemu_pipe` protocol to ship GL commands to the host's `libvm.so`, which has its own EGL context created on the `Surface` we passed in via `nativeAddSurface(...)`. This is the same mechanism as twoyi (see `VIRTUAL_MASTER_FULL_ANALYSIS.md`). There is no Java code involved.
   533→
   534→### 5.4 Other HAL services (each is a `LocalSocket`-or-virtual-dev bridge)
   535→
   536→`com.android.vmcore.hal.HALManager` is created per-VM in `VMInstance.m5100WoWo()`:
   537→
   538→```java
   539→this.f8933WWWWWWWW = new HALManager(vMApp, vMInstance);
   540→this.f8933WWWWWWWW.startHALMgr();
   541→```
   542→
   543→Inside, `HALManager.nativeSetup(vmId)` returns a `long` pointer to a native HAL dispatcher. The dispatcher then calls back into Java via private methods (named `CameraConnect`, `CameraDisconnect`, `CameraStart`, `CameraStop`, `CameraFocus`, `CameraFrame`, `CameraFlash`, `CameraList`, `EnableSensors`, `DisableSensors`, `CheckSensorsSupport`, `ExecPhoneCommand`, `SetLocation`, `GetWifiScanResults`, `SetWifiEnabled`, …). These JNI callbacks let the guest access host hardware (camera, sensors, GPS, WiFi scan, phone state, battery) as if it were native.
   544→
   545→The full HAL composition:
   546→
   547→| HAL Service           | Java Class                                | What it does                                                          |
   548→|-----------------------|-------------------------------------------|-----------------------------------------------------------------------|
   549→| Display               | `DisplayService`                          | Surface registration (see §3)                                         |
   550→| Input (touch)         | `InputService`                            | Touch event forwarding                                                |
   551→| Audio                 | `AudioService`                            | Audio capture/playback (via `AudioRecord` / `AudioTrack`)             |
   552→| Camera                | `CameraService` (in HALManager)           | Camera1 API proxy (open/start/stop/focus/zoom)                        |
   553→| Sensor                | `SensorService` (in HALManager)           | 12 sensor types (accel/gyro/mag/…) via `SensorManager`                |
   554→| Location              | `LocationService`                         | GPS pass-through + fake-location support                              |
   555→| WiFi scan             | `WiFiService`                             | `WifiManager.getScanResults()` proxy                                  |
   556→| Phone                 | `PhoneService`                            | SIM state, signal strength, SMS, dial (via `TelephonyManager`)        |
   557→| Battery               | `BatteryService`                          | Battery level/charging state (via `ACTION_BATTERY_CHANGED` receiver)  |
   558→| Network               | `NetlinkManager`                          | Virtual network interface (`tun0`) with MAC/IP/gateway/DNS             |
   559→| HW control            | `HWControlService`                        | Hardware buttons (power/volume)                                       |

   705→## 7. Differences from twoyi
   706→
   707→This section is the most important for the twoyi project. Here are the architectural choices Virtual Master made that twoyi did (or didn't):
   708→
   709→| Aspect                          | Twoyi (current)                          | Virtual Master                                                  |
   710→|---------------------------------|------------------------------------------|------------------------------------------------------------------|
   711→| **Native library**              | `libvm.so` + `libOpenglRender.so` + `libloader.so` (3 libs) | Single `libvm.so` (all-in-one)                                  |
   712→| **Application class**           | `io.twoyi.TwoyiApplication`              | `com.android.vmapp.VMApp` (with reflection bypass + Firebase)   |
   713→| **Display activity**            | `io.twoyi.Render2Activity`               | `com.android.vmapp.vm.VMDisplayActivity`                        |
   714→| **Boot progress UI**            | `BootLogTexture` (TextureView overlay)   | `VMStartActivity0..3` (Lottie animation + status text)           |
   715→| **Surface type**                | `TextureView` (originally) / SurfaceView (new) | `SurfaceView` (wrapped in `VMSurfaceView extends FrameLayout`) |
   716→| **Surface→native API**          | AOSP emugl `initOpenGLRenderer()` + `createOpenGLSubwindow()` (global singleton) | **Custom per-VM `DisplayService.nativeAddSurface(ptr, surfaceId, surface, w, h, rot)`** |
   717→| **Multi-VM support**            | No (single VM)                           | **Yes** — up to 4 concurrent VMs (VMStartActivity0..3, taskAffinity `.vm0..3`) |
   718→| **State machine**               | Implicit (boot log lines)                | **Explicit**: 11 states (-5..7) with EventBus events            |
   719→| **Touch input**                 | Unix socket `/dev/input/touch`           | Same path; Java side: `InputService.nativeOnTouchEvent`         |
   720→| **Binder virtualization**       | ❌ None (uses host binder)                | ✅ Per-VM `/vm%d/dev/binder` via `setupBinder()` JNI            |
   721→| **Audio virtualization**        | ❌ None                                   | ✅ `AudioService` (Java) + `/dev/audio` (native)                |
   722→| **Network virtualization**      | ❌ None                                   | ✅ `NetlinkManager` + `tun0` with per-VM MAC/IP/gateway         |
   723→| **Camera/Sensor/GPS HAL**       | ❌ None                                   | ✅ Full HAL proxy (Camera1 API, 12 sensor types, GPS, WiFi scan) |
   724→| **Phone/SMS HAL**               | ❌ None                                   | ✅ `PhoneService` (TelephonyManager proxy)                       |
   725→| **Battery HAL**                 | ❌ None                                   | ✅ `BatteryService` (ACTION_BATTERY_CHANGED receiver)            |
   726→| **ROM source**                  | Bundled `rom.zip` (~100 MB)              | **Downloaded from server** (6 versions, 66–351 MB each)         |
   727→| **ROM encryption**              | None                                     | **AES-128-ECB or XOR** (key `%z89aviCM0KkbEs9`), chosen per-URI by `e=` query param |
   728→| **ROM extraction**              | ZIP                                      | ZIP **or 7z** (chosen by `m=` query param + 64-bit check)       |
   729→| **Add-ons (GApps/Magisk/…)**    | None                                     | 4 AES-encrypted plugin ZIPs bundled in `assets/plugins/`        |
   730→| **IPC channel 1**               | `TwoyiMessenger` (Java-side Handler)     | `VMEventManager` (LocalServerSocket at `/dev/event`)            |
   731→| **IPC channel 2**               | `TwoyiSocketServer` (TCP)                | Binder virtualization (per-VM `/vm%d/dev/binder`)               |
   732→| **Hidden-API bypass**           | None (uses only public APIs)             | `me.weishu.reflection.BootstrapClass.exemptAll()` (embedded dex) |
   733→| **String obfuscation**          | None                                     | StringFog (Vigenère-XOR, per-string key)                        |
   734→| **Native string obfuscation**   | None                                     | Obfuscator-LLVM (per-block XOR, 74 `datadiv_decode` functions)  |
   735→| **Touch coords to guest**       | Direct                                   | Rotated/scaled in Java (`VMSurfaceView.m5234WWWWWWWW`)         |
   736→
   737→### 7.1 Key takeaways for twoyi
   738→
   739→1. **Per-VM renderer pointer.** Virtual Master's `DisplayService.nativeSetup(vmId, dpi)` returns a `long` that's then passed to every subsequent `nativeAddSurface`/`nativeRemoveSurface`/`nativeStartService` call. This is a much cleaner API than twoyi's global-singleton emugl. **Recommendation: refactor twoyi's `libOpenglRender` to take a per-instance handle.**
   740→
   741→2. **Surface-passing is explicit, not via NativeActivity.** Virtual Master shows you don't need `NativeActivity` — just implement `SurfaceHolder.Callback` and call a custom `nativeAddSurface(surface, w, h, rotation)` from `surfaceCreated`. **Recommendation: adopt this pattern in twoyi — it's simpler and supports multiple surfaces.**
   742→
   743→3. **The boot state machine matters.** Twoyi currently uses an implicit boot log (line-by-line text). Virtual Master's 11-state explicit machine with EventBus events gives the UI much better feedback ("Installing…", "Fixing FS…", "Starting services…", "OS booting…", "OS ready"). **Recommendation: add a state enum to `TwoyiStatusManager` and emit status events.**
   744→
   745→4. **Binder virtualization is the hardest piece.** Virtual Master has it, twoyi doesn't. The Java side is small (`BinderService` ~400 lines) but the native `setupBinder()` JNI is significant — it creates a per-VM `/vm%d/dev/binder` and routes the guest's `servicemanager` calls back to the host. Without this, the guest's `servicemanager` would either fail to start or talk to the host's servicemanager (which is what twoyi does, with limitations — the guest's `getSystemService(ACTIVITY_SERVICE)` returns the *host's* ActivityManager, which is why twoyi's guest can launch host apps but not its own).
   746→
   747→5. **ROM download + on-the-fly AES decryption is elegant.** The `CipherOutputStream` wraps `FileOutputStream`, so the cleartext ROM never touches disk during download. **Recommendation: consider this for twoyi if we ever distribute ROMs server-side.**
   748→
   749→6. **Multi-VM support is straightforward.** Per-VM data dir (`vm/vmN/fs`), per-VM SharedPreferences (`vm_config_N.xml`), per-VM task affinity, per-VM renderer pointer. **Recommendation: adopt this directory layout in twoyi for future multi-VM support.**
   750→
   751→7. **The ROM catalog + `pad://` URI scheme.** Virtual Master separates the *logical* ROM ID (`pad://rom_7_1_2`) from the *physical* download URL (resolved via API call). This lets them swap mirrors without changing the app. **Recommendation: not urgent for twoyi (we bundle the ROM), but useful if we ever ship a "ROM store".**

   953→## 10. Conclusion
   954→
   955→Virtual Master's Java side is a well-architected, modular Android-in-Android container with:
   956→
   957→- A clear state machine driving the boot sequence (11 states, EventBus-dispatched)
   958→- A two-stage install/boot pipeline (8 setup tasks → 10 startup tasks)
   959→- Per-VM data isolation (`vm/vmN/fs`, `vm_config_N.xml`, per-VM binder device)
   960→- A clean rendering API that takes a Surface directly via `nativeAddSurface` (no NativeActivity needed)
   961→- A two-channel IPC model (Unix socket for events, virtual binder for system services)
   962→- A comprehensive HAL proxy (display, input, audio, camera, sensor, location, wifi, phone, battery, network)
   963→- Server-side ROM distribution with on-the-fly AES/XOR decryption
   964→- An explicit JNI contract that makes the native libvm.so easily replaceable
   965→
   966→The most actionable insights for twoyi are:
   967→
   968→1. **Adopt the `nativeAddSurface(ptr, surfaceId, surface, w, h, rot)` API** instead of the global-singleton emugl API. This unblocks multi-VM and multi-surface (preview + fullscreen).
   969→2. **Add an explicit state machine** with EventBus events to TwoyiStatusManager — gives the UI proper boot feedback.
   970→3. **The hardest piece to copy is binder virtualization** — without it, the guest's `servicemanager` either fails or talks to the host's. This is a significant native-side project.
   971→4. **The ROM download + AES decrypt pipeline** is a clean pattern if twoyi ever moves to server-side ROM distribution.
