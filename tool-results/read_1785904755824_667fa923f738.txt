The entire module is: create seven files + spawn one refresh thread. The 856 LOC (vs. audio.rs 1,423 / sensors.rs 2,294) reflects this — most of the line count is rustdoc + tests, not implementation. The implementation proper is ~350 LOC.
   222→2. **The `BatteryDeviceView` duplication was the wrong abstraction.** The first draft duplicated all seven `update_*` methods on a `BatteryDeviceView<'a>` struct so the refresh thread could call them without owning a `BatteryDevice`. The cleaner solution is to lift `write_file_at(dir, name, value)` and `refresh_dir(dir)` to free functions — both `BatteryDevice::write_file` (a one-line delegate) and the spawn closure call them directly. This removed ~90 LOC and made the code easier to reason about (no second struct to keep in sync with `BatteryDevice`). The lesson generalises: when a thread needs to call instance methods but only owns a subset of the instance's state, lift the method body to a free function taking that subset as args.
   223→3. **The 1 s sleep tick is the right granularity for the refresh loop.** A single `thread::sleep(Duration::from_secs(30))` would block `Drop::join()` for up to 30 s on shutdown, which would time out the `spawn_then_drop_joins_cleanly` test (default 60 s timeout) and feel sluggish in production. Sleeping in 1 s ticks and re-checking the shutdown flag between ticks means the thread observes shutdown within ~1 s. The cost is 30 extra `AtomicBool::load(Acquire)` calls per refresh cycle, which is negligible.
   224→4. **The "charging" file should be derived from "status", not independently settable.** The Linux `power_supply` ABI has both a `status` file (string: Charging/Discharging/Full/Not charging) and a `charging` file (0/1) — they're redundant, and if they disagree the guest's battery HAL gets confused. The fix is to make `update_charging` take a `BatteryStatus` and derive the 0/1 from it, so the two files can never disagree. The `update_charging_derives_from_status` test asserts this invariant for all four status variants.
   225→5. **The unit choice (mV for voltage, 1/10 °C for temperature) matches the JNI values 1:1.** The standard Linux `power_supply` ABI uses µV for `voltage_now`, but VM's file-based battery HAL uses mV (matching `android.os.BatteryManager`'s int fields). We mirror VM's choice so the JNI value and the file content are identical — no unit conversion needed, which means `jni_get_battery_voltage()` returning 4200 produces a file containing "4200", and `read_voltage()` reads 4200 back. If a future guest ROM's battery HAL expects µV, the fix is a one-line `* 1000` in `update_voltage`. Documented in `BATTERY_IMPL.md` §1.2.
   226→6. **The HAL-DETAIL-1 analysis was accurate.** The "file-based battery" description in `HAL_VIRTUALIZATION_ANALYSIS.md` §4 and `DEVELOPMENT_ROADMAP.md` task 4.10 translated directly into the implementation. The only design decisions not specified by the analysis were: (a) the 30 s refresh interval (chosen to be within the guest's typical 1-minute poll cadence), (b) the 1 s sleep tick granularity (chosen for fast shutdown), (c) the `BatteryStatus` enum's `as_str()` returning "Not charging" (two words, matching the Linux ABI), and (d) the `Drop` impl not unlinking the sysfs files (chosen to avoid racing with guest open fds). All four decisions are documented in `BATTERY_IMPL.md` §4.
   227→7. **The skeleton compiles and tests pass with zero external deps.** The crate still depends on only `libc`. No `jni` crate, no `bitflags` crate, no `log` crate. The JNI up-calls are stubbed as no-ops, the `BatteryStatus` enum is hand-rolled with `#[repr(u8)]`, and logging goes through the crate-local `info!`/`warning!`/`error!` macros (which expand to `eprintln!`). The battery skeleton can ship in the next APK build without pulling in any new dependencies.

   282→1. **The twoyi rootfs layout is unusual: `init` lives at the rootfs root, not at `/system/bin/init`.** This was confirmed by reading `RomManager.romExist()` at line 182: `new File(getRootfsDir(context), "init")`.
