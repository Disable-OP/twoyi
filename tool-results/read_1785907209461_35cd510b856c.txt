   594→   594→1. **GSI definition (§1):** A Treble GSI is an Android `system.img` conforming to the Treble HAL interface contract (introduced in Android 8.0). The wire protocol is just `{magic, direction, sample_rate, channels}` (16-byte header) followed by a raw byte stream. The 44 100/11 025 Hz hard-coding means twoyi's guest ROM **must** also expect those rates from its audio HAL module — if the GSI's `audio.primary.default.so` asks for 48 000 Hz, the host AudioTrack will still play it (Android resamples internally), but the guest's perception of its own sample rate will be wrong.
  1890→  1890→2. **AudioService and SensorService have different ownership patterns.** Audio is top-level (alongside Input/Display) because it has hard real-time requirements; Sensor is under `HALManager` because sensor events are bursty and low-rate. Twoyi should mirror this — `audio.rs` gets its own dedicated thread with no shared state, `sensors.rs` can share a dispatcher with future HALs.
  1891→  1891→3. **The sensor state machine is a 3-bit mask per index, not a boolean.** `SUPPORTED | ENABLED | ACTIVE` is needed because: a sensor may be supported by the host (bit 0 set) but not enabled by the guest (bit 1 clear); or enabled by the guest (bit 1 set) but not active because the VM is backgrounded (bit 2 clear). Twoyi's Rust dispatcher needs to track this same mask so it can correctly answer `CheckSensorsSupport` without actually registering a host listener.
  1892→  1892→4. **`nativeSensorChanged` is a down-call (Java→native), not an up-call.** The flow is: host `SensorManager` → Java `onSensorChanged` → `HALManager.SensorChanged` → `nativeSensorChanged(ptr, idx, ts, x, y, z)` (JNI) → Rust dispatcher pushes a 24-byte `SensorEvent` into a per-idx `mpsc::Sender` → pump thread drains it to the socket. The `EnableSensors`/`DisableSensors`/`CheckSensorsSupport`/`SetDelay` methods are up-calls (native→Java) — the guest triggers them via control messages on the socket.
  1893→  1893→5. **VM's `SetDelay` zeroes both the sampling period AND the max latency arrays.** This looks like a decompiler artifact but the bytecode matches. Twoyi should mirror this quirk for protocol compatibility, not "fix" it.
  1894→  1894→6. **No hidden-API bypass needed.** `AudioTrack`, `AudioRecord`, `SensorManager.registerListener`, `SensorEventListener.onSensorChanged` are all public API. The only manifest changes needed are `<uses-permission android:name="android.permission.RECORD_AUDIO" />` (for capture) and `<uses-permission android:name="android.permission.HIGH_SAMPLING_RATE_SENSORS" />` (API 31+, only for >200 Hz sensors).
  1895→  1895→7. **Latency budget for the user's rhythm game is the bottleneck.** VM uses `AudioTrack` in `MODE_STREAM` which gives ~125 ms host-side latency + ~80 ms guest AudioFlinger latency = ~200 ms total. For a rhythm game this is perceptible. The fix is `AudioTrack.Builder.setPerformanceMode(PERFORMANCE_MODE_LOW_LATENCY).setBufferSizeInFrames(192)` (API 26+) — drops to ~20 ms host-side. This is a Java-only change in `acquireAudioTrack`; the Rust pump doesn't care.

  1994→  1994→   - **`handle_connection`** — clones the stream via `UnixStream::try_clone()`, creates an `Arc<SensorConnState>`, spawns a `kr64-sensor-pump` sub-thread (which runs `pump_events`), then runs `handle_control` in the worker thread itself. When the control read returns EOF, the worker signals shutdown, joins the pump sub-thread, and returns.
  1995→  1995→   - **`handle_control`** — reads 12-byte control messages in a loop, dispatches by `cmd`: `CHECK_SUPPORT` queries the JNI stub (cached in `SensorConnState`) and writes a 4-byte LE u32 reply; `ENABLE` calls the JNI stub and conditionally marks the sensor enabled; `DISABLE` calls the JNI stub and marks it disabled; `SET_DELAY` calls the JNI stub and updates the per-sensor sampling period. Out-of-range `idx` and unknown `cmd` are logged and skipped.
  1996→  1996→   - **`pump_events`** — the event pump. Snapshots the enabled-sensor list, polls each enabled sensor via `jni_read_sensor_event`, and writes any returned `SensorEvent` (24 bytes) to the guest. Sleeps for the shortest delay among enabled sensors (clamped to `MIN_POLL_NS`..`MAX_POLL_NS` = 1 ms..1 s) between iterations. When no sensors are enabled, sleeps for `SENSOR_IDLE_POLL_MS` (50 ms) and re-checks. Exits when the connection's shutdown flag is set.
  1997→  1997→   - **JNI up-call stubs** — `jni_check_sensor_support` (returns `false`), `jni_enable_sensor` (returns `false`), `jni_disable_sensor` (no-op), `jni_set_sensor_delay` (no-op), `jni_read_sensor_event` (returns `None`). Documented with the exact Java signatures they'll need to invoke. `JniObject = *mut c_void` so the skeleton doesn't need the `jni` crate.
