    10→
    11→## TL;DR
    12→
    13→Virtual Master virtualizes **10 HAL domains** (display, input, audio, camera, sensor, location, wifi, phone, battery, network) plus an HW-control shim. Twoyi today ships only **two of those** — Display (via the emugl `/dev/qemu_pipe` path) and Input (via `/dev/input/touch` + `/dev/input/key0`). Closing the gap is mostly Java + JNI callback work, **not** new native kernel-replacement logic, because the device-node plumbing is already in place in `app/rs/kr64/src/devices.rs`.
    14→
    15→The single hardest piece is **Audio** (real-time duplex loopback with thread synchronization) and the single most labour-intensive is **Camera** (frame-format negotiation + per-frame YUV→JPEG).

    19→## 1. What HALs does Virtual Master virtualize?
    20→
    21→Source: `VM_JAVA_ANALYSIS.md` §5.4 + the `com.android.vmcore.hal.*` decompiled classes.
    22→
    23→### 1.1 Display
    24→
    25→| Field | Value |
    26→|---|---|
    27→| **What it does** | Registers a host `android.view.Surface` with the per-VM emugl renderer so the guest's SurfaceFlinger can composite into it. |
    28→| **Java class** | `com.android.vmcore.hal.DisplayService` — JNI wrapper with `nativeSetup(vmId, dpi)`, `nativeStartService(ptr, w, h)`, `nativeAddSurface(ptr, surfaceId, surface, w, h, rotation)`, `nativeRemoveSurface`, `nativeGetFPS`, `nativeDispose`. |
    29→| **Native fn** | `libvm.so::nativeAddSurface` (binds the Surface to a per-VM ColorBuffer; uses emugl's `qemu_pipe` GL transport). |
    30→| **Device path** | `/dev/qemu_pipe` (created by `libkr64.so`, owned by guest SurfaceFlinger). |
    31→| **IPC mechanism** | Custom binary protocol over the `qemu_pipe` socket (no Java involvement past `nativeAddSurface`). |
    32→| **What guest sees** | A normal EGL surface that a normal SurfaceFlinger composites into; the framebuffer appears as a real display. Multi-surface supported (live preview + fullscreen). |
    33→
    34→### 1.2 Input (Touch + Keys)
    35→
    36→| Field | Value |
    37→|---|---|
    38→| **What it does** | Forwards host `MotionEvent`s and `KeyEvent`s into the guest's `EventHub`. |
    39→| **Java class** | `com.android.vmcore.hal.InputService` — `nativeOnTouchEvent(ptr, action, pointerId, t, x, y)`. Coordinate transform (rotation, scale) done in `VMSurfaceView.m5234WWWWWWWW`. |
    40→| **Native fn** | `libvm.so` writes Linux `input_event` structs to the touch/key sockets. |
    41→| **Device paths** | `/dev/input/touch`, `/dev/input/key0` (or similar). |
    42→| **IPC mechanism** | Unix domain socket; the host writes a 96-byte `device_info` header on accept, then streams `struct input_event` records (16 bytes each on aarch64). |
    43→| **What guest sees** | A standard multi-touch device (`vtouch`) and a 5-key keyboard (`vkey`) — both appear in `/dev/input/` and are picked up by `EventHub.java`. |
    44→
    45→### 1.3 Audio
    46→
    47→| Field | Value |
    48→|---|---|
    49→| **What it does** | Bidirectional audio: guest playback → host `AudioTrack`, host microphone → guest capture. |
    50→| **Java class** | `com.android.vmcore.hal.AudioService` — owns `List<AudioTrack> mTrackList` and `List<AudioRecord> mRecordList`. JNI: `nativeSetup`, `nativeStartService`, `nativeStopService`, `nativeDispose`. Private `acquireAudioTrack(int[])` / `acquireAudioRecord(int[])` create host tracks at **44100 Hz / 11025 Hz** respectively. |
    51→| **Native fn** | `libvm.so::nativeStartService` opens `/dev/audio` and pumps PCM frames between the socket and the Java-callback `writeAudioData` / `readRecordData`. |
    52→| **Device path** | `/dev/audio` (created by `libkr64.so`). |
    53→| **IPC mechanism** | Unix socket carrying raw PCM samples + a small control header (sample-rate / channel-count / format negotiated on connect). |
    54→| **What guest sees** | A standard ALSA-style `/dev/audio` node that `AudioFlinger` opens for playback and capture. |
    55→
    56→### 1.4 Camera
    57→
    58→| Field | Value |
    59→|---|---|
    60→| **What it does** | Proxies the deprecated Camera1 API (`android.hardware.Camera`) so the guest can open/start/stop/focus/zoom/take-picture. |
    61→| **Java class** | `com.android.vmcore.hal.CameraService` (owned by `HALManager`). Called by `HALManager` JNI-callback methods: `CameraConnect`, `CameraDisconnect`, `CameraStart(w,h,fps,client)`, `CameraStop`, `CameraFocus`, `CameraFrame`, `CameraFlash`, `CameraList`. Host→guest frame delivery: `nativeCameraPicture(ptr, client, byte[])` and `nativeCameraPreview(ptr, client, byte[])`. |
    62→| **Native fn** | `libvm.so` exposes a virtual `/dev/camera*` device node and routes guest ioctl-style requests back into Java. |
    63→| **Device paths** | `/dev/camera0`, `/dev/camera1` (one per host camera returned by `Camera.getNumberOfCameras()`). |
    64→| **IPC mechanism** | Custom binary protocol: open/close on connect; preview frames streamed as YUV420/NV21 byte arrays back to Java, which calls `Camera.startPreview` with a `PreviewCallback` and forwards the buffer to native. |
    65→| **What guest sees** | A `/dev/camera0` that the guest's `cameraserver` HAL opens like real hardware; the legacy `android.hardware.Camera` Java API just works. |
    66→
    67→### 1.5 Sensor (12 types)
    68→
    69→| Field | Value |
    70→|---|---|
    71→| **What it does** | Proxies 12 Android sensor types from the host `SensorManager` to the guest's sensor HAL. |
    72→| **Java class** | `com.android.vmcore.hal.SensorService`. Static `SparseIntArray` (in `static {}` block at line 61) maps guest indices 0..11 → host `Sensor.TYPE_*` values: **1 (ACCEL), 2 (MAG), 3 (ORIENT), 7 (TEMP), 8 (LIGHT), 5 (PROX), 6 (GYRO), 12 (HUMIDITY), 9 (PRESSURE), 19 (GRAVITY), 18 (STEP_DETECT), 4 (GYRO_UNCAL)**. |
    73→| **Native fn** | `libvm.so` exposes a virtual `/dev/sensor` (or similar) device node and a per-sensor subscription list. Java callback `nativeSensorChanged(ptr, sensorIdx, timestampNs, x, y, z)` pushes 3-axis samples to native. |
    74→| **Java callbacks** | `EnableSensors(int idx)`, `DisableSensors(int idx)`, `CheckSensorsSupport(int idx)` — invoked from native via JNI. |
    75→| **Device paths** | (Inferred) `/dev/input/accel`, `/dev/input/gyro`, …, or a single multiplexed `/dev/sensors` socket. |
    76→| **IPC mechanism** | Java `SensorManager.registerListener` → host sensor event → `SensorChanged` → `nativeSensorChanged` → guest sensor HAL. |
    77→| **What guest sees** | A real `/dev/input/*` sensor device that the guest's `sensorservice` reads via the standard input subsystem. |
    78→
    79→### 1.6 Location (GPS)
    80→
    81→| Field | Value |
    82→|---|---|
    83→| **What it does** | Passes host GPS fixes (and NMEA sentences) to the guest; supports fake-location override. |
    84→| **Java class** | `com.android.vmcore.hal.LocationService implements LocationListener`. Uses `LocationManager` + `addNmeaListener`. JNI callbacks: `nativeGPSNmeaChanged(ptr, nmea)`. Host→guest methods: `SetLocation(lat, lon, …)`, `m5135WWWWWWWW()` (start), `m5136…()` (stop). |
    85→| **Native fn** | `libvm.so` writes the location update to the guest's GPS HAL socket. |
    86→| **Device paths** | (Inferred) `/dev/socket/gps` or a character device. |
    87→| **IPC mechanism** | Java → native → guest GPS HAL via custom binary protocol. |
    88→| **What guest sees** | A real GPS provider (`gps`); `LocationManager.getLastKnownLocation()` works. |
    89→
    90→### 1.7 WiFi Scan
    91→
    92→| Field | Value |
    93→|---|---|
    94→| **What it does** | Proxies `WifiManager.getScanResults()` and `setWifiEnabled()` from guest to host. |
    95→| **Java class** | `com.android.vmcore.hal.WiFiService` — holds `WifiManager f9119WWWoWWWo`. Host→guest callback `nativeWIFIChanged(ptr, jsonScanResults)`. Called via `SetWiFiStart()` from native. |
    96→| **Native fn** | `libvm.so` exposes a virtual wifi HAL node and triggers Java `getScanResults()` when the guest calls it. |
    97→| **Device paths** | (Inferred) `/dev/socket/wpa_*` or virtual wlan0. |
    98→| **IPC mechanism** | Custom binary protocol over Unix socket; results encoded as JSON or simple TLV. |
    99→| **What guest sees** | A working wifi HAL that returns the host's scan results. |
   100→
   101→### 1.8 Phone (SIM/SMS/Call)
   102→
   103→| Field | Value |
   104→|---|---|
   105→| **What it does** | Proxies `TelephonyManager` (SIM state, signal strength, network registration), supports SMS send/receive and dial intents. |
   106→| **Java class** | `com.android.vmcore.hal.PhoneService` + a `phone/` sub-package (`CallPdu`, `GsmAlphabet`, `CarrierManager`, `MccTable`, `SmsConstants`, `IccUtils`, … ~14 helper classes — full PDU encoding/decoding). Single dispatcher: `ExecPhoneCommand(int cmd, String arg)` (~350 lines, switch on ~25 phone commands). Host→guest unsolicited: `nativePhoneUnsolicited(ptr, json)`. |
   107→| **Native fn** | `libvm.so` exposes a virtual `/dev/socket/rild`-style node and routes `RIL_REQUEST_*` commands back to Java. |
   108→| **Device paths** | `/dev/socket/rild`, `/dev/socket/rild-debug` (standard Android RIL paths). |
   109→| **IPC mechanism** | RIL protocol (compatible with `ReferenceRIL`); Java ↔ native via JNI callbacks. |
   110→| **What guest sees** | A working `TelephonyManager` with SIM state, signal, and SMS support. |
   111→
   112→### 1.9 Battery
   113→
   114→| Field | Value |
   115→|---|---|
   116→| **What it does** | Mirrors host battery state (level, charging, temperature, voltage) into the guest. |
   117→| **Java class** | `com.android.vmcore.hal.BatteryService` — registered as a `BroadcastReceiver` for `ACTION_BATTERY_CHANGED`. Holds a `BatteryManager f9019WWWWoWWWWo`. No native callbacks listed (battery is host-pushed periodically). |
   118→| **Native fn** | `libvm.so` creates `/dev/hal/power_supply*` (per `VM_KR64_ANALYSIS.md` device inventory). |
   119→| **Device paths** | `/dev/hal/power_supply*`, plus the standard `/sys/class/power_supply/` sysfs tree. |
   120→| **IPC mechanism** | File-based: host writes battery stats to a virtual sysfs that the guest's `BatteryService` Java polls. |
   121→| **What guest sees** | A standard `/sys/class/power_supply/battery/` tree. |
   122→
   123→### 1.10 Network (tun0)
   124→
   125→| Field | Value |
   126→|---|---|
   127→| **What it does** | Creates a virtual network interface (`tun0`) with per-VM MAC/IP/gateway/DNS; routes netlink events between guest and host. |
   128→| **Java class** | `com.android.vmcore.hal.NetlinkManager implements InterfaceC1653WoWo`. Holds a `VMNetworkConfig{ifname, mac, ip, gateway_ip, dns_ip}`. JNI: `nativeSetup`, `nativeStartMgr`, `nativeStopMgr`, `nativeSetNetworkConfig(ptr, cfg)`, `nativeOnWifiConnected`, `nativeOnWifiDisconnected`, `nativeOnWifiScanResultsChanged`. |
   129→| **Native fn** | `libvm.so` opens a netlink socket and creates `/dev/netlink_client/*` socket(s). |
   130→| **Device paths** | `/dev/netlink_client/*` (NETLINK_ROUTE emulation), plus the virtual `tun0`. |
   131→| **IPC mechanism** | Netlink protocol (RTM_NEWADDR, RTM_NEWLINK, …) over a Unix socket. |
   132→| **What guest sees** | A real ethernet/wlan interface with the configured IP, gateway, and DNS — full TCP/UDP connectivity via the host. |

   140→| **Device paths** | (Same as Input — emits `EV_KEY` on `/dev/input/key0`.) |

   145→## 2. What HALs does twoyi need? (priority-ranked)

   151→- **Audio:** ❌ Missing.

   160→### Priority 1 — Critical (must have for basic boot)
   161→
   162→| HAL | Why critical | twoyi status |
   163→|---|---|---|
   164→| **Display** | Without it the guest never renders. | ✅ Done. Needs API refactor to per-VM pointer (see §3.1). |
   165→| **Input (Touch + Keys)** | Without it the guest boots but is unusable. | ✅ Done. |
   166→
   167→### Priority 2 — Important (for a usable experience)
   168→
   169→| HAL | Why important | twoyi status |
   170→|---|---|---|
   171→| **Audio** | Most apps produce sound; mute guest is unusable for media/notifications. | ❌ Build new. |
   172→| **Sensor** | Many apps (camera with rotation, games, navigation) refuse to run without accel/gyro/mag. | ❌ Build new. |
   173→
   174→### Priority 3 — Nice to have (for full feature parity)
   175→
   176→| HAL | Why nice-to-have | twoyi status |
   177→|---|---|---|
   178→| **Camera** | Required only by camera apps and barcode scanners. | ❌ Build new. |
   179→| **Location** | Required only by maps/navigation/weather apps. | ❌ Build new. |
   180→| **WiFi** | Required only if the guest checks WiFi state (most apps fall back to "no network"). | ❌ Build new. |
   181→| **Phone** | Required only by dialer/SMS apps. | ❌ Build new. |
   182→| **Battery** | Guest already inherits host's battery via the standard `/sys` passthrough in many setups; only needed if the guest has its own battery UI. | ❌ Build new. |
   183→| **Network** | Required only if the guest needs its own IP identity (most apps work with the host's network). | ❌ Build new. |

   189→### 3.1 Display — refactor API, no new HAL needed
   190→
   191→| Aspect | Plan |
   192→|---|---|
   193→| **Language split** | Java side: replace `Renderer.init/resetWindow/removeWindow` static methods with `DisplayService` instance (per VM). Rust side: `core.rs` already wraps `renderer_bindings::setNativeWindow` and `renderer_new::reset_window` — extend these to take a `ptr` argument. |
   194→| **Device path** | Already created by kr64: `{rootfs}/dev/qemu_pipe` (`devices.rs::create_qemu_pipe`). No change. |
   195→| **IPC mechanism** | Already emugl binary protocol over `qemu_pipe`. No change. |
   196→| **Action** | Refactor `Renderer.java` to `DisplayService.java` with `nativeAddSurface(long ptr, int surfaceId, Surface, w, h, rot)`. This is **VM_JAVA_ANALYSIS.md §7.1 recommendation #1**. Effort: ~1 day. |

   199→
   200→| Aspect | Plan |
   201→|---|---|

   207→### 3.3 Audio
   208→
   209→| Aspect | Plan |
   210→|---|---|
   211→| **Language split** | **Java (most of it):** `AudioService.java` owning `List<AudioTrack>` and `List<AudioRecord>`. JNI: `nativeSetup`, `nativeStartService`, `nativeStopService`, `nativeDispose`. **Rust (thin):** socket accept loop in `app/rs/src/audio.rs` (new file). |

   213→| **IPC mechanism** | Unix socket. On connect: client sends `{sample_rate, channel_count, format, direction (playback/capture)}` header (8–16 bytes). Then bidirectional PCM stream. Rust thread pumps bytes between the socket and the JNI callback (`writeAudioData` / `readRecordData`). |
   214→| **Java callbacks** | `acquireAudioTrack(int[] params)` → `new AudioTrack(STREAM_MUSIC, 44100, STEREO, PCM_16BIT, minBuf, MODE_STREAM)`. `acquireAudioRecord(int[] params)` → `new AudioRecord(MIC, 11025, CHANNEL_IN_MONO, PCM_16BIT, minBuf)`. Match VM's exact sample rates for compatibility. |
   215→| **Action** | Add `audio.rs` (~200 lines), extend `devices.rs` (~30 lines), write `AudioService.java` (~300 lines, ~1:1 port of VM's decompiled class). Effort: ~3 days. |

   217→### 3.4 Sensor (12 types)
   218→
   219→| Aspect | Plan |
   220→|---|---|
   221→| **Language split** | **Java (most of it):** `SensorService.java` owning `Sensor[12]` and `SensorManager`. JNI: `nativeSensorChanged(ptr, idx, ts, x, y, z)`.    225→| **Action** | Add `sensor.rs` (~150 lines), extend `devices.rs` (~30 lines), write `SensorService.java` (~400 lines, port of VM's). Effort: ~2 days. |

   227→### 3.5 Camera
   228→
   229→| Aspect | Plan |
   230→|---|---|
   231→| **Language split** | **Java (most of it):** `CameraService.java` using the deprecated `android.hardware.Camera` API (Camera1, matches VM). JNI: `nativeCameraPicture`, `nativeCameraPreview`. Callbacks: `CameraConnect`, `CameraStart(w,h,fps,client)`, `CameraStop`, `CameraFocus`, `CameraFrame`, `CameraFlash`, `CameraList`. **Rust (thin):** accept loop, route open/close ioctls to Java. |

   235→| **Action** | Add `camera.rs` (~250 lines), extend `devices.rs` (~30 lines), write `CameraService.java` (~600 lines, port of VM's plus format conversion). Effort: ~5 days. |

   274→### 3.10 Network (tun0)
   275→
   276→| Aspect | Plan |
   277→|---|---|
   278→| **Language split** | **Rust (most of it):** `netlink.rs` (new file) — creates `tun0`, handles RTM_NEWADDR/RTM_NEWLINK, forwards to guest. **Java (thin):** `NetlinkManager.java` with `VMNetworkConfig` POJO. JNI: `nativeSetNetworkConfig(ptr, cfg)`. |

   281→| **Gotchas** | Real networking requires the host to actually route the guest's traffic — this means creating a real `tun` device on the host side and configuring NAT. For an MVP, just stub the interface and let the guest share the host's network via binder-level proxying. |
   282→| **Action** | Add `netlink.rs` (~400 lines), extend `devices.rs` (~30 lines), write `NetlinkManager.java` (~200 lines). Effort: ~5 days. |

   318→## 5. Cross-cutting concerns
   319→
   320→### 5.1 HALManager dispatcher pattern
   321→
   322→VM's `HALManager` is a single Java class with a `long mNativePtr` and ~30 private methods (`CameraConnect`, `EnableSensors`, `ExecPhoneCommand`, …) that the native side calls back via JNI. This is the cleanest pattern for twoyi:
   323→
   324→```java
   325→public class HALManager {
   326→    private long mNativePtr;
   327→    private final AudioService mAudioService;
   328→    private final SensorService mSensorService;
   329→    // ...
   330→
   331→    public HALManager(Context ctx, TwoyiProfile profile) {
   332→        mNativePtr = nativeSetup(profile.getId());
   333→        mAudioService = new AudioService(ctx, profile, this);
   334→        mSensorService = new SensorService(ctx, profile, this);
   335→        // ...
   336→    }
   337→
   338→    // Called from native (JNI callbacks):
   339→    private void AudioStart(int sampleRate, int channels) { mAudioService.start(...); }
   340→    private void AudioStop() { mAudioService.stop(); }
   341→    private void EnableSensors(int idx) { mSensorService.enable(idx); }
   342→    private void DisableSensors(int idx) { mSensorService.disable(idx); }
   343→    // ...
   344→}
   345→```
   346→
   347→Rust side: `nativeSetup` returns a pointer to a `*mut HalDispatcher` struct that holds a `JavaVM` + `jobject` (global ref to the HALManager) + a map of device-path → callback-id. The kr64 daemon's accept loop dispatches each connection to the right callback.
   348→
   349→### 5.2 Device-node creation ownership
   350→
   351→VM creates all HAL device nodes inside `libkr64.so` (the kernel-replacement daemon). Twoyi's `app/rs/kr64/src/devices.rs` already follows this pattern — extend it with `create_audio_device`, `create_sensor_device`, `create_camera_device`, `create_location_socket`, `create_wifi_socket`, `create_rild_sockets`, `create_power_supply_files`, `create_netlink_socket`. Each one is ~20 lines following the existing `bind_unix_socket` helper.
   352→
   353→### 5.3 Java↔Rust threading
   354→
   355→Each HAL service needs:
   356→- **Java side:** A `HandlerThread` (so `SensorManager.registerListener` callbacks don't run on the main thread).
   357→- **Rust side:** A dedicated thread per socket (so one blocked HAL doesn't stall the others).
   358→- **JNI up-calls:** Must attach the Rust thread to the JVM via `JavaVM::attach_current_thread` (the `jni` crate handles this).
   359→
   360→### 5.4 Permission strategy
   361→
   362→VM uses `me.weishu.reflection.BootstrapClass.exemptAll()` (the FreeReflection trick) to bypass hidden-API restrictions. Twoyi currently uses only public APIs. For HAL virtualization we need:
   363→- `Camera.open()` — public API ✅
   364→- `SensorManager.registerListener` — public API ✅
   365→- `LocationManager.requestLocationUpdates` — public API (needs `ACCESS_FINE_LOCATION` permission) ✅
   366→- `WifiManager.getScanResults` — public API (needs `ACCESS_WIFI_STATE` + `CHANGE_WIFI_STATE`) ✅
   367→- `TelephonyManager.*` — public API (needs `READ_PHONE_STATE`) ✅
   368→- `AudioRecord` with `MediaRecorder.AudioSource.MIC` — public API (needs `RECORD_AUDIO`) ✅
   369→
   370→**Conclusion: no hidden-API bypass needed for HAL work.** Just declare the permissions in `AndroidManifest.xml`.
   371→
   372→### 5.5 Binder virtualization (orthogonal but blocking)
   373→
   374→VM's `BinderService.setupBinder(vmId, ...)` creates a per-VM `/vm%d/dev/binder` so the guest's `servicemanager` doesn't talk to the host's. Without this, the guest's `getSystemService(ACTIVITY_SERVICE)` returns the **host's** ActivityManager (per `VM_JAVA_ANALYSIS.md` §7.1 takeaway #4). This is **not** a HAL — it's a separate concern — but it's a prerequisite for some HALs (notably Phone, which needs the guest's `TelephonyManager` to be the guest's, not the host's).
   375→
   376→**Action item:** Treat binder virtualization as a separate task (proposed: `BINDER-1`). HAL work can proceed in parallel; only Phone + Network depend on it.
